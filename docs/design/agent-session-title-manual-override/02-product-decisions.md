# 产品方案、关键决策与取舍

## 权威业务合同

本表是本功能核心业务语义的唯一权威定义。其他文档负责展开技术实现、边界和测试，不得改变本表语义。

| 场景 | 权威结果 |
|---|---|
| 用户打开弹窗后取消或关闭 | 不调用 API，不改变标题，不触发手动接管 |
| 用户点击保存，输入合法，API 成功 | 保存规范化标题并将 `title_manually_set` 原子置为 `1` |
| 保存的规范化标题与当前标题相同 | 仍必须调用 API 并完成手动接管；服务端幂等成功 |
| 既有标题不符合手动输入规则 | 弹窗完整回填、不截断；显示对应字段错误并禁止保存，用户编辑为合法标题后才能接管 |
| 既有标题原始长度超过 1000 | 仍完整回填；输入组件不得使用 DOM `maxlength` 截断，迁移和弹窗打开/取消均不得修改历史标题 |
| 用户再次手动保存 | 允许更新标题，`title_manually_set` 保持 `1` |
| 手动接管后恢复自动命名 | 不支持；不存在 UI、API 或隐式恢复路径 |
| manual 下首条用户消息 | 消息与 Run 正常处理，自动标题更新跳过 |
| manual 下 completed `todolist` append | Context item 写回成功，自动标题更新跳过 |
| manual 下 `todolist` update-to-completed | Context item 更新成功，自动标题更新跳过 |
| 手动标题 Store 写入 | 不写 `agent_session.updated_at` |
| idle 时仅调用手动标题 API | 响应中的 `updatedAt` 与调用前相同，列表排序不因改名变化 |
| 运行中调用手动标题 API | 标题写入本身不推进 `updatedAt`；其他并发业务路径可独立推进该字段 |
| Fork 新 Session | `title_manually_set = 0`，不继承源 Session 的手动接管状态 |
| 已持久化 primary/subtask | 均允许手动设置 |
| draft Session | 不显示设置入口，不调用手动标题 API |
| 旧列表请求早于手动 mutation、晚于 mutation 返回 | 若远端仍含该 Session，暂时保留手动 API 成功响应的完整本地 record，不采用旧列表中该 Session 的任何字段；随后强制刷新一次 |
| 组件卸载 | 使所有在途列表和标题 mutation 响应失效，清理弹窗目标；服务端已成功的 mutation 不回滚，但卸载组件不得再写本地状态 |

## 用户体验方案

### Tab 设置入口

在 AI Agent 工具的每个已持久化 Session Tab 中，于标题文本后增加设置图标按钮。

展示规则：

| Session 类型 | 是否展示 |
|---|---:|
| 已持久化 primary | 是 |
| 已持久化 subtask | 是 |
| 本地 draft | 否 |
| “新增 Session”特殊 Tab | 否 |

按钮必须是可聚焦的真实按钮，并显式设置 `aria-label="设置会话标题"`（英文 locale 使用对应英文文本）；Tooltip 仅作视觉提示，不能替代可访问名称。按钮须支持 Enter/Space 激活。点击按钮不得切换 Tab、关闭 Tab 或触发新增 Tab。

### 设置弹窗

弹窗最小内容：

- 标题输入框；
- 当前标题回填；
- 字符限制提示；
- 保存按钮；
- 取消按钮。

弹窗不展示“自动更新标题”开关。产品语义不是可切换模式，而是：首次保存即由用户永久接管。

建议在第一次和以后每次编辑都显示稳定说明：

> 保存后，此会话标题将仅由你手动修改，不再根据消息或任务目标自动更新。

这样用户在第一次保存前能够理解不可逆影响；已接管状态不需要额外从服务端返回，因为 UI 行为始终是“允许继续手动修改”，且没有恢复入口。

### 保存行为

- 打开弹窗时使用当前本地 `session.title` 回填；
- 回填必须保留完整字符串，包括超过 50、超过 1000 或含禁止控制字符的既有标题；
- 输入组件不设置 DOM `maxlength`，避免程序化回填或用户编辑被浏览器静默截断；
- 输入框允许用户编辑；
- 前端按与后端一致的规则压缩空白并校验；
- 既有标题规范化后为空、超过 50 或含禁止控制字符时，显示对应字段错误并禁用保存；
- 用户点击保存且输入合法时一律调用手动设置 API；
- 仅当当前标题符合手动输入规则时，“保存相同标题也接管”才成立；不合法的既有标题必须先编辑为合法值；
- API 不为历史标题设置例外，提交值仍须满足统一请求和业务规则；
- 保存期间禁用重复提交；
- 保存成功后立即原位替换对应 Session 记录；
- 保存失败时保持弹窗、输入内容和焦点上下文，显示可诊断错误；
- 成功后不通过重新排序来突出 Session。

“保存相同标题也接管”是重要边界：用户可能认可当前自动标题，只希望阻止它以后变化。既然弹窗明确告知保存会永久停止自动更新，点击保存就是明确的接管意图。只有取消或关闭弹窗才不产生接管。

## 手动接管语义

### 决策

用户首次成功保存一个合法标题后，无论规范化标题是否与当前标题相同：

- 标题立即变为用户输入的规范化值；
- Session 永久停止自动命名；
- 后续首条消息和 `todolist.goal` 都不得覆盖；
- 用户可以无限次继续手动修改；
- 没有恢复自动命名的产品入口。

### 为什么不可恢复

这是明确的产品需求，而非技术限制。用户一旦主动管理标题，系统不应再猜测何时可以重新接管。

收益：

- 行为简单、可预测；
- UI 不需要模式开关和复杂说明；
- 不存在“切回自动后何时生成新标题”的歧义；
- 不需要维护“当前标题来源”读模型；
- 避免后续 `todolist` 静默覆盖用户意图。

代价：

- 用户误操作后无法恢复自动命名；
- 若未来出现真实需求，需要新增明确的恢复能力和迁移产品合同。

本期接受该代价，不预埋未使用的恢复 UI 或 API。

## 内部标记而非公开模式

### 决策

使用数据库内部字段 `title_manually_set`，不把它加入 `AgentSessionRecord`。

理由：

- 前端不需要根据标记展示不同控件；
- 设置按钮始终可用，弹窗始终只编辑标题；
- 没有恢复功能，不需要前端读取或切换模式；
- 降低共享契约、Worker 协议和其他 Session 读模型的扩散；
- 字段表达的是服务端自动写权限，而非需要公开展示的业务属性。

不得仅从标题文本推断是否手动接管，例如不能用“标题是否等于新会话”或“标题是否与首消息相同”判断。

## 手动标题长度与规范化

### 最终规则

手动标题在后端按以下顺序处理：

- 必须是字符串；
- 将 JavaScript 正则 `/\s+/g` 匹配的连续空白压缩为单个 ASCII 空格；
- `trim()` 去除首尾空白；
- 规范化结果必须满足 `1 <= title.length <= 50`；
- 不合法返回 `400`；
- 超长不得静默截断。

示例：

| 输入 | 结果 |
|---|---|
| `"  修复   登录问题  "` | 保存为 `"修复 登录问题"` |
| `"\n\t"` | `400` |
| 规范化后 50 个 UTF-16 code unit | 成功 |
| 规范化后 51 个 UTF-16 code unit | `400` |

### 为什么手动输入不截断

自动标题必须在无人干预时产生可展示结果，因此沿用截断。手动标题是用户明确输入，静默截断会保存与用户预期不同的名称，应要求用户修正。

### Unicode 与 Emoji

本期长度沿用 JavaScript `string.length`：

- 长度单位是 UTF-16 code unit；
- 常见 BMP 中文字符通常计为 1；
- 部分 Emoji、组合字符、旗帜和肤色序列可能计为多个；
- 不引入 grapheme cluster 分割库；
- 不修改既有自动标题截断算法。

规范化后仍存在的 C0/C1 控制字符必须拒绝：

```text
U+0000–U+001F、U+007F–U+009F
```

前后端都应使用同一认知，但后端是最终权威。Emoji 可见字符计数优化明确不属于本期范围。

## `updatedAt` 与排序

### 决策

- 手动标题 Store SQL 不写 `agent_session.updated_at`；
- 自动标题现有路径继续传入并更新 `updated_at`；
- 不借本需求重定义 Session 活跃时间。

可验收语义按场景区分：

- Session idle 且期间只有手动标题 API 写入时，API 返回的 `updatedAt` 必须与调用前相同；
- Session 正在运行时，手动标题写入本身不得推进 `updated_at`，但消息、Context、Run 等其他并发业务路径可以独立推进它，因此不得断言整个请求期间的最终 `updatedAt` 绝对不变；
- 前端不得因为手动保存响应主动重排 Session；若后续刷新观察到由其他业务活动造成的 `updatedAt` 变化，则按既有排序语义处理。

### 取舍原因

手动改标题属于元数据整理，不代表 Session 发生新的对话活动。若更新 `updated_at`，会导致：

- Session 列表排序变化；
- 近期 Session 列表被元数据操作污染；
- 用户仅改名却看到 Tab/列表位置变化。

现有自动标题更新会写 `updated_at`，见 `apps/api/src/modules/agent/agent.store.ts:642-650`。虽然它与纯元数据语义不完全一致，但本期明确保持，以减少行为变化和回归范围。后续如需统一，应作为独立的 Session 活跃时间治理需求处理。

## Fork、Subtask 与 Draft

### Fork

Fork 是创建新 Session，不是继续编辑原 Session。因此：

- 新 Session 的 `title_manually_set` 必须为 `0`；
- 不继承源 Session 的手动接管状态；
- 即使源 Session 已手动接管，Fork 仍可被后续自动事件命名；
- Fork 初始标题仍沿用当前创建逻辑，例如 `${fromSession.title} (fork)`：
  - `apps/api/src/modules/agent/session/sqlite-session-interaction-store.ts:115-129`

### Subtask

已持久化 subtask Session 允许手动设置标题：

- 后端接口不按 `kind` 拒绝；
- UI 对可见的已持久化 subtask Tab 展示设置按钮；
- subtask 虽然不能发送普通用户消息，但仍可能存在 `todolist` 写回，因此手动锁同样必须生效；
- “subtask session is read-only”仅约束普通发送消息，不应被扩大解释为禁止元数据修改，现有发送限制见 `apps/api/src/modules/agent/session/session-interaction-application.ts:46-52`。

### Draft

Draft 尚无服务端 Session ID 和数据库记录：

- 不显示设置按钮；
- 不为 draft 新增本地改名能力；
- 首次持久化后按真实 Session 规则展示按钮；
- 不允许为了支持 draft 改名而提前创建空 Session。

## 运行中修改

允许在 Agent 正在运行时手动修改标题：

- 不要求取消或暂停 Run；
- 手动写入与自动标题更新通过 SQL 条件保证最终一致；
- 手动设置先完成时，后续自动更新跳过；
- 自动更新先完成时，后续手动设置覆盖并锁定；
- Run、Context item 和 `todolist` 写回结果不受标题锁影响。

不增加基于 Run 状态的 UI 禁用逻辑，因为标题是独立元数据，且禁止运行中修改不能消除自动写回竞争。

## 未采纳方案

### 仅新增 `UPDATE title`，保持后写覆盖

不采纳。后续 `todolist` 会静默覆盖用户刚保存的标题，违背功能目的。

### 暴露 `auto/manual` 模式并允许恢复

不采纳。与最终需求不符，并会引入切回自动后的重算时机、来源展示和更多接口状态。

### 使用 `title_source`

不采纳。需求关心的是“自动写权限是否永久关闭”，不是当前字符串最初来自哪里；`source` 容易产生错误语义。

### 通过应用层先查询标记再更新

不采纳。先读后写存在竞争窗口，无法阻止并发自动更新覆盖手动标题。

### 手动标题也更新 `updated_at`

不采纳。会污染活跃时间并改变排序。

### 手动标题静默截断

不采纳。用户明确输入应获得可预测的校验结果。

### 草稿也允许改名

不采纳。会增加本地状态和创建语义，且不是当前需求。
