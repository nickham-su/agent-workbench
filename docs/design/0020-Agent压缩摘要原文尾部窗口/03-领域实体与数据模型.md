# 领域实体与数据模型

## AgentMessage 判别联合

共享契约采用最小收紧方案：

- `CompactionMessage` 建立严格分支；
- User、Assistant、System、Runtime 保持当前 `status` 与 `parts` 宽约束；
- 所有普通分支通过 `additionalProperties: false` 明确禁止 `retainedFromMessageId`。

```ts
type MessageBase = {
  id: string;
  workspaceId: string;
  previousMessageId: string | null;
  replacesMessageId: string | null;
  depth: number;
  originSessionId: string | null;
  originRunId: string | null;
  updatedRevision: number;
  createdAt: number;
  updatedAt: number;
};

type CompactionMessage = MessageBase & {
  type: "compaction";
  status: "completed";
  retainedFromMessageId: string | null;
  parts: [AgentTextPart];
};
```

`retainedFromMessageId` 只属于 compaction。普通 Message 出现该字段必须被契约拒绝。

## CompactionMessage 字段与 TextPart

| 字段 | 约束 | 业务含义 |
|---|---|---|
| `previousMessageId` | 提交时非空 | 压缩前 head，也是 B 的物理终点 |
| `replacesMessageId` | 必须 null | 压缩不是消息替换 |
| `type` | 固定 compaction | 判别字段 |
| `status` | 固定 completed | 摘要成功后才提交 |
| `originSessionId` | 创建会话 ID | 审计字段，不用于 tail 所属判断 |
| `originRunId` | 创建 Run ID | Run fence 与审计 |
| `retainedFromMessageId` | string/null | B 第一条来源 Message；null 表示 B 为空 |
| `parts` | 单 TextPart | 摘要正文 |

摘要 Part 必须 `position=0`、`text.trim()` 非空，不允许 image、reasoning 或 tool_call。摘要正文与 retainedFrom 在同一事务提交。

合法 fork/subtask 可以继承其他 Session 创建的物理祖先消息。retainedFrom 校验依据是 Workspace、当前 Session 祖先链和 resolver 有效原文序列，不得要求 `originSessionId === currentSessionId`。

## agent_message 数据库约束

新增：

```sql
retained_from_message_id text null
```

冻结约束：

```sql
check (type = 'compaction' or retained_from_message_id is null)
foreign key (retained_from_message_id)
  references agent_message(id)
  on delete restrict
```

增加同 Workspace insert/update trigger：

```text
retained target.workspace_id = new.workspace_id
```

不可变边界：

- `previous_message_id`、`workspace_id`、`depth` 继续遵守现有不可变策略；
- `retained_from_message_id` 创建后不允许更新；
- 非 compaction retained 必须 null；
- compaction retained 可为 string 或 null；
- schema semantics 检测必须验证列、FK 动作、check、Workspace trigger 和 update 拒绝 trigger。

## Workspace destructive cleanup

`retained_from_message_id ON DELETE RESTRICT` 使 compaction 引用的祖先不能先删除。不得通过先执行以下更新绕过不可变边界：

```sql
update agent_message
set previous_message_id = null,
    replaces_message_id = null,
    retained_from_message_id = null
```

准确改造位置是：

- `apps/api/src/infra/db/workspace-agent-data-cleanup.ts`
- `deleteWorkspaceAgentData()`

目标 Message schema 下的唯一可执行顺序固定为：

```text
agent_archived_text_fts行
→ agent_text_part_fts_map
→ agent_client_request
→ session_run_state
→ agent_session_agent_model_override
→ agent_tool_execution
→ agent_message_part
→ agent_run
→ agent_session
→ agent_message逆拓扑批次
→ agent_attachment
```

顺序依据当前 FK：

- FTS map 引用 MessagePart，必须先删 FTS 行和 map；
- `agent_tool_execution.call_part_id → agent_message_part.id ON DELETE RESTRICT`，所以 ToolExecution 必须先于 MessagePart；
- MessagePart 引用 Message 为 `ON DELETE CASCADE`，但为保证 ToolExecution 顺序与可诊断性，仍显式先删 Part；Image Part 对 Attachment 是 `ON DELETE RESTRICT`，删 Part 后才可删 Attachment；
- Run 的 `trigger_message_id → agent_message.id ON DELETE RESTRICT`，所以 Run 必须先于 Message；删除 Run 会按现有 `ON DELETE SET NULL` 解除 Message/Execution 的 `origin_run_id`；
- Session 的 `head_message_id/context_root_message_id → agent_message.id ON DELETE RESTRICT`，所以 Session 必须先于 Message；删除 Session 会按现有 `ON DELETE SET NULL` 解除 Message 的 `origin_session_id`；
- `agent_session_agent_model_override`、`session_run_state`、Run 的 Session FK 虽有 cascade，仍按上表显式删除，避免把关键顺序交给级联副作用；
- 删除 ToolExecution 时，Run 的 `parent_tool_execution_id` 由 `ON DELETE SET NULL` 自动解除；删除 Run 时，parent Run 引用同样由 `ON DELETE SET NULL` 解除。

`agent_context_item` 与 `agent_context_item_attachment` 只属于旧 ContextItem schema，不存在于目标 Message schema。schema 收敛必须先整体重建 Agent 域；旧 schema 的销毁顺序固定为先 `agent_context_item_attachment`、后 `agent_context_item`。`deleteWorkspaceAgentData()` 只运行在目标 schema，不增加运行时双 schema 分支。

完成上述外部引用解除后，才对 Workspace 内 Message 图执行确定性逆拓扑删除，最后删除不再被 Image Part 引用的 Attachment。

图边方向固定为“引用者 → 被引用者”：

```text
X.previous_message_id = Y.id        => X → Y
X.replaces_message_id = Y.id        => X → Y
X.retained_from_message_id = Y.id   => X → Y
```

因此 X 必须先删，Y 后删。每轮候选是当前剩余集合中**没有任何剩余 Workspace Message 引用它**的节点，即从“被引用节点”角度没有入边的节点。`depth DESC, id ASC` 只用于同一轮合法候选的确定性排序，不承担图正确性。

SQL 思路固定为：

```sql
select m.id
from agent_message m
where m.workspace_id = :workspaceId
  and not exists (
    select 1
    from agent_message ref
    where ref.workspace_id = :workspaceId
      and (
        ref.previous_message_id = m.id
        or ref.replaces_message_id = m.id
        or ref.retained_from_message_id = m.id
      )
  )
order by m.depth desc, m.id asc
limit :batchSize;
```

伪代码：

```text
while workspace仍有Message:
  candidates = 查询当前无入边节点
  if candidates为空:
    fail data_invariant_cycle
  delete candidates
```

批次内候选互不引用，因此可在同一事务中删除；每批后重新查询。若仍有节点而候选为空，必须作为 data invariant/cycle failure 中止并保留事务原子性，禁止清空任一图字段绕过 FK。

SQLite 外键检查必须保持开启。实现不得依赖单条无序 `DELETE ... WHERE workspace_id=?` 恰好按某种顺序执行。

必须覆盖：

- 首次压缩后 Workspace 删除；
- 连续压缩、retained 区间跨旧摘要后 Workspace 删除；
- replacement 边连接相同 depth Message 时仍按引用关系删除；
- retained 边、previous 边和 replaces 边同时存在的图；
- ToolExecution 引用 ToolCall Part 时，错误地先删 Part 必须触发 FK，正确顺序清理成功；
- Session head/root 与 Run trigger 在 Message 删除前已解除；
- `PRAGMA foreign_keys=ON` 下完整清理成功；
- 人工 cycle/invariant 异常时明确失败；
- 删除过程中不更新 `previous_message_id`、`replaces_message_id` 或 `retained_from_message_id`。

## 三层 Block

### ResolvedContextBlock

API resolver 生成的来源实体，保存来源 Message、Parts、Executions、附件和原始 replay。它描述逻辑来源，不携带目标 Provider wire message。

### PrimaryMaterializedBlock

按本 Run 主 ExecutionProfile 物化的**附件展开前、provider-neutral 请求语义块**。固定结构为：

```ts
type PrimaryMaterializedBlock = {
  sourceBlockId: string;
  messages: PrimaryProviderNeutralMessage[];
  isProjectionEmpty: boolean;
  canStartRetainedTail: boolean;
  containsTriggerMedia: boolean;
};
```

`messages` 已应用兼容 Provider replay，仍以 `attachment_ref` 表示附件；它不是 `materializePromptAttachments()` 之后带 `file.data` bytes 的最终 `streamText` 请求。该块用于：

- EstimatorV1；
- 20k 选择；
- retained 边界；
- 压缩前后成本；
- Provider 首块合法性。

### SummaryInputBlock

从冻结 A 来源块生成 provider-neutral 摘要语义输入。它不携带 encrypted replay 或 providerOptions；replay-only 且无可见内容时写固定占位。candidate 和 primary 摘要模型消费相同语义。

### RetainableOriginalBlock

这是对 `PrimaryMaterializedBlock` 的业务筛选视图，而不是第四套来源权威。必须同时满足：

- 来源为 completed User/System/Assistant；
- 非 runtime、非 compaction；
- 主 profile 投影非空；
- Assistant 工具执行完整；
- 位于当前 resolver 有效来源集合。

空投影块不计预算、不算进展、不能成为 retainedFrom。

## CompactionPlan

```ts
type CompactionMode =
  | "proactive"
  | "manual"
  | "context_limit_standard"
  | "context_limit_full";

type CompactionPlan = {
  planId: string;
  expectedHeadMessageId: string | null;
  expectedRevision: number;
  mode: CompactionMode;
  estimatorVersion: "estimator-v1";
  profileFingerprint: string;

  resolvedSourceBlockIds: string[];
  prefixSourceBlockIds: string[];
  retainedSourceBlockIds: string[];
  retainedFromMessageId: string | null;

  estimatedBeforeCost: number;
  estimatedPrefixCost: number;
  estimatedRetainedCost: number;
  containsTriggerMedia: boolean;
};
```

Plan 冻结来源 ID、顺序、A/B、主 profile fingerprint 和成本，不冻结 candidate/primary Provider wire messages。

Plan 不变量：

- A/B 是同一 source 快照的连续逻辑切分；
- B 只含主 profile 下非空可保留原文；
- current compaction 只能进入 A；
- `retainedFromMessageId` 等于 B 第一来源块 ID；
- candidate→primary 不改变 A/B 或 `SummaryInputBlock` 语义；
- CAS conflict 或 fingerprint 变化使 Plan 与摘要正文全部作废。

```ts
type CompactionResult =
  | { kind: "committed"; messageId: string }
  | { kind: "no_prefix" }
  | { kind: "no_progress" }
  | { kind: "blocked_oversized_tail" }
  | { kind: "blocked_media_requires_resend" }
  | { kind: "blocked_pending_tools" }
  | { kind: "summary_input_limit" }
  | { kind: "provider_unavailable" }
  | { kind: "conflict" }
  | { kind: "cancelled" };
```

不得再用 boolean 混淆 committed、skipped、blocked 和 failed。

## ToolExecution 终态时间

`agent_tool_execution.completed_at` 与共享 `AgentToolExecution.completedAt` 是终态执行时间的唯一字段，读侧与内部DTO必须原样返回。普通工具完成路径保持既有语义；本方案额外冻结 convergence 的异常终结规则：

- queued→cancelled、running→unknown 时，`completedAt` 必须等于本次 `convergence.updatedAt`；
- `startedAt` 原样保留；不得为了取消或unknown伪造、清空或覆盖 result、structured result、artifact path 或 error；
- status、`completedAt`、`updatedAt`、`updatedRevision` 必须和本Run其余convergence写入处于同一数据库事务；
- completed intent的不变量失败必须回滚，不能只更新任一ToolExecution；
- 已terminal的一致重放必须验证并保留既有`completedAt`，不得以新的请求时间刷新它。

## Run terminal result

结果属于 Run，不属于 `session_run_state`。为使 startup recovery 不依赖消息/工具产物猜测终态，`agent_run` 新增持久阶段和 terminal intent：

```sql
execution_phase text not null,
intended_terminal_status text null,
intended_terminal_code text null,
intended_terminal_detail text null,
terminal_result_code text null,
terminal_result_detail text null
```

阶段固定为：

```text
work_pending
work_in_progress
terminal_intent_persisted
terminal
```

状态机：

```text
Run创建 → running/work_pending
Worker真正开始 → running/work_in_progress
有持久成功产物 → 同一事务完成产物 + running/terminal_intent_persisted + intended三元组
无产物结果 → persistTerminalIntent → running/terminal_intent_persisted + intended三元组
convergence → 同一事务收敛本Run产物、Run terminal result/phase、session_run_state与Session revision
```

数据库必须强制：

- `status='running'` 时 phase 只能是前三种；`status in ('completed','failed','cancelled')` 时 phase 必须为 `terminal`；
- `work_pending/work_in_progress` 时 intended 与 terminal result 全部为 null；
- `terminal_intent_persisted` 时 status 仍为 running，`intended_terminal_status` 必须是 completed/failed/cancelled，intended code 必须非空，intended detail 可 null，实际 terminal result 必须为 null；
- `terminal` 时 intended 三列必须清空，实际 `terminal_result_code` 必须非空；
- intended/actual code 长度都必须为 1..80；intended/actual detail 非 null 时长度必须为 1..240；
- intended 与 actual 的 runKind/status/code/detail 合法性都由同一全局 registry 验证；
- `terminal_result_code` 长度必须为 1..80；
- `terminal_result_detail` 可为 null，非 null 时长度必须为 1..240；
- detail 默认 null，只允许全局 registry 中的枚举化诊断键，不允许自由文本或“安全文案”；
- 禁止保存 Provider 原始响应、异常堆栈、用户文本、摘要、工具内容、密文或凭证；
- 已终态 Run 的相同幂等收敛可成功返回，试图改写 status/code/detail 必须 conflict/data invariant failure。

数据库强制 status/result nullability 与长度等基本形态约束；完整 runKind/status/code 合法组合由代码中的全局 registry 作为唯一业务权威，避免巨型 SQL 码表。API 在写入事务前必须严格验证组合，unknown code 一律拒绝。

终态控制流程必须有两个幂等原语：

```text
persistTerminalIntent(runId, intendedStatus, intendedCode, intendedDetail)
convergeRunTerminal(runId)
```

`persistTerminalIntent` 只用于没有持久业务产物的结果，原子写 intended 三元组并将 phase 置为 `terminal_intent_persisted`；完全相同的重放成功，不同 intent 冲突拒绝。

`convergeRunTerminal` 不接收 Worker 任意结果，只读取已持久的 intended status/code/detail，并在**一个数据库事务**内完成下列全部收敛：

- 严格按 `workspaceId + sessionId + runId` 的 origin 范围选择本 Run 的 Message 与 ToolExecution，绝不触碰其他 Run；
- intended 为 `completed` 时，断言本 Run 不存在 streaming 或其他非终态 Message，且不存在 queued/running ToolExecution；若不满足即 data invariant failure，整个事务回滚，禁止将 Session 置 idle；
- intended 为 `failed` 时，将本 Run streaming Assistant 置为 failed，queued ToolExecution 置为 cancelled，running ToolExecution 置为 unknown；
- intended 为 `cancelled` 时，将本 Run streaming Assistant 置为 cancelled，queued ToolExecution 置为 cancelled，running ToolExecution 置为 unknown；
- queued→cancelled或running→unknown时，对每个发生变化的ToolExecution在同一行写`completedAt=convergence.updatedAt`、`updatedRevision`与`updatedAt`；保留`startedAt`，不得伪造、清除或改变result/error。running→unknown保持“副作用可能已发生”的既有诊断语义，queued→cancelled表示未执行；
- 对上述实际发生变化的 Message 写入 `updatedRevision`、`updatedAt`；
- 递增 Session revision，写 Run 实际 status/result、phase=terminal、清空 intended 三元组，并将本 Session 的 `session_run_state` 收敛为 idle；
- 以上 artifact 状态、revision/timestamp、Run、Session 与 run state 写入必须同事务提交，任一检查或写入失败均不得留下部分收敛。

持久化原语返回：

```ts
type ConvergeRunTerminalResult = {
  kind: "transitioned" | "already_converged";
  finalStatus: "completed" | "failed" | "cancelled";
};
```

已 terminal 时，仅当实际 status/result、相关 origin artifact状态（包括ToolExecution的`completedAt`）、Session/run state收敛状态全部与上述规则一致才返回`already_converged`；首次完整提交返回`transitioned`。不同终态、残留 streaming/nonterminal Message、queued/running ToolExecution 或其他矛盾必须 conflict/data invariant failure。intent 持久后崩溃时，startup 调用同一原语完成全部收敛。

应用层在收到任一成功结果后调用唯一`afterConvergeRunTerminal`：总是`runPromptStaticCache.clear(runId)`；仅`transitioned`调用既有`agent.run.completed.v1`发布器，事件携带该`finalStatus`。发布在数据库提交之后；发布器或SSE listener失败只记录错误，绝不回滚终态事务，也不通过`already_converged`补发。本次不建outbox，接受进程内best-effort事件可能永久漏送的风险。

有持久业务产物的成功结果，产物与 intent 必须处于同一数据库事务，不能先提交产物再调用独立 intent RPC：

- user 最终 Assistant 与 subtask 最终 Assistant 使用原子 `completeTerminalAssistantWithExecutions`：完成 Assistant、保存 response tokens，写 terminal intent；该入口要求 ToolExecution 为空且 Assistant 不含 ToolCall，分别写 `run_completed` 或 `subtask_completed`；replay/reasoning 可保留；
- manual compaction 成功使用原子 `commitCompaction`：插入 CompactionMessage 与 TextPart、更新 Session root/head、写 `completed/compaction_completed` intent；
- 原子请求响应丢失时，以相同的 Assistant/Parts/Executions 或 compaction 坐标、摘要、retainedFrom 和 intent 重放；持久层必须同时验证产物与 intended 三元组完全相同才成功，否则 conflict。

Worker 在流结束后、本地已知 `recognizedCalls.length`、可见文本和空响应计数时选择完成入口：

- 有 ToolCall 时只能调用普通 `completeAssistantWithExecutions`，不写 intent，继续工具/下一模型步骤；
- 无 ToolCall 且有可见文本时调用原子 terminal Assistant 入口；
- 空 Assistant 在计数未达到阈值时调用普通入口并继续；第 N 次空响应在提交前已知达到阈值，调用原子 terminal Assistant 入口；
- `runModelStep()` 不得无条件先完成 Assistant 再让外层决定终态；应重构为在流结束且终态规则已判定后选择上述入口。

无业务产物或失败/取消结果使用独立 `persistTerminalIntent`，包括：

- manual no_prefix/no_progress/blocked/provider failure；
- user/subtask provider 或 Worker failure、context-limit failure；
- 用户取消；
- API enqueue failure、API cancel 与 startup recovery failure。

最终 Assistant、ToolExecution 或 CompactionMessage 都不是 terminal intent 权威，startup recovery 不得据此推断业务已经结束。唯一权威是 `execution_phase='terminal_intent_persisted'` 及 intended 三元组。

独立 `persistTerminalIntent` 与 `convergeRunTerminal` 共享同一个独立 10 秒 terminal-control budget。intent 阶段最多三次真实 HTTP 请求；intent 成功后 convergence 在剩余预算内最多三次真实 HTTP 请求；每阶段重试间隔固定 250ms，因此总真实 HTTP 请求最多六次，但总时长绝不超过10秒。API Client 两个 RPC 均 `maxRetries:0`，重试只存在于 Runner/专用 terminal loop。原子 terminal Assistant 与原子 compaction commit 属于 work transaction，受 work deadline 和其自身幂等重试政策约束；原子成功后只调用 convergence：在首次 convergence 前创建新的10秒控制面deadline，最多3个真实HTTP请求，不消耗独立 intent 阶段请求额度。

若独立 intent 三次仍完全写不进去，数据库 phase 保持 `work_in_progress`，startup 按现有安全恢复规则处理：可恢复则继续同一 Run；不可恢复则由 API 先持久化 `failed/run_startup_recovery_failed` intent，再走同一 convergence。若任一原子成功产物或独立 intent 已写而 Worker 崩溃或 convergence 未完成，startup 只执行同一完整 convergence，绝不重跑业务；不再存在“成功产物已提交而 phase 仍为 work_in_progress”的合法窗口。

## Workspace删除的Run收敛编排

删除应用层唯一使用`convergeWorkspaceRunsForDeletion`，替换并删除旧`cancelWorkspaceRunsAndConverge`直接改artifact的实现。该函数不是新的持久化权威，而是按以下固定顺序编排既有原语：持久deletion intent、设置deleting fence、按`sessionId`稳定序获得相关Session handoff locks、查询本Workspace当前active的user/manual/subtask Run、按`runId`稳定序逐Run处理。每个Run各自使用短数据库事务：无intent时本地持久`cancelled/run_cancelled` intent后调用完整convergence；已有相同取消intent直接converge；已有其他intent先converge原intent，已terminal后跳过。每次convergence均经过`afterConvergeRunTerminal`。

只有所有Run的数据库收敛成功，才能在锁内按稳定Session顺序调用`runtime.cancelSessionAndWait`并drain；所有drain成功才可进入Workspace destructive cleanup。任一Run冲突/invariant失败或任一drain失败均停止且保留deletion intent/fence供重试；前者不允许开始drain或物理删除，后者重试时不得改变已terminal结果。查询、更新和runtime调用均按workspaceId严格过滤，子任务Run不得漏掉，其他Workspace不得受影响。

## 数据不变量
