# ModelContext Resolver、物化层与尾部算法

## 唯一权威原则

新增模型上下文专用 resolver，统一定义：

- 当前有效动态上下文的来源集合；
- 当前摘要和 retained tail 的展开；
- `ResolvedContextBlock`；
- provider-neutral transcript；
- Provider replay source；
- 提交端合法来源范围。

主模型 PromptContext、compaction source、proactive/manual 两种压缩规划、连续压缩和提交校验必须复用它。

普通 Timeline 不复用 ModelContext Resolver，而使用独立展示链：

- 从 Session head 沿 `previousMessageId` 回溯到最早可达祖先，再按旧到新排列；
- 不按摘要 S、retained tail B 的模型逻辑顺序重排，也不去重或隐藏压缩前原文；
- 以 `contextRoot..head` 计算 `inCurrentOperationRange`，root 之前消息只读；
- context root 变化会改变整段历史的操作区间标记，因此 delta 必须 reset 或返回等价的全量边界更新，不能只追加 compaction Message。

## Compaction source 请求与一致快照

请求固定为：

```ts
{
  workspaceId: string;
  sessionId: string;
  runId: string;
}
```

客户端不得传入 triggerMessageId、locale、pending 截止或 head/revision。API 必须：

- 读取 Run；
- 校验 `run.workspaceId/sessionId` 与请求一致；
- 校验 Run 是当前 Session 的 active Run，或符合既有受保护恢复读取规则；
- 从 Run 派生 triggerMessageId、agent/provider/model、runKind；
- 从 `session_run_state` 派生 pending 范围；
- 本次将 locale 固定为 `null`，生成 locale-neutral 的 one-shot 摘要提示；不从 Run 或其他历史 Run 推断 locale；
- 在单个 `better-sqlite3` `db.transaction(() => ...)` deferred 只读事务中读取 Session 坐标、Run、链、Parts、ToolExecutions、replay、附件引用和 pending 状态。

返回的 `headMessageId/sessionRevision/contextRootMessageId/blocks` 必须来自同一事务快照。读取只能采用该事务方案；事务外不得补读 blocks，Worker 也不得重新读取历史补齐摘要输入。

## 当前摘要与 retained 区间

若 context root 不是 compaction：

```text
有效来源 = contextRoot..head
```

若 context root 是 compaction S：

```text
有效来源 = S + retainedRange(S) + S 后消息
```

retained 闭区间：

```text
start = S.retainedFromMessageId
end = S.previousMessageId
```

沿 `previousMessageId` 从 end 回溯到 start，必须实际抵达，且全部属于同一 Workspace。读取后反转为旧到新。

区间规范化：

- 跳过旧 compaction，不递归；
- 跳过 runtime 和非 completed Message；
- 绑定 Assistant 的全部终态 ToolExecution；
- 保留原始 replay envelope；
- 按 Message ID 防御性去重。

fork/subtask 合法共享祖先按 Workspace + 当前 Session 祖先链判断，不要求 originSessionId 相同。

## 三层来源与物化

### ResolvedContextBlock

API resolver 输出的逻辑来源块，保存：

- 来源 Message ID、类型和物理坐标；
- Parts、ToolExecutions、附件元数据；
- 原始私有 replay envelope；
- 当前摘要、原文和 pending 边界标记。

它不携带目标 Provider wire message，也不决定 token 成本。

### PrimaryMaterializedBlock

Worker 按本 Run 主 `ExecutionProfile` 生成附件展开前的 provider-neutral 请求语义块：

```ts
type PrimaryMaterializedBlock = {
  sourceBlockId: string;
  messages: PrimaryProviderNeutralMessage[];
  isProjectionEmpty: boolean;
  canStartRetainedTail: boolean;
  containsTriggerMedia: boolean;
};
```

其语义固定为：

- 已按主 profile 投影；
- 已调用兼容 replay helper，把 OpenAI Responses replay 应用到对应 assistant part；
- 当前 trigger 附件仍保持 `attachment_ref`，不读取文件 bytes；
- 不是最终 `streamText` 的 file/bytes 消息；
- 不缓存跨 Provider wire object。

生产顺序唯一为：

```text
ResolvedContextBlock
→ PrimaryMaterializedBlock（attachment_ref + compatible replay）
→ estimatePrimaryMaterializedBlock(block)
→ request-only materializePromptAttachments（attachment_ref → file + bytes）
→ streamText
```

`materializePromptAttachments()` 只属于实际主模型请求阶段，不得提前到 planner/Estimator，也不得把文件 bytes、临时 URL 或存储读取结果写入 Plan/canonical。PrimaryMaterializedBlock 还包含或派生：

- EstimatorV1 canonical 和成本；
- 是否投影非空；
- 是否可作为 `retainedFromMessageId` 起点；
- 是否包含当前 trigger 媒体。

它是以下行为的唯一成本与边界依据：

- 20k 尾部选择；
- retained 起点；
- `estimatedBefore`；
- `estimatedAfter = estimate(S+B)`；
- 主 Provider 的 Assistant 首块合法性。

当前摘要物化为 system message，计入压缩前成本并可进入 A，但永不进入 B，也不能成为 retainedFrom。

目标 profile 下投影为空的原文块成本为 0，不参与 20k、不算有效进展、不能成为 retainedFrom；它可以物理位于 retained 闭区间，由主模型投影过滤。

### SummaryInputBlock

从冻结 A 的 `ResolvedContextBlock` 来源生成 provider-neutral 摘要语义，不复用主 Provider wire replay：

- 保留可见 text；
- 保留可见 reasoning text；
- 保留 tool name、tool input、tool result preview/error；
- 不携带 `encryptedContent`、Provider 私有 replay item 或 `providerOptions`；
- replay-only 且没有任何可见内容的 Assistant 固定生成：

```text
[Prior assistant replay state omitted from summary input]
```

candidate 与 primary 摘要模型消费完全相同的 `SummaryInputBlock[]` 语义输入，各 Provider SDK 只负责协议转换。切换摘要模型不得改变 A/B、块顺序或摘要内容语义。

## profileFingerprint

执行顺序固定为：

```text
getExecutionProfile
→ normalize profile并计算fingerprint
→ getCompactionSource
→ PrimaryMaterializedBlock物化
→ plan
```

`CompactionPlan.profileFingerprint` 必填。模型 ID 规范化规则固定为：

```ts
const normalizedModelId = profile.model.providerModelId ?? profile.model.id;
```

`providerModelId` 按现有 schema 已是非空字符串；实现可做等价 trim 防御，但不得在有值时退回 `model.id`。fingerprint 输入固定为：

```text
profile.resolved.providerId
normalizedModelId
profile.provider.npm
providerAdapterIdentity
profile.model.contextWindowTokens
primaryMaterializerVersion
estimatorVersion
```

当前 `ExecutionProfile` 没有独立 `api` 字段，不得编造 `profile.api`。`providerAdapterIdentity` 由以下三项构成：

- `provider.npm`；
- Worker 实际主模型调用路径的稳定标识；
- 该调用路径维护的固定 Provider API 映射，例如官方 `@ai-sdk/openai` 主调用路径映射为 `responses`。

fingerprint 对上述对象做稳定 canonical 后计算摘要值。不得包含 API key、Authorization、baseURL、代理凭证、Provider options 或其他秘密。

CAS conflict 后必须重新执行 `getExecutionProfile → fingerprint`，然后才允许重新 source：

- fingerprint 不同：旧 Plan 与摘要正文全部作废；proactive 跳过，manual 以 `compaction_conflict` 终止；
- fingerprint 相同：才可重新 `getCompactionSource`、物化、规划和摘要；
- 不得继续使用旧 source、旧物化结果、旧 A/B 或旧成本。

## EstimatorV1 生产契约

### 输入与版本

Estimator 不直接 canonicalize AI SDK `ModelMessage`。唯一流水线是：

```text
estimatePrimaryMaterializedBlock(block)
→ block.messages（附件展开前的 provider-neutral消息数组）
→ mapEstimatorCanonicalMessages()
→ EstimatorCanonicalMessage[]
→ canonical JSON
→ cost
```

生产接口固定为：

```ts
function estimatePrimaryMaterializedBlock(block: PrimaryMaterializedBlock): EstimatorEstimate;
```

不提供接受裸 `ModelMessage[]`、单条 message、canonical object 或 attachment bytes 的生产重载。这样可以显式排除 AI SDK 与 Provider 的不稳定字段，并只对白名单 replay 字段计费。Estimator 输入不是持久化 Message、`SummaryInputBlock`、最终 file/bytes 请求或 Provider wire object。

```ts
const ESTIMATOR_VERSION = "estimator-v1";
const COMPACTION_KEEP_RECENT_TOKENS = 20_000;
```

相同 `profileFingerprint + estimatorVersion + PrimaryMaterializedBlock fixture` 必须产生逐字节相同的 `EstimatorCanonicalMessage[]`、canonical JSON 和估值。

### 专用 canonical schema

```ts
type EstimatorCanonicalReplayProvider = {
  npm: "@ai-sdk/openai";
  api: "responses";
  providerId: string;
  model: string;
};

type EstimatorCanonicalReplay = {
  provider: EstimatorCanonicalReplayProvider;
  item:
    | { type: "text"; itemId: string; phase?: "commentary" | "final_answer" }
    | { type: "reasoning"; itemId: string; encryptedContent: "<encrypted>" }
    | { type: "function_call"; itemId: string };
};

type EstimatorCanonicalUserPart =
  | { type: "text"; text: string }
  | { type: "attachment_ref"; mediaType: string; filename: "<filename>" };

type EstimatorCanonicalAssistantPart =
  | { type: "text"; text: string; replay?: EstimatorCanonicalReplay }
  | { type: "reasoning"; text: string; replay?: EstimatorCanonicalReplay }
  | {
      type: "tool-call";
      toolCallId: string;
      toolName: string;
      input: CanonicalJsonValue;
      replay?: EstimatorCanonicalReplay;
    };

type EstimatorCanonicalToolResultPart = {
  type: "tool-result";
  toolCallId: string;
  toolName: string;
  output: {
    type: "text" | "error-text";
    value: string;
  };
};

type EstimatorCanonicalMessage =
  | { role: "system"; content: string }
  | { role: "user"; content: string | EstimatorCanonicalUserPart[] }
  | { role: "assistant"; content: EstimatorCanonicalAssistantPart[] }
  | { role: "tool"; content: EstimatorCanonicalToolResultPart[] };
```

`CanonicalJsonValue` 只允许 null、boolean、有限 number、string、数组和普通对象。ToolCall `input` 中出现 `undefined`、`NaN`、`Infinity`、函数、symbol、循环引用或非 JSON 对象时立即 data invariant failure。

### 真实 ModelMessage 到 canonical 的映射

映射必须与 `runtime-transcript-projector.ts` 和 `openai-responses-replay.ts` 的真实输出一致：

| 真实输入 | Canonical 输出 |
|---|---|
| system | 只取 `{role:"system",content:string}` |
| user string | 保持 string，不改造成 part 数组 |
| user text part | 只取 `type/text` |
| user `attachment_ref` | 只取 `type/mediaType`，filename 固定为 `<filename>` |
| assistant string | 规范化为单个 text part；空字符串规范化为空数组 |
| assistant text | 只取 `type/text` 和兼容 replay 白名单 |
| assistant reasoning | 只取 `type/text` 和兼容 replay 白名单 |
| assistant tool-call | 只取 `type/toolCallId/toolName/input` 和兼容 replay 白名单 |
| empty assistant | `{role:"assistant",content:[]}` |
| tool message | 保持 tool result part 顺序 |
| tool-result | 只取 `toolCallId/toolName/output.type/output.value` |

当前 `RuntimeTranscriptProjector.projectDetailed()` 产生的真实 ToolResult 为：

```ts
{
  type: "tool-result",
  toolCallId,
  toolName,
  output: { type: "text" | "error-text", value: string },
}
```

不得改写为 `result` 字段，也不得遗漏 `toolName` 或 `output.type`。

删除规则固定为：

- 排除 message-level `providerOptions`；
- 排除所有不兼容或未知 Provider 的 `providerOptions`；
- 排除 OpenAI options 中除当前 replay 白名单之外的字段；
- 排除 `providerExecuted`、时间戳、运行时 ID、SDK 临时字段、对象原型、本地路径、附件 `workspaceId/attachmentId`、URL、二进制和凭证；
- 对支持集合外的 message role 或 content part 明确失败，不得静默 stringify；
- 添加、删除或改变任意未知 `providerOptions`，EstimatorCanonicalMessage 和估值必须不变。

### OpenAI Responses replay 映射

只在主 profile 使用官方 `@ai-sdk/openai` Responses adapter，且 part 上的 `providerOptions.openai` 与当前 profile 兼容时映射 replay。Provider identity 不从任意 options 信任输入，而是从当前 ExecutionProfile 与固定 adapter 映射构造：

```text
provider.npm = "@ai-sdk/openai"
provider.api = "responses"
provider.providerId = profile.resolved.providerId
provider.model = providerModelId ?? model.id
```

真实 part 映射固定为：

- reasoning part：读取 `itemId`、`reasoningEncryptedContent`；canonical item type 为 `reasoning`，密文替换为 `<encrypted>`；
- text part：读取 `itemId` 和可选 `phase`；canonical item type 为 `text`；
- tool-call part：读取 `itemId`；canonical item type 为 `function_call`；
- 当前 `applyOpenAiResponsesReplay()` 没有把 `summaryIndex` 注入真实 ModelMessage part，因此 Estimator 不得从别处补造该字段；若未来真实 part schema显式加入，必须提升 estimator version 后再纳入；
- 缺失 `itemId`、类型不匹配、非官方 adapter 或不兼容模型的 options 全部按普通 part 估算，未知 options 不影响成本。

真实 reasoning 密文不进入 canonical。每个被接受的 reasoning replay 额外增加：

```ts
64 + Math.ceil(utf8ByteLength(reasoningEncryptedContent) / 4)
```

日志、错误和 golden 失败输出不得打印真实密文。

### Canonical JSON

每个 `PrimaryMaterializedBlock` 将映射完成的**整个 `EstimatorCanonicalMessage[]` 数组**作为唯一 canonical JSON 根：

```ts
const canonicalMessages = mapEstimatorCanonicalMessages(block.messages);
const canonicalJson = canonicalJsonStringify(canonicalMessages); // 根必为数组
```

禁止逐 message stringify 后拼接，也禁止单条消息时省略 `[`、`]`。数组方括号和消息间逗号都进入 UTF-8 字节成本。

- 对象 key 在每一层递归按字典序排序；比较 key 的 Unicode code point 序列，不使用 locale；
- 数组保持原顺序；
- 字符串保持原 Unicode 内容，按标准 JSON 转义，不做 NFC/NFD、大小写或 locale 归一化；
- 数字只允许有限 JSON number，使用标准 JSON 数字表示；
- 禁止 `undefined`、`NaN`、`Infinity` 和函数；发现即 data invariant failure，不允许省略或转为 null；
- ToolCall input 递归使用同一 canonical JSON 规则。

```ts
const textTokens = Math.ceil(utf8ByteLength(canonicalJson) / 3);
```

文本内容不分语言、代码或标点类别，统一按 canonical JSON 的 UTF-8 字节数计算。

### 固定开销

| 结构 | 固定开销 |
|---|---:|
| 每条 ModelMessage | 8 tokens |
| 每个 content part | 4 tokens |
| 每个 tool call | 额外 8 tokens |
| 每个 tool result | 额外 8 tokens |
| 每个 attachment_ref | 额外 1,024 tokens |

user/system string content 不计 content-part 开销；数组中的 text、attachment、reasoning、tool-call 和 tool-result 各计一个 content part。固定开销只补偿协议结构。

### Attachment canonical

`attachment_ref` canonical：

- 保留真实 `mediaType`；
- `filename` 一律替换成固定 `"<filename>"`；
- 不保留 attachmentId、本地路径、临时 URL 或二进制；
- 不按扩展名、图片尺寸或媒体子类型分类；
- 每个 attachment 在 canonical 文本成本之外再加 1,024 tokens。

### 最终公式

```ts
const fixedCosts =
  messageCount * 8
  + contentPartCount * 4
  + toolCallCount * 8
  + toolResultCount * 8
  + attachmentCount * 1024
  + replayEncryptedExtra;

const estimate = Math.ceil((textTokens + fixedCosts) * 1.10);
```

- 安全系数固定为 10%；
- 一个 Block 对整个数组根只计算一次 `textTokens ceil` 和一次最终 1.10 安全系数 `ceil`，不得逐 message ceil；
- block 总成本为各 block estimate 之和；
- 总历史成本为 `sum(estimatePrimaryMaterializedBlock(block))`，不得把多个来源 Block 合并后重新 ceil；
- 修改任一 canonical 规则、开销或系数必须提升 estimator version。

### Canonical 示例与 golden 数值

以下示例展示“真实 PrimaryMaterializedBlock fixture → EstimatorCanonicalMessage[] → 数组根 canonical string”。对象 key 已递归排序，数组保持真实顺序。

#### System 与 User string

```json
[{"content":"You are helpful.","role":"system"}]
[{"content":"修复 build error","role":"user"}]
```

#### User parts 与 attachment_ref

```json
[{"content":[{"text":"请看截图","type":"text"},{"filename":"<filename>","mediaType":"image/png","type":"attachment_ref"}],"role":"user"}]
```

#### Assistant text、reasoning、tool-call

```json
[{"content":[{"text":"先检查类型。","type":"reasoning"},{"text":"开始读取。","type":"text"},{"input":{"path":"a.ts"},"toolCallId":"call_1","toolName":"read","type":"tool-call"}],"role":"assistant"}]
```

#### Empty Assistant

```json
[{"content":[],"role":"assistant"}]
```

#### Tool message 与真实 tool-result

```json
[{"content":[{"output":{"type":"text","value":"ok"},"toolCallId":"call_1","toolName":"read","type":"tool-result"}],"role":"tool"}]
```

#### 一个来源 Block 映射成多条 ModelMessage

Assistant ToolCall 原子块会映射成 assistant + tool 两条消息，但仍只有一个 canonical 数组根：

```json
[{"content":[{"input":{"path":"a.ts"},"toolCallId":"call_1","toolName":"read","type":"tool-call"}],"role":"assistant"},{"content":[{"output":{"type":"text","value":"ok"},"toolCallId":"call_1","toolName":"read","type":"tool-result"}],"role":"tool"}]
```

- UTF-8 bytes：248，其中包含 `[`、`]` 和两条消息之间的逗号；
- textTokens：83；
- fixedCosts：`2*8 + 2*4 + 8 + 8 = 40`；
- estimate：136；
- 必须断言只执行一次最终 `ceil((83+40)*1.10)`，不能把两条消息分别估算后相加。

#### Reasoning replay

真实 fixture 的 reasoning part 输入片段如下。它用于说明 mapper 的来源结构，不是 canonical JSON golden；Estimator 的 canonical JSON 根仍然只能是完整消息数组：

```ts
{"providerOptions":{"openai":{"itemId":"rs_1","reasoningEncryptedContent":"YWJjZA=="}},"text":"需要检查类型。","type":"reasoning"}
```

其 canonical message 为：

```json
[{"content":[{"replay":{"item":{"encryptedContent":"<encrypted>","itemId":"rs_1","type":"reasoning"},"provider":{"api":"responses","model":"gpt-5","npm":"@ai-sdk/openai","providerId":"openai"}},"text":"需要检查类型。","type":"reasoning"}],"role":"assistant"}]
```

text 与 tool-call replay 分别使用 `item.type = "text"` 和 `item.type = "function_call"`；它们没有密文额外成本。golden 必须分别覆盖三种 replay part。

### Golden 测试要求

每个 golden 必须以真实 `PrimaryMaterializedBlock` fixture 为输入，不能直接手写 canonical 或传裸 message 数组。固定断言链为：

```text
真实 PrimaryMaterializedBlock fixture
→ EstimatorCanonicalMessage[]
→ canonical string
→ UTF-8 byte length / fixedCosts / replayEncryptedExtra
→ 最终 estimate
```

每个 fixture 同时断言：

- 映射后的专用 canonical 对象深度相等；
- canonical string 完全相等；
- UTF-8 byte length；
- textTokens；
- fixedCosts 分项；
- 最终 estimate。

fixture 集合固定覆盖 system、user string、user text parts、attachment_ref、assistant string/text、reasoning、tool-call、empty assistant、tool message、真实 tool-result、OpenAI text/reasoning/function_call replay、嵌套 ToolCall input、多个 attachment、不同密文长度。另断言未知/message-level providerOptions、OpenAI 非白名单字段和 key 插入顺序变化不改变结果；非法 JSON 值明确失败。

另有强制 fixture：一个 `ResolvedContextBlock` 经 Primary materializer 映射成 assistant+tool 多条消息，断言数组方括号、消息间逗号、一次 ceil/安全系数和 block estimate；两个独立 Block 的总成本只做逐 Block estimate 求和。

## 20k 尾部选择

候选集合只包括主 profile 下非空的 `PrimaryMaterializedBlock` 原文块。

```ts
let total = 0;
let first = blocks.length;
for (let i = blocks.length - 1; i >= 0; i--) {
  if (total + blocks[i].estimatedTokens > 20_000) break;
  total += blocks[i].estimatedTokens;
  first = i;
}
```

随后校正首块合法性：

- 若首块 `validAsRetainedStart=true`，完成；
- 若为不合法 Assistant 起点，向前扩到最近合法 User/System 块；
- 将扩入块全部计费；
- 扩展后超过 20k，则标准窗口不可用；
- 不注入 synthetic 承接消息。

当前 trigger 含附件时：

- B 必须从该 trigger User 或更早合法块开始；
- trigger 块及其后缀超过 20k，标准窗口不可用；
- proactive 跳过；manual 返回 `compaction_media_requires_resend`。

## A/B 与有效进展

```text
A = 当前摘要（如有） + 未进入 B 的非空来源块
B = 选中的非空 PrimaryMaterializedBlock 原文后缀
```

Plan 冻结的是 A/B 的 `ResolvedContextBlock` 来源 ID 和顺序，而不是跨 Provider wire messages。

proactive/manual 要求：

- 至少一个非空原文块进入 A；
- B 非空；
- `estimate(S+B) < estimatedBeforeCost`。

如果旧摘要很大、所有新原文都能保留，只有旧摘要进入 A：有意返回 no_prefix，不主动重写。

## 摘要输入分区和调用上限

计数冻结为：

```text
finalLeafCount <= 8
attemptedPartitionCount <= 15
logicalProviderCallCount <= 30
```

定义：

- attempted partition 是一次实际尝试摘要的连续 `SummaryInputBlock` 分区；满二叉树 8 个最终叶最多包含 15 个节点，失败后被拆分的内部节点也计数；
- 每个 attempted partition 最多创建 candidate 和 primary 两个 logical calls；primary 只在 candidate 返回 context-limit 时使用；
- 网络瞬时重试属于同一 logical call，不增加 partition 或 logical call 计数；
- proactive 每 logical call 最多 1 次网络请求，绝对网络请求上限 30；
- manual 每 logical call 最多 2 次网络请求，绝对网络请求上限为 60；
- 上述绝对上限还受模式 deadline 约束，不能保证所有调用都能启动。

确定性拆分顺序为深度优先、先左后右、按块数量中点拆分。创建第 16 个 partition、第 9 个最终叶或第 31 个 logical call 之前立即失败，不再拆分。

若 primary 对单块仍返回 context-limit，或达到任一上限，结果为 `summary_input_limit`。该结果只结束当前压缩摘要，不触发主模型恢复压缩。

叶摘要按原顺序使用 `\n\n---\n\n` 拼接，中间结果不落库。最终收益检查针对完整 S+B。

## 连续压缩示例

物理链：

```text
A → B → C → S1 → D → E → S2
```

S2 retainedFrom=C、previous=E。物理区间含 `C → S1 → D → E`，resolver 输出必须是：

```text
S2 → C → D → E
```

S1 不输出、不递归。
