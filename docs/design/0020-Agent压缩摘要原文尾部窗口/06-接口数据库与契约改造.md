# API、数据库与共享契约改造

## 共享 Message 契约

修改 `packages/shared/src/contracts/agent-message.ts`：

- 提取公共 record 字段；
- compaction 分支严格限定 completed、retainedFrom 必填可 null、单 TextPart；
- User/Assistant/System/Runtime 保持当前宽 status/parts 约束；
- 普通分支 `additionalProperties:false`，明确禁止 retainedFrom；
- 不顺带收紧其他消息生命周期。

## Compaction commit 契约

`commitCompaction` 的严格内部请求在既有 compaction 坐标、摘要和 `retainedFromMessageId` 外，固定携带 `completed/compaction_completed/null` terminal intent。它不是“提交摘要后再完成 Run”的两次写入。请求中 `retainedFromMessageId` 为：

```ts
retainedFromMessageId: Type.Union([IdSchema, Type.Null()])
```

服务端校验：

- Run fence；
- head/revision；
- summary 非空；
- retainedFrom 是 resolver 有效原文序列中的合法主 profile 非空边界；
- 是连续后缀起点；
- 同 Workspace、当前 Session 祖先链；
- fork/subtask 可来自其他 originSession；
- 非 runtime/compaction/非 completed；
- Assistant 工具执行完整。

API 不重复实现 EstimatorV1 或20k，只验证图和来源合法性。单一数据库事务必须插入 CompactionMessage 和 TextPart、更新 Session root/head、写 intended 三元组并置 `terminal_intent_persisted`。幂等 exact replay 必须同时比较 retainedFrom、坐标、摘要和 intent；任一不同均 conflict。

## Compaction source 内部端点

### 请求与保护

```ts
export const AgentApiCompactionSourceRequestSchema = Type.Object({
  workspaceId: IdSchema,
  sessionId: IdSchema,
  runId: IdSchema,
}, { additionalProperties: false });
```

路由位于现有 `/api/internal/agent/*` 控制面并执行 `assertInternalToken`。

### Ownership 与派生

API 验证：

- Run 存在；
- Run workspace/session 与请求相同；
- `session_run_state.active_run_id === runId`，或满足现有受保护 startup recovery 读取规则；
- Run status 为 running；
- Session 属于请求 Workspace。

从 Run 派生 triggerMessageId、agent/provider/model、runKind、subtaskDepth；从 run state 和消息状态派生 pending 范围。locale 本次固定返回 `null`，one-shot 摘要提示为 locale-neutral；不得从 Run、旧 Run 或请求字段推断 locale。

### 唯一快照实现

`getCompactionSource()` 必须在单个 `better-sqlite3` `db.transaction(() => ...)` deferred 只读事务中读取：

- Run ownership/status；
- Session head/root/revision；
- 当前 root 与 retained 区间；
- post-root 链；
- Parts；
- ToolExecutions；
- replay JSON；
- attachment 元数据；
- pending 状态和截止。

坐标与 blocks 必须来自同一事务。只实现事务读取路径；禁止事务外补读和 Worker 二次读取历史。

## agent_run terminal result

### Schema

`agent_run` 新增：

```sql
execution_phase text not null default 'work_pending',
intended_terminal_status text null,
intended_terminal_code text null,
intended_terminal_detail text null,
terminal_result_code text null,
terminal_result_detail text null
```

必须建立基本形态约束：

```sql
check (
  execution_phase in (
    'work_pending',
    'work_in_progress',
    'terminal_intent_persisted',
    'terminal'
  )
)
check (
  (status = 'running' and execution_phase in (
    'work_pending', 'work_in_progress', 'terminal_intent_persisted'
  ))
  or (status in ('completed', 'failed', 'cancelled') and execution_phase = 'terminal')
)
check (
  (execution_phase in ('work_pending', 'work_in_progress')
    and intended_terminal_status is null
    and intended_terminal_code is null
    and intended_terminal_detail is null
    and terminal_result_code is null
    and terminal_result_detail is null)
  or
  (execution_phase = 'terminal_intent_persisted'
    and status = 'running'
    and intended_terminal_status in ('completed', 'failed', 'cancelled')
    and intended_terminal_code is not null
    and terminal_result_code is null
    and terminal_result_detail is null)
  or
  (execution_phase = 'terminal'
    and status in ('completed', 'failed', 'cancelled')
    and intended_terminal_status is null
    and intended_terminal_code is null
    and intended_terminal_detail is null
    and terminal_result_code is not null)
)
check (intended_terminal_code is null or length(intended_terminal_code) between 1 and 80)
check (intended_terminal_detail is null or length(intended_terminal_detail) between 1 and 240)
check (terminal_result_code is null or length(terminal_result_code) between 1 and 80)
check (terminal_result_detail is null or length(terminal_result_detail) between 1 and 240)
```

Run 创建时必须显式或通过数据库默认得到 `running/work_pending`。Worker 成功获取并开始处理该 Run 后，通过受保护幂等写将 phase 改为 `work_in_progress`。公共 Run 状态接口在 phase 不是 terminal 时始终返回 `status: running` 和 null terminal result；尤其 `terminal_intent_persisted` 不得提前暴露 intended code。

数据库不复制完整码表为巨型 SQL check；代码中的全局 registry 是 intended/actual runKind/status/code 合法组合的唯一业务权威，API 必须在事务写入前严格验证。unknown code 或未登记组合一律拒绝。

`terminal_result_detail` 默认 null；非 null 时只允许 registry 登记的枚举化诊断键，禁止自由文本、安全文案、Provider 原始错误和异常消息。

- Worker 可提交的 user 子集：`run_completed`、`run_failed`、`context_limit_media_requires_resend`、`context_limit_recovery_exhausted`、`compaction_conflict`、`run_cancelled`；

- `detail` 允许集合与 code 一起定义，初始集合为空；需要新增诊断键时必须修改 registry 和契约测试。

### M15：最终内部动作、契约与持久层

目标方案删除 `AgentApiRunCompleteRequestSchema`、旧 completeRun 端点、API Client 方法、`completeRunFromWorker()` 及任何包装兼容层。所有内部请求均位于 `/api/internal/agent/*`、校验 `assertInternalToken`、使用严格 TypeBox `additionalProperties:false`，成功统一响应 `{ ok: true, updatedAt: number }`；含 Message 的动作额外返回 `assistantMessageId` 或 `compactionMessageId`。

所有六个请求都以如下公共字段为根，并由对应严格 schema 展开动作专有字段：

```ts
type AgentApiInternalRunActionBase = {
  workspaceId: string;
  sessionId: string;
  runId: string;
  updatedAt: number;
};

type AgentApiInternalActionResponse = {
  ok: true;
  updatedAt: number;
};

type AgentApiConvergeRunTerminalResponse = AgentApiInternalActionResponse & {
  kind: "transitioned" | "already_converged";
  finalStatus: "completed" | "failed" | "cancelled";
};

type AgentApiCompleteAssistantResponse = AgentApiInternalActionResponse & {
  assistantMessageId: string;
};

type AgentApiCommitCompactionResponse = AgentApiInternalActionResponse & {
  compactionMessageId: string;
};
```

| 动作 | method / path | 请求核心字段 | 应用层与持久层事务 |
|---|---|---|---|
| `markRunWorkInProgress` | `POST /api/internal/agent/runs/mark-work-in-progress` | workspaceId、sessionId、runId、updatedAt | `markRunWorkInProgress()`；仅`work_pending→work_in_progress`，重复幂等 |
| `persistTerminalIntent` | `POST /api/internal/agent/runs/persist-terminal-intent` | workspaceId、sessionId、runId、intendedTerminalStatus/code/detail、updatedAt | `persistTerminalIntent()`；只写无产物结果的 intent |
| `convergeRunTerminal` | `POST /api/internal/agent/runs/converge-terminal` | workspaceId、sessionId、runId、updatedAt | 返回`AgentApiConvergeRunTerminalResponse`；`convergeRunTerminal()`只读 intent，在同一事务收敛本Run origin Message/ToolExecution、Session revision、实际终态与session state |
| `completeAssistantWithExecutions` | `POST /api/internal/agent/messages/complete-assistant-with-executions` | workspaceId、sessionId、runId、assistant completion、responseTokens、executions、updatedAt | `completeAssistantWithExecutions()`；完成非终态 Assistant/ToolExecution，不写 intent |
| `completeTerminalAssistantWithExecutions` | `POST /api/internal/agent/messages/complete-terminal-assistant-with-executions` | 前行动作字段 + intendedTerminalStatus/code/detail | `completeTerminalAssistantWithExecutions()`；同一事务完成 Assistant、response tokens 和 intent |
| `commitCompaction` | `POST /api/internal/agent/sessions/commit-compaction` | workspaceId、sessionId、runId、CAS坐标、summary、retainedFromMessageId、intendedTerminalStatus/code/detail、updatedAt | `commitCompaction()`；同一事务提交 compaction、更新 Session root/head 和 intent |

所有请求都必须校验 workspace/session/run ownership、当前 phase、调用来源和 registry。`intendedTerminalDetail` 未提供时规范化为 `null`；Worker 不得提交 unknown code 或任意 detail。

Assistant 完成请求共享既有 Assistant Parts、ToolExecution、response token 与 fenced-write 字段。额外不变量固定为：

- 普通 `completeAssistantWithExecutions` 可以带 ToolCall 与其 ToolExecution，但不得携带 terminal intent；
- `completeTerminalAssistantWithExecutions` 的 Assistant 可含 text、reasoning、replay，但 ToolCall 和 ToolExecution 都必须为空；请求的 terminal intent 对 user 必须是`completed/run_completed`，对 subtask 必须是`completed/subtask_completed`；
- terminal Assistant 请求重放时，持久层同时比对 Assistant/Parts、response tokens、空的 executions 与 intent；完全相同成功，否则 conflict；
- compaction 请求重放时，同时比对 CAS 坐标、摘要、retainedFrom、CompactionMessage/TextPart 与 intent；完全相同成功，否则 conflict。

`AgentApiClient` 最终只暴露表中六个同名方法，不保留 `completeRun()`。`persistTerminalIntent()` 与 `convergeRunTerminal()` 的 policy 固定 `maxRetries:0`，调用方显式传入裁剪后的 timeout；`markRunWorkInProgress()`、`completeAssistantWithExecutions()`、`completeTerminalAssistantWithExecutions()` 与 `commitCompaction()` 使用各自现有 work-write policy，所有请求须携带稳定幂等输入。后两种原子动作收到网络错误或响应丢失时，Runner 必须在剩余 work deadline 内以完全相同请求重发，不得改用独立 intent 补写成功结果。

应用层固定暴露与动作同名的六个方法；持久层将普通 Assistant、terminal Assistant、compaction 分成三个独立事务方法，不能以一个“完成后再补 intent”的通用方法隐藏原子性差异。

`persistTerminalIntent()` 的持久化规则固定为：

- `work_pending/work_in_progress → terminal_intent_persisted`；
- 写 intended status/code/detail；
- 完全相同 intent 重放成功；
- 不同 intent、已 terminal 不同结果或非法 phase 返回 conflict。

`convergeRunTerminal()` 不接受 status/code/detail 或任何 Worker 结果。在同一数据库事务中，严格以 `workspaceId/sessionId/runId` 的 origin 范围处理并完成：

- 读取 intended status/code/detail；
- intended 为 completed 时断言本 Run 不存在 streaming/nonterminal Message，且不存在 queued/running ToolExecution；违反即 data invariant failure，回滚且不得将 session_run_state 写 idle；
- intended 为 failed 时将本 Run streaming Assistant 置 failed；intended 为 cancelled 时置 cancelled；
- failed/cancelled 均将本 Run queued ToolExecution 置 cancelled、running ToolExecution 置 unknown。前者明确未执行，后者保持副作用可能已发生的诊断语义；
- queued/running ToolExecution发生上述转态时，在同一行将`completed_at=updatedAt`，同时写status、`updated_revision`与`updated_at`；保留`started_at`，不得构造或修改result/error；
- 对所有状态改变的 Message 更新 `updated_revision` 与 `updated_at`，递增 Session revision；
- 写 Run actual status/result、`execution_phase='terminal'`、清空 intended，并将该 Session 的 `session_run_state` 写 idle。

上述 artifact、revision/timestamp、Run、Session 与 run state 是不可拆事务。首次提交返回`kind='transitioned'`及finalStatus；已terminal的完整一致检查（含artifact `completed_at`）返回`kind='already_converged'`及同一finalStatus。不得在 API cancel、enqueue failure、startup failure 或 Worker failure/cancel 的其他路径另行收敛 artifact；既有 `failMessageRunAndConverge` 与 `cancelRunAndConvergeInTransaction` 的 artifact 语义迁移到此 persistence helper 后删除，最多只作为实现迁移素材，不保留并行权威。

已 terminal 的重放仅在 actual status/result、origin artifact 状态、Session revision/run state 都已符合规则时幂等成功；不同实际结果，或残留 streaming/nonterminal Message、queued/running ToolExecution 等矛盾一律 conflict/data invariant failure。缺 intent 明确失败。

应用层所有调用来源必须使用同一个`afterConvergeRunTerminal(input, result)`，包括Worker RPC、API cancel、enqueue failure、startup recovery和Workspace删除本地逐Run收敛。该函数对两种成功结果均`runPromptStaticCache.clear(runId)`；仅`transitioned`发布既有`agent.run.completed.v1`与finalStatus。发布发生在持久化事务后；异常只记录结构化错误，不回滚，不补发。现有Hub是进程内best-effort广播，本方案不引入outbox。

Workspace删除不增加Worker RPC。删除应用层实现`convergeWorkspaceRunsForDeletion`，替换并删除`cancelWorkspaceRunsAndConverge`的直接SQL artifact写入：deletion intent和fence建立后，在按`sessionId`稳定排序的handoff locks中查询目标Workspace当前active user/manual/subtask Runs；按`runId`稳定排序逐个本地调用persist intent与上述完整convergence，并调用统一后置函数。每Run独立数据库事务。所有Run DB成功后才按稳定Session顺序调用`runtime.cancelSessionAndWait`；所有drain成功后才调用destructive cleanup。已有其他intent先收敛原intent，禁止覆盖；任一失败保留deletion intent，停止后续drain/cleanup。

API cancel、enqueue 永久失败、startup recovery failure 使用 API 内部同一 `persistTerminalIntent()` + `convergeRunTerminal()` helper；不得绕过 intended 阶段直接写终态。Worker 必须先调用 `markRunWorkInProgress`，不得仅凭进程内状态推断 phase。

### Terminal-control 重试与 startup recovery

Runner/专用 terminal loop 共享一个绝对10秒 budget：

- intent RPC 最多三次真实 HTTP 请求；
- intent 成功后 convergence RPC 使用剩余预算，最多三次真实 HTTP 请求；
- 两阶段合计最多六次，但不是六次保证额度，总时间仍不超过10秒；
- 固定 250ms 短退避；
- RPC 和退避均受剩余 10 秒限制；
- 每次 timeout 为配置 timeout 与剩余预算的较小值；
- `persistTerminalIntent` 与 `convergeRunTerminal` 两个 API Client policy 都设为 `maxRetries:0`；
- 重试唯一位于 Runner/专用 terminal loop，确保真实 HTTP attempt 可精确计数。
- 原子 terminal Assistant 或 compaction 成功后，不调用 persist intent；以首次 convergence 前新建的10秒deadline执行最多3次 convergence。

startup recovery 只按持久 phase 决策：

| phase | 唯一动作 |
|---|---|---|
| `terminal_intent_persisted` | 绝不prepare/enqueue，不检查Assistant/Tool/Compaction产物，只调用同一完整convergence |
| `work_pending` | 按现有安全恢复规则prepare/enqueue；无法恢复时先写`run_startup_recovery_failed` intent再converge |
| `work_in_progress` | 按现有安全恢复规则继续同一Run；工具已完成但等待下一模型步骤时必须继续；无法恢复时先写startup failure intent再converge |
| `terminal` | 不恢复、不改写 |

最终 Assistant 是否 completed、ToolExecution 是否 completed、是否存在 CompactionMessage，都不能作为 terminal intent 的替代证据。成功的 terminal Assistant 和 successful compaction 在其原子事务内已经写入 intent，因此不存在产物已提交而 phase 仍为work_in_progress的合法状态。若独立 intent 完全写不进去而进程崩溃，Run 仍为 work_in_progress，startup 只能按恢复规则继续或失败，不能猜测并补写原结果；若 convergence 持续失败，保留 intent 并在后续startup调用同一完整事务继续收敛，不改写错误码。

## 公共 Run 状态接口

### 路径

结合现有公开路由均以 Session 为边界，新增：

```http
GET /api/agent/sessions/:sessionId/runs/:runId?workspaceId=:workspaceId
```

这样与现有：

```http
GET  /api/agent/sessions/:sessionId/timeline
POST /api/agent/sessions/:sessionId/compact
POST /api/agent/sessions/:sessionId/cancel
```

保持一致，并天然要求 sessionId。

### 契约

```ts
export const AgentRunStatusResponseSchema = Type.Object({
  workspaceId: IdSchema,
  sessionId: IdSchema,
  runId: IdSchema,
  runKind: AgentRunKindSchema,
  status: Type.Union([
    Type.Literal("running"),
    Type.Literal("completed"),
    Type.Literal("failed"),
    Type.Literal("cancelled"),
  ]),
  terminalResultCode: Type.Union([Type.String({ minLength: 1, maxLength: 80 }), Type.Null()]),

```

响应不暴露 `executionPhase` 或 intended 三元组。phase 非 terminal 时规范化为 running/null/null；只有 phase terminal 时返回实际 terminal result。

API 校验：

- Session 属于 workspaceId；
- Run 属于同 workspaceId/sessionId；
- 不允许仅凭 runId 跨 Session 查询；
- 非终态 result 必须 null；
- 返回 detail 前确保其符合安全约束。

该接口是公共只读接口，不返回 Provider 错误、replay、消息正文或 profile 凭证。

## `/compact`、普通发送与前端消费

当前 `AgentCompactSessionResponseSchema` 与 `AgentSendMessageResponseSchema` 都包含顶层 `runId`。空 Session/head null 在 manual 调度前同步 HTTP 400，不创建 Run。

`clientRequestId` 幂等重放必须返回第一次创建的同一 runId；如果该 Run 已终态，前端可立即查询相同结果。

manual 和普通 user 必须复用同一个 pending-run registry，不允许两套轮询、展示或持久化逻辑。改造位置：

- `apps/web/src/features/workspace/tools/agent/AgentClientPane.vue`：捕获 `compactAgentSession()`、`sendAgentMessage()`、`sendAgentMessageMultipart()` 返回的 `runId`；当前普通发送代码不得继续忽略返回值；
- `apps/web/src/shared/api/api.ts`：增加公共 Run 状态查询；
- `apps/web/src/features/workspace/tools/agent/useAgentSessionStatusStore.ts`：扩展或在同目录抽取共用 `pendingRun` registry，复用现有轮询调度；不得把 per-Run terminal code 混入现有 Session indicator 的 `runNoticeText`；
- `apps/web/src/shared/i18n/locales/*`：为 registry code 建立完整映射。

每条当前 tab 记录与 key 都必须使用以下版本化定义，不保留未版本化的内存记录结构：

```text
key prefix = agent-workbench.agent.pending-run.v1/
key = <prefix><workspaceId>/<sessionId>/<runKind>/<runId>
```

```ts
type PendingRunStorageRecordV1 = {
  schemaVersion: 1;
  workspaceId: string;
  sessionId: string;
  runId: string;
  runKind: "user" | "manual_compaction";
  createdAt: number;
};
```

统一入口固定为 `restorePendingRuns({workspaceId, sessionId})`：

- 扫描当前 prefix；JSON损坏、schemaVersion错误、字段缺失、key与record不一致时直接删除，不展示提示；
- 只调度当前 workspace/session 的合法记录，其他 workspace/session 的合法记录保留且不轮询；
- 当前 workspace 或 session 已确认删除时，清理其全部相关 key；
- 同一 workspace/session 多条记录按 `createdAt`、再按 runId 排 FIFO；最多并发查询3条，完成一批后取下一批；
- 网络错误、timeout、429、5xx 保留记录，复用现有轮询退避节奏重试；
- 404、ownership mismatch、响应 runKind 与记录不一致属于永久 stale：当前 tab 显示一次固定通用提示，然后删除；
- terminal 后消费并删除；user `completed/run_completed` 静默删除，其他终态按既定i18n显示一次；
- running 或 `terminal_intent_persisted` 对外规范化的 running 继续轮询；
- 不使用 localStorage、BroadcastChannel 或服务端 consumed 标记。

行为固定为：

- `/compact` 成功后登记 `manual_compaction`；普通文本或 multipart send 成功后登记 `user`；
- 页面刷新后恢复 pending runId；
- 使用新 Run 状态接口和现有轮询节奏查询；
- running 继续等待；每个终态在当前 tab 消费一次后删除记录；
- user `completed/run_completed` 静默清理，不额外弹提示；
- manual completed code 显示对应产品提示；
- failed/cancelled 必须按 terminal code i18n 展示；`context_limit_media_requires_resend` 提示重发更小/更少附件，`context_limit_recovery_exhausted` 提示缩短输入或手动整理上下文，`compaction_conflict` 提示上下文已变化并可重试；
- unknown code 不应由 API 返回；若客户端版本落后，显示固定通用本地化错误，不直接展示 detail；
- terminal result 仅通过 Run 状态查询读取，timeline snapshot/delta 和实时事件契约保持现状。

## pending tools

manual 遇到 pending tools 不提交摘要，Run failed 并写稳定：

```text
compaction_pending_tools
```

前端 i18n 提示先等待或取消当前工具执行。proactive 继续走既有 pending tool 流程，不创建面向用户的 compaction terminal code。

## Workspace cleanup

修改 `apps/api/src/infra/db/workspace-agent-data-cleanup.ts` 的 `deleteWorkspaceAgentData()`：

- 不再清空 Message 的三类图字段；
- 严格按以下目标schema顺序删除：FTS行→FTS map→client request→session_run_state→session model override→ToolExecution→MessagePart→Run→Session→Message逆拓扑→Attachment；
- ToolExecution 必须先于 MessagePart，因为 `call_part_id` 是 `ON DELETE RESTRICT`；
- Run 必须先于 Message，解除 `trigger_message_id RESTRICT`；Session 必须先于 Message，解除head/root RESTRICT；
- Run/Session删除同时依赖现有SET NULL解除Message/Execution origin和parent execution引用；
- 对 `previous_message_id`、`replaces_message_id`、`retained_from_message_id` 三类“引用者 → 被引用者”边执行逆拓扑删除；
- 每轮只删除没有任何剩余 Workspace Message 引用的节点；`depth DESC, id ASC` 仅为候选排序；
- 若仍有节点但某轮无候选，抛出 data invariant/cycle failure 并回滚；
- 保持 `PRAGMA foreign_keys=ON`；
- replacement 同 depth、retained 边、ToolExecution FK和连续压缩图必须可完整删除；
- 旧ContextItem schema只在schema整体重建时按context_item_attachment→context_item销毁，不在目标cleanup保留双schema分支。

查询思路：

```sql
select m.id
from agent_message m
where m.workspace_id = :workspaceId
  and not exists (
    select 1 from agent_message ref
    where ref.workspace_id = :workspaceId
      and (
        ref.previous_message_id = m.id
        or ref.replaces_message_id = m.id
        or ref.retained_from_message_id = m.id
      )
  )
order by m.depth desc, m.id asc
limit :batchSize;
```
