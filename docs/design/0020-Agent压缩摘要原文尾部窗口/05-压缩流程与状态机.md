# 压缩流程、模式与恢复状态机

## Work deadline

每种模式必须在调用 compaction source **之前**创建绝对 deadline。deadline 覆盖：

```text
source RPC
→ API deferred只读事务
→ Worker物化
→ A/B规划
→ SummaryInputBlock生成
→ 摘要Provider调用与网络重试
→ 退避等待
→ CAS重规划及重新source
→ 收益检查
→ commit RPC尝试
```

这是业务工作预算，不包含 terminal intent 与终态收敛。所有 work API RPC、Provider 请求和退避都必须接收 AbortSignal，并以剩余 deadline 设置超时。进入某一步前剩余时间不足时，不得发起新的 RPC、logical call 或退避。

| 模式 | Deadline |
|---|---:|
| proactive | 整个压缩尝试总计 15 秒 |
| manual | 整个 Run 压缩尝试总计 120 秒 |
| recovery standard | standard 级总计 45 秒 |
| recovery full | 从 standard 明确转入 full 时新建 45 秒 |

同一级内 CAS 重规划不重置 deadline。standard 转 full 时才创建 full 的新 45 秒 deadline。Run 的用户取消信号始终可提前终止所有级别。

## Terminal-control budget

无持久业务产物而需独立写 intent 的 manual、user、subtask 结果，进入共享的独立 10 秒 terminal-control 预算：

```text
TERMINAL_CONTROL_BUDGET = 10s
MAX_TERMINAL_INTENT_HTTP_ATTEMPTS = 3
MAX_TERMINAL_CONVERGENCE_HTTP_ATTEMPTS = 3
TERMINAL_CONTROL_RETRY_DELAY = 250ms
```

- 该预算不计入 work deadline，也不能反向延长 work deadline；
- 只适用于无持久业务产物的独立 `persistTerminalIntent`，成功后调用 terminal convergence；不得继续 source、模型、工具、摘要、重规划或 commit；
- intent 阶段最多三次真实 HTTP 请求；intent 成功后 convergence 阶段使用剩余时间，最多三次真实 HTTP 请求；
- 两阶段合计最多六次真实 HTTP 请求，但都受同一个10秒绝对 deadline，前一阶段耗时会减少后一阶段可用时间；
- 每次额外请求前固定退避250ms；当剩余时间不足以完成退避或一次请求时停止；
- `AgentApiClient` 的两个内部 RPC policy 都固定 `maxRetries:0`，不得叠加 Client 内部重试；
- 每次请求 timeout 裁剪为 `min(内部RPC配置timeout, terminal-control剩余时间)`；
- Runner/专用 terminal loop 是唯一重试层；同阶段每次发送完全相同的 status/code/detail，依赖幂等语义；
- proactive 只是某个 user Run 内部的 skipped 优化时，不产生独立 terminal result；最终由所属 user Run 的真实结局收敛；
- 独立 manual Run、普通 user Run、subtask Run 都必须收敛为终态。

有成功持久业务产物时，不先走独立 intent 阶段：

- 无 ToolCall 的终态 Assistant 由 `completeTerminalAssistantWithExecutions` 在同一 work transaction 完成 Assistant、response tokens 和 intent；
- manual compaction 成功由 `commitCompaction` 在同一 work transaction 完成 CompactionMessage、TextPart、Session root/head 和 intent；
- 这两种原子请求响应丢失时在 work deadline 内以完全相同参数重试；原子成功后以首次 convergence 前创建的独立10秒deadline调用 convergence，最多3个真实HTTP请求。由于没有独立 intent 请求，该deadline的完整时间都可用于 convergence。

阶段流程固定为：

```text
有产物成功 → 原子完成产物+intent
无产物结果 → persistTerminalIntent(status/code/detail)
→ execution_phase=terminal_intent_persisted（status仍running）
→ convergeRunTerminal()单事务收敛origin artifact、Session revision、Run与run state
→ 返回transitioned或already_converged + finalStatus
→ afterConvergeRunTerminal：总是清prompt static cache；仅transitioned发布既有SSE完成事件
```

最终 Assistant、已完成 ToolExecution 或 CompactionMessage 不能替代 intent。若 Worker 在原子产物+intent或独立 intent 成功后崩溃，startup 只调用同一完整 convergence；若独立 intent 完全写不进去，Run 仍是 `work_in_progress`，startup 按现有安全恢复规则继续同一 Run或持久化 `run_startup_recovery_failed` intent后收敛，不能猜测原业务结果。

`afterConvergeRunTerminal` 是Worker RPC、API cancel、enqueue failure、startup recovery和Workspace删除逐Run收敛的唯一后置路径。数据库事务成功或一致重放后均清除该runId cache；只有`transitioned`才发布现有`agent.run.completed.v1`。发布失败不回滚已提交数据库、记录错误；不借幂等重放补发，避免重复。本次不增加outbox，保持进程内best-effort事件语义。

## 总体流水线

```text
START_DEADLINE
→ compaction source同一快照
→ PrimaryMaterializedBlock（attachment_ref/replay，附件展开前）
→ estimatePrimaryMaterializedBlock(block)
→ 冻结CompactionPlan(profileFingerprint/A/B来源)
→ 从A生成SummaryInputBlock
→ 按分区/调用上限调用摘要Provider
→ 估算完整S+B
→ 成功时原子commitCompaction+intent，其他结果独立persistTerminalIntent
→ 或主模型终态时原子completeTerminalAssistantWithExecutions+intent
→ terminal convergence
```

摘要函数不得重新调用 messages-context 或 source 改变 A/B。candidate 与 primary 只转换同一批 `SummaryInputBlock`，不得读取不同历史或使用私有 replay 改变摘要语义。

## Plan 生命周期与 CAS 重规划

以下情况使 Plan 和摘要正文全部作废：

- CAS conflict；
- Run fence 丢失；
- 用户取消；
- 数据不变量错误。

| 模式 | CAS 重新规划次数 | 用尽后的结果 |
|---|---:|---|
| proactive | 0 | 跳过，继续主模型 |
| manual | 1 | failed / `compaction_conflict` |
| recovery standard+full 整个事件 | 总计 1 | failed / `compaction_conflict` |

初始顺序固定为：

```text
getExecutionProfile → fingerprint → getCompactionSource → materialize → plan
```

CAS conflict 后先重新 `getExecutionProfile` 并计算 fingerprint：

- fingerprint 不同：proactive 跳过；manual/recovery 都以 `compaction_conflict` 终止；
- fingerprint 相同：才可重新 source、物化、估算和生成摘要；
- 任一分支都不得复用旧 Plan 或旧摘要，且不能重置当前级 work deadline。

## 摘要分区和 Provider 调用预算

计数作用域冻结为：

| 模式 | 计数作用域 |
|---|---|
| proactive | 整个 proactive attempt |
| manual | 整个 manual Run |
| recovery | 每个 recovery level；standard 与 full 分开 |

每个作用域同时维护：

```text
finalLeafCount <= 8
attemptedPartitionCount <= 15
logicalProviderCallCount <= 30
```

- attempted partition 包含失败后继续拆分的内部节点；
- 每个 partition 最多 candidate + primary 两个 logical calls；
- primary 仅在 candidate 返回 context-limit 时调用；
- 创建第16个 partition、第9个最终叶或第31个 logical call前立即 `summary_input_limit`；
- 网络瞬时重试复用同一 logical call，不增加 logical 计数，但增加该作用域的 networkRequestCount；
- CAS replan 不清零 partition、logical 或 network 计数；
- recovery 只有 standard 明确转入 full 时才创建新的 level 计数；
- 接近上限后发生 CAS conflict，重规划只能消费剩余额度，不能获得新额度。

网络请求上限：

| 模式 | 每 logical call | 绝对网络请求上限 |
|---|---:|---:|
| proactive | 1次，不重试 | 30 |
| manual | 首次+1次瞬时重试 | 60 |
| recovery standard | 首次+1次瞬时重试 | 60 |
| recovery full | 首次+1次瞬时重试 | 60 |

绝对上限不是保证额度；deadline 可以更早终止。

## Provider 错误与退避

### Proactive

- network、timeout、429、5xx 零额外重试；
- 任一 transient 失败或 15 秒 deadline 到达后跳过本次压缩，继续普通主模型步骤；
- candidate context-limit→primary 是能力回退，不是网络重试；
- auth、permission、invalid request、控制面永久错误、数据不变量错误向外失败，不得吞掉。

### Manual

- 每 logical call 对 network、timeout、429、5xx 最多额外重试 1 次；
- 固定退避 1 秒；服务端较短 Retry-After 可使用，较长值受剩余 deadline 截断；
- 120 秒 deadline 到达或重试耗尽写 `compaction_provider_unavailable`；
- auth/permission/invalid request 永不重试；
- 用户取消写全局 registry 统一码 `run_cancelled`。

### Recovery

- standard 和 full 每 logical call 最多额外重试 1 次，固定退避 1 秒；
- 当前级 45 秒 deadline 到达或 transient 重试耗尽，整个 recovery 失败，不进入下一等级；
- Run terminal code 使用 `context_limit_recovery_exhausted`；
- auth/permission/invalid/control permanent/data invariant 立即失败；
- cancelled 立即终止。

本设计只定义压缩摘要调用的重试。普通主模型步骤中非 context-limit 错误的既有重试策略不在本次修改范围。

## Proactive 主动压缩

提交条件：

- pending tools 为空；
- 至少一个主 profile 非空原文块进入 A；
- B 非空；
- 当前 trigger 媒体完整保留在 B；
- 摘要非空；
- `estimatedAfter < estimatedBefore`；
- CAS/fence 成功。

结果：

| 结果 | 行为 |
|---|---|
| committed | 重读上下文，继续循环 |
| no_prefix/no_progress | 跳过，继续主模型 |
| blocked_oversized_tail | 跳过，继续主模型 |
| blocked_media_requires_resend | 跳过，不压缩媒体 |
| blocked_pending_tools | 先执行既有 pending tool 流程 |
| provider unavailable/deadline | 跳过，继续主模型 |
| summary_input_limit | 记录诊断，继续主模型 |
| cancelled | Run cancelled |
| 永久控制面/安全/数据错误 | Run failed |

同一 `(headMessageId, revision, profileFingerprint)` 只尝试一次 proactive。

## Manual 手动压缩

### 调度前同步失败

空 Session/head null 继续由 `/compact` 同步返回 HTTP 400，不创建 Run，也没有 terminal result code。

其他可调度情况由 `/compact` 返回 `runId`，最终结果写入该 `agent_run`。

### 终态结果码

| CompactionResult | Run status | terminalResultCode |
|---|---|---|
| committed | completed | `compaction_completed` |
| no_prefix | completed | `compaction_not_needed` |
| no_progress | completed | `compaction_no_progress` |
| blocked_oversized_tail | completed | `compaction_oversized_tail` |
| blocked_media_requires_resend | completed | `compaction_media_requires_resend` |
| blocked_pending_tools | failed | `compaction_pending_tools` |
| summary_input_limit或永久业务失败 | failed | `compaction_failed` |
| provider unavailable/deadline | failed | `compaction_provider_unavailable` |
| conflict exhausted | failed | `compaction_conflict` |
| fingerprint changed | failed | `compaction_conflict` |
| cancelled | cancelled | `run_cancelled` |

manual 不隐式 full。`terminalResultDetail` 默认 null；如使用，只能保存全局 registry 允许的枚举化诊断键。

## Context-limit recovery

### 错误分类

| 分类 | 示例 | 转移 |
|---|---|---|
| `business_no_progress` | no_prefix、no_progress、blocked_oversized_tail、标准方案无可提交结果但摘要能力正常 | standard 不提交，进入 full；有 trigger 媒体时直接失败 |
| `model_step_context_limit` | standard 已提交，完整主模型步骤仍明确 context-limit | 进入 full；有 trigger 媒体时直接失败 |
| `summary_input_limit` | 单块 primary 仍超限、超过8叶/15 partition/30 logical calls | 立即 recovery failed，不进 full |
| `media_requires_resend` | trigger 媒体块或强制后缀超过20k；full将移除trigger媒体 | 立即失败，不进 full |
| `transient_provider` | network、timeout、429、5xx | 当前级首次+1次；耗尽失败，不进 full |
| `auth_permission` | 401/403、无权模型 | 立即失败 |
| `invalid_request` | 非 context-limit 400、schema/provider参数错误 | 立即失败 |
| `control_permanent` | ownership/fence/内部RPC永久错误 | 立即失败 |
| `data_invariant` | 链损坏、缺execution、跨Workspace、非法canonical输入 | 立即失败 |
| `cancelled` | AbortSignal/User cancel | cancelled |
| `commit_conflict` | CAS conflict | 整个事件最多重规划1次；耗尽 `compaction_conflict` |

只有 standard 的业务无进展，以及 standard 提交后完整主模型步骤仍 context-limit，能够进入 full。`summary_input_limit` 不进入 full，因为 full 输入只会更大。

### 状态机

```text
MODEL_STEP
  └─ context_limit
       → START_STANDARD_45S
       → STANDARD_PLAN
          ├─ media/summary_input_limit/permanent/cancel/transient耗尽 → FAILED
          ├─ business_no_progress → START_FULL_45S
          └─ committed → RELOAD → RETRY_MODEL_STEP_STANDARD
               ├─ success → RECOVERY_DONE
               ├─ context_limit → START_FULL_45S
               └─ other error → 按原错误失败

START_FULL_45S
  ├─ current trigger contains media → FAILED(context_limit_media_requires_resend)
  └─ FULL_PLAN
       ├─ summary_input_limit/no_progress/transient耗尽/permanent/cancel → FAILED
       └─ committed → RELOAD → RETRY_MODEL_STEP_FULL
            ├─ success → RECOVERY_DONE
            └─ context_limit/other error → FAILED(context_limit_recovery_exhausted)
```

一次级别内 CAS 重规划不重置该级 45 秒。standard 转 full 时才启动新的 full 45 秒。

普通 user Run 的成功、失败、取消必须严格使用全局 terminal code registry。context-limit 媒体失败、恢复耗尽和 fingerprint/CAS conflict 分别映射为 `context_limit_media_requires_resend`、`context_limit_recovery_exhausted`、`compaction_conflict`；不得使用未注册码。

## 当前 trigger 媒体策略

- 当前 trigger 带图片/附件的 User 块必须完整留在 B；
- 该块或从它到末尾的强制后缀超过20k：proactive跳过、manual写 `compaction_media_requires_resend`、recovery写 `context_limit_media_requires_resend`；
- full 不得移除当前 trigger 媒体后继续推理；
- 不注入“媒体已移除”后让模型继续回答的 synthetic prompt；
- UI 提示用户重新发送更小或更少附件。

## 完整模型步骤与恢复事件

只有 `runModelStep()` 整体正常返回且流中没有 context-limit，恢复事件才结束。建立流、首 chunk、部分文本、创建或 discard streaming Assistant 都不结束事件。

## 收益检查

```text
estimatedAfter = EstimatorV1(summary system message) + retained primary cost
estimatedAfter < estimatedBefore
```

检查完整 S+B，不能只检查叶摘要或 A。

## 取消与统一终态收敛

任何业务阶段取消都中止 work RPC、Provider、退避和未开始提交，不进入 full。取消也是业务结果，必须先在 terminal-control budget 内持久化 `cancelled/run_cancelled` intent，再 convergence。

`persistTerminalIntent` 幂等规则：

- phase 为 work_pending/work_in_progress 时写入 intent；
- phase 已为 terminal_intent_persisted 且三元组完全相同则成功；
- 不同 intent 或已 terminal 且结果不同则 conflict。

`convergeRunTerminal` 幂等规则：

- 只接受 terminal_intent_persisted；只读 intended，收敛本 Run origin Message/ToolExecution，复制 intended 到实际终态并清空 intended；
- completed intent 必须没有 streaming/nonterminal Message 与 queued/running ToolExecution，否则 data invariant failure，不得 idle；
- failed/cancelled 将 streaming Assistant 分别设为failed/cancelled，queued ToolExecution设为cancelled，running ToolExecution设为unknown；
- queued/running ToolExecution实际转态时，保留startedAt，在同一事务将completedAt设为convergence.updatedAt，并同写status、updatedAt、updatedRevision；不得伪造或改变result/error；
- 所有转换的 artifact updatedRevision/updatedAt/completedAt、Session revision、Run status/result/phase、intended清空与session_run_state idle必须同一事务；
- 已 terminal 只有实际结果和artifact/session收敛状态（含completedAt）都一致才返回already_converged；首次完整收敛返回transitioned；
- 缺 intent、不同结果或残留矛盾不得覆盖，必须返回 conflict/data invariant failure。

startup recovery 按持久 phase 唯一决策：`terminal_intent_persisted` 绝不重跑业务，只调用同一完整 convergence；`work_pending/work_in_progress` 继续现有安全恢复或写 `run_startup_recovery_failed` intent后调用该 convergence。工具已完成、正等待下一模型步骤的 `work_in_progress` 必须继续同一 Run；不得从最终 Assistant、ToolExecution、CompactionMessage 或其他 artifact 推导 terminal intent。

## Workspace删除状态机

Workspace删除的Run阶段固定为：

```text
持久deletion intent
→ Workspace deleting fence
→ sessionId稳定序的handoff locks
→ 查询本Workspace当前active user/manual/subtask Runs
→ runId稳定序逐Run：persist cancelled/run_cancelled intent → 完整convergence → afterConvergeRunTerminal
→ 全部Run数据库收敛
→ sessionId稳定序runtime.cancelSessionAndWait/drain
→ 全部drain成功
→ destructive cleanup
```

每个Run是独立短事务，禁止将所有Run或runtime drain包入一个巨大数据库事务。已有相同取消intent直接converge；已有其他terminal intent先收敛原intent，terminal后幂等跳过；已terminal一致Run跳过。任一persist/converge conflict或data invariant failure立即停止，保留deletion intent/fence，不得开始drain或cleanup。DB都成功但任一drain失败也停止并保留intent；下次从已terminal Run继续drain，不改写任何terminal结果。所有查询和更新均限制于目标Workspace。
