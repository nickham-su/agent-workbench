# 现状、问题与目标

本文件保留立项时的改造前基线；带“改造前”的行为、测试和风险仅作历史追溯。现行摘要调用和验收以第 05、08 节为准。

## 立项背景（历史）

立项时项目刚完成一次尚未发布的不兼容 Message 模型升级；当时没有需要保留的新模型历史数据，因此方案允许直接调整表结构、共享契约和运行时语义，不需要：

- 旧字段兼容；
- 双写或双读；
- 历史消息回填；
- 运行时按 schema 版本分支。

当时规划通过 schema 收敛机制重建本地开发数据库，不编写旧数据语义迁移。

## 改造前的 Worker 压缩行为（历史记录，非现行实现）

改造前的 `AgentRunner.generateCompactionSummary()` 会再次调用 `getMessagesContext()`，取动态上下文并追加摘要指令；遇摘要模型 context-limit 时按 `ModelMessage[]` 数量中点递归二分，最多八块。现行实现没有此路径。

改造前的 `AgentRunner.compactContext()`：

- 生成摘要；
- 对 Provider 错误按既有策略重试；
- 以 context 的 head/revision 提交摘要；
- 返回布尔值。

历史代码位置（以下函数已移除）：

- `apps/agent-worker/src/runtime/runner.ts`
  - `generateCompactionSummary()`
  - `compactContext()`
  - `processRun()` 中 manual、auto 调用

### 现行模型错误行为

主模型 Provider 错误（包括被启发式识别为 context-limit 的错误）统一进入普通指数退避重试，并受 Web 设置的 `modelRequestMaxRetries` 限制；不再启动上下文恢复压缩。

当前实现已删除摘要调用的 context-limit 分类、候选模型回退与递归分片；手动/自动摘要请求的抛错均按 `modelRequestMaxRetries` 退避，重试耗尽时自动压缩所在 Run 失败。

改造前手动 `/compact` 与普通发送响应都返回 Run ID，但当时的公开读侧没有按 runId 读取终态 code 的接口；`AgentClientPane.vue` 的普通发送路径当时还忽略 `sendAgentMessage/sendAgentMessageMultipart` 返回值。`session_run_state.run_notice_text` 是运行中瞬态 notice，不能承担终态产品结果。因此本次把 terminal result 持久化到 `agent_run`，新增按 Session/Run 查询的公共只读接口，并让 manual/user 共用当前标签页 pending-run 机制。

改造前 Worker 会先完成 Assistant/Compaction 业务产物，再由外层决定是否写 Run 终态；两次写之间发生崩溃会留下“产物已提交、phase 仍 work_in_progress”的不可判定窗口。不能靠最终 Assistant、ToolExecution 或 CompactionMessage 反推结果，否则会重复执行或写入错误结果。因此成功的最终 Assistant 与 manual compaction 必须将产物和 intended terminal 三元组置于同一事务；`execution_phase` 与 intended 三元组仍是 recovery 的唯一终态权威。

改造前的 completeRun 控制面将业务结果与终态写入混在一个迟到的动作中，并存在 Client 内部重试。目标方案删除该端点、契约、Client 方法和包装，只保留独立 intent/convergence 与原子终态 Assistant/Compaction 动作。独立 intent/convergence 的 API Client policy 固定为 `maxRetries:0`，唯一重试层收敛到 Runner/专用 terminal loop。

改造前失败、取消和启动恢复路径分别处理 streaming Assistant、ToolExecution、Run 或 session state，会形成多套 artifact 收敛权威，并可能在 Run 已终态时遗留 streaming Message、queued ToolExecution，或者让其他 Run 的产物被误改。本方案把这些状态转移统一迁入按 `workspaceId/sessionId/runId` origin 限定的 `convergeRunTerminal()` 单一事务：completed 必须验证没有非终态 artifact；failed/cancelled 才按固定矩阵收敛 artifact、revision、Run 与 session state。

改造前Workspace删除路径另有批量取消实现，直接在store事务中改Message、ToolExecution、Run和run state；它既未复用terminal intent/convergence权威，也只按`session_run_state.active_run_id`选择，可能遗漏同Workspace的manual/subtask Run，并与普通终态路径的cache失效和SSE通知分叉。目标方案删除该实现，改为删除应用层编排器`convergeWorkspaceRunsForDeletion`，逐Run复用相同的持久化和应用层后置处理。

改造前终态后的prompt static cache清理、`agent.run.completed.v1`发布和失败路径并未共享单一后置处理；SSE Hub本身是内存best-effort broadcaster。新方案必须让所有convergence来源共用后置处理：数据库成功即清cache，实际首次转terminal才发布既有事件；发布失败只记录错误，不回滚、不通过重放补发。本次不引入outbox。与此同时，旧批量取消虽然写入`completed_at`，尚未将其作为完整convergence的固定DTO/幂等语义说明；必须冻结为本次convergence时间戳。

## 立项时的问题与现行约束

### 改造前摘要信息损失没有原文缓冲

摘要不可避免会丢失：

- 最近用户要求的原句；
- 代码、命令和错误文本细节；
- 最近 ToolCall 参数及结果；
- Provider replay 所需的私有上下文。

改造前摘要一提交，最近原文与更早原文一起退出上下文，模型只能依赖摘要重建工作状态；现行实现按 20k 窗口保留有效近期原文尾部。

### 改造前物理消息链与模型有效上下文被等同

改造前直接将 `contextRoot..head` 作为模型上下文；现行尾部窗口要求：

```text
物理消息链 ≠ 模型有效上下文顺序
```

模型需要先看到摘要，再看到物理上位于摘要之前的原文尾部；连续压缩时，尾部物理区间还可能穿过旧摘要。

### 改造前摘要生成的 TOCTOU 风险（现已由冻结计划规避）

改造前摘要生成自行重读 messages-context；若先规划 A/B、再重读历史，则可能导致：

- 规划坐标与摘要内容不一致；
- Provider 回退改变摘要输入范围；
- CAS 冲突后错误复用旧摘要。

现行流程冻结来源和计划，CAS 冲突后重新取源规划，不复用旧摘要。

### 改造前二分可能破坏工具语义（现已移除）

改造前按 `ModelMessage[]` 中点拆分可能将 Assistant ToolCall 与紧随其后的 ToolResult 分到不同摘要叶子；现行摘要整体发送旧前缀，不再二分。

### 两种压缩模式语义不同但接口相同

改造前 `compactContext(): boolean` 无法表达：

- 无需压缩；
- 没有成本收益；
- 最新块超过窗口；
- 正常失败。

### 估算规则尚未形成生产契约

估算若没有从附件展开前的 `PrimaryMaterializedBlock` 到专用白名单 canonical schema 的固定映射、UTF-8 字节公式、结构开销和版本，会导致：

- 不同实现选择不同 retainedFrom；
- 测试无法写出稳定 golden；
- 同一上下文重试时计划漂移；
- Provider replay、工具 JSON 和附件成本被遗漏，或意外读取并保存附件 bytes。

因此本方案冻结唯一生产入口 `estimatePrimaryMaterializedBlock(block)`；canonical 根是一个 Block 映射得到的完整消息数组，附件只在估算后、实际请求前展开，而不是把公式和附件阶段留给开发阶段决定。

## 改造目标

### 功能目标

- 压缩后保留目标 20,000 tokens 的最近原文尾部。
- 摘要只覆盖尾部之前的有效前缀。
- 支持连续压缩，并保持不重复、不遗漏。
- 保持 ToolCall/ToolResult 和 Provider replay 语义完整。
- 支持主动和手动压缩的明确控制流。
- 主模型 Provider 错误统一按 Web 配置的普通指数退避重试。
- 为所有 Run 提供归属于 Run、可持久查询的稳定终态结果码。
- 当前 trigger 图片无法安全保留时明确失败，不允许静默丢弃后继续。

### 正确性目标

- 消息边界、CAS、Run fence 和 Session revision 保持一致。
- 单一 resolver 定义有效模型上下文。
- 所有模型请求、压缩规划和提交校验使用一致的来源范围。
- 并发变化导致旧计划彻底作废。

### 产品边界目标

- 普通时间线展示当前分支从最早可达祖先到 head 的完整物理历史，包括压缩前原文和 compaction 摘要。
- context root 继续作为模型解析坐标和用户结构操作边界；root 之前的消息只读，不允许 revert/fork。
- retained tail 即使会进入模型私有上下文，在 Timeline 中仍属于 root 之前的只读历史；“是否可操作”不得解释为“模型是否可见”。
- 归档继续表示 context root 之前物理历史的搜索/读取投影，因此可以与 Timeline 的可见集合重叠。
- retained tail 不扩大用户回退和分叉权限。

### 可维护性目标

- 共享契约通过类型表达 compaction 专有字段。
- Provider 兼容投影与成本估算不在 API/Worker 重复实现。
- 结果类型和日志字段足够诊断压缩为何成功、跳过或失败。
