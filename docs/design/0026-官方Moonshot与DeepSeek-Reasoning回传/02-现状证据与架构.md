# 现状证据与目标架构

## 当前实现事实

以下结论来自当前工作区源码；路径与导出符号是审查锚点，行号会随演进漂移。

| 层级 | 当前事实 | 本设计的利用方式 |
|---|---|---|
| 消息契约 | `packages/shared/src/contracts/agent-message.ts` 已定义 reasoning Part，正文为 `text`。 | 不增加 reasoning 消息类型。 |
| Worker 流 | `apps/agent-worker/src/runtime/runner.ts` 的 `StreamingAssistantPart` 有 text/reasoning/tool_call，主循环消费 `reasoning-start`、`reasoning-delta`、`reasoning-end`。 | 标准 SDK reasoning stream 可沿用既有流处理；需补空 text/hook 测试。 |
| 写入 | `apps/api/src/modules/agent/agent-message.store.ts` 的 `AgentMessagePartInput` 支持 text/reasoning/tool_call 的 `providerReplay`，并写入 `provider_replay_json`。 | 默认不改表、不复制正文。 |
| 通用上下文 | `apps/api/src/modules/agent/read-side/runtime-transcript-projector.ts` 跳过 reasoning，空 text 不可见。 | 保持 Provider-neutral transcript。 |
| 私有上下文 | `projectModelContextToPrompt()` 位于 `model-context-resolver.ts`，已有 `assistantOrdinal`、`visibleIndex`、`providerReplay`。 | 扩展为完整 Assistant provenance、边界占位和空 Part 处理。 |
| Worker 协议抽象 | `conversation-state/types.ts` 已有 Adapter、Attempt、`prepareInvocation()`、`observeChunk()`、`finalizeAttempt()`。 | 扩展为 mandatory attempt context、finish capability 与 part hook。 |
| OpenAI 基线 | `openai-responses-adapter.ts`、`openai-responses-replay.ts` 处理 raw events、encrypted content 和 terminal validation。 | 保持既有 OpenAI envelope JSON/回放算法，不复制私有 wire 协议。 |
| Provider 工厂 | `runner.ts` 与 `packages/shared/src/llm/single-call.ts` 各有 `providerOptionsKeyByNpm()`、`createLanguageModel()`。 | 两处都需接官方 Provider；主调用/Worker single-call 都由 Worker 能力表 preflight 约束。 |

## 当前调用链与需修正的时序

```text
SQLite agent_message_part.provider_replay_json
  → ModelContextResolver / projectModelContextToPrompt()
  → PromptContext: messages + providerReplay
  → Worker runModelStep()
  → capability preflight + Registry.resolve(profile)
  → Adapter.prepareInvocation()
  → materialize attachments / build tools / streamText()
  → Attempt.observeChunk() + Runner materialize Part hook
  → finalizeAttempt()
  → final flush
  → 原子 complete Assistant + create queued ToolExecution
  → 后续循环执行工具
```

目标顺序是必须的事务边界：

- `finalizeAttempt()` 成功后才能进入 final flush。
- final flush 成功后，Runner 才构造 queued execution 输入。
- API 必须在同一事务中完成 Assistant 并创建 queued `ToolExecution`。
- 随后的运行循环才执行工具。
- `finalizeAttempt()` 或 final flush 失败时，不得调用这个原子完成接口，因而不能有 completed Assistant、queued execution 或工具副作用的半提交状态。

当前 `runModelStep()` 已由 Runner 负责 streaming Part、retry、complete 和工具调度；Adapter 不得接管这些职责。

## 当前已知缺口

### OpenAI-only replay contract

`packages/shared/src/internal-contracts/agent-provider-replay.ts` 的 `AgentProviderReplayEnvelopeSchema` 当前仅接受：

```ts
{
  version: 1,
  provider: { npm: "@ai-sdk/openai", api: "responses", providerId, model },
  item: /* OpenAI reasoning/text/function_call item */,
}
```

`normalizeProviderReplay()` 当前无条件重建为 OpenAI provider；`assertAgentProviderReplayUpdateCompatible()` 只理解 OpenAI item ID、summary index、phase 和 encrypted content。新设计必须泛化为 discriminated union，但不得改变既有 OpenAI JSON 形状。OpenAI 顶层 `version: 1` 在新增 invocation provenance 中映射为 `protocolVersion: 1`。

### PromptContext provenance 与 reasoning-only 缺口

当前 `projectModelContextToPrompt()` 只聚合有 replay metadata 的 reasoning-only Assistant。它必须改为：只要 completed Assistant 有原始 reasoning Part、但没有通用可见内容，就保留一个 protected 边界占位，即使 metadata 缺失、损坏或未知版本；source 使用 `assistantProvenance: null`。

`assistantOrdinal` 当前实际是 `RuntimeTranscriptProjector.projectDetailed()` 返回的 provider-neutral `messages` 数组中的 Assistant message index。它不是“第几个 Assistant”，本期不改名但所有新算法必须按这一语义使用。

### Attempt 与 options contract 缺口

当前 `PreparedProviderInvocation` 没有必须的 attempt context，`createAttempt()` 无参数。新设计必须让所有 Adapter（包括 OpenAI）返回 immutable context，并由 Runner 传给 `createAttempt(context)`；无 Adapter 的原始 invocation 不创建 Attempt。

新 Provider 还缺少两个安全边界：一是 API/Web/Worker 对 namespace payload 各自处理，无法保证非 reserved options 保留而 fixed payload 不被覆盖；二是 recovery continuation 尚未有基于已有 Part provenance 的 identity fence。实现必须以 shared 唯一 sanitizer/fixed-last merge 收敛前者，并以同 Run/same immutable identity + existing Part identical metadata 收敛后者。

`runModelStep()` 已计算 `preparedProviderOptions`，但当前设置 request options 的 guard 检查的是改写前 `runtimeOptions.providerOptions`。固定思考 payload 会因此丢失。修复时还必须统一语义：Adapter 返回的是 namespace 内部 payload，Runner 只包一次 namespace。

## 目标职责边界

```text
Worker capability table
  ├─ 新 Provider 精确模型的唯一运行时支持判定
  ├─ 固定 thinking payload 映射
  └─ 未验证模型在网络请求前失败

shared contracts
  ├─ Provider npm、严格 replay union、内部 PromptContext schema
  └─ 不存凭证、正文、base URL、完整 options 或 wire JSON

API read-side
  ├─ 读取 Fork/Revert/Compaction 后的当前有效链
  ├─ settings 保存复用 shared sanitizer；Web 的提示不是行为权威
  ├─ 从所有 Part 统一推导 Assistant provenance / null 边界
  └─ 输出 provider-neutral messages + protected providerReplay

Worker Adapter
  ├─ 使用能力表给定的固定 payload，恢复连续兼容 reasoning
  ├─ 返回完整 attempt context 和协议完成能力
  └─ 为本 Attempt 的 Part 生成静态 provenance

Runner
  ├─ 是模型调用、流、持久化、retry、原子完成和工具的唯一协调者
  ├─ 按最终 payload 只包装一次 provider namespace
  ├─ recovery continuation 先验证同 Run/same identity 与已有 Part metadata，再续接或安全 replacement
  └─ 不理解 reasoning_content、thinking.keep 或 Provider raw body
```

## 目标调用链

```text
preflight: Worker capability table 精确命中
  → 官方 SDK model + Adapter.prepareInvocation()
  → 内部 providerOptions payload + immutable attemptContext
  → Runner namespace wrap once / streamText()
  → stream 中创建 text/reasoning/tool_call Part 时执行 hook
  → final validation 指明是否允许 reasoning-only Assistant
  → final flush
  → API 原子完成 Assistant + 创建 queued ToolExecution
  → 后续 PromptContext 推导 provenance / 连续段
```

## 不采用的替代方案

| 方案 | 不采用原因 |
|---|---|
| 将 reasoning 放入 `RuntimeTranscriptProjector` | 会进入 compaction、single-call、日志和非目标 Provider，成为默认传播。 |
| 未验证模型让 Adapter 返回 `null` 后普通调用 | 绕过固定思考和 replay，产生产品承诺不一致。 |
| 在 Runner 按 npm 手写 reasoning HTTP JSON | 破坏 Adapter 边界，绕过 SDK 转换和版本兼容。 |
| 将 Moonshot/DeepSeek 伪装为 OpenAI envelope | OpenAI encrypted/item identity 语义不同，且会污染 primary projection。 |
| 从全历史搜同模型 reasoning | 会跨越 Provider、模型、legacy 或 provenance 缺口。 |
| Adapter 接管工具、提交或 retry | 破坏 Runner/API 的状态机与原子完成权威。 |

## 相关既有设计的冲突处理

`docs/design/0022-Provider对话状态适配器` 中未实施的 DeepSeek 预留采用 `@ai-sdk/openai-compatible`、模型级 `protocolAdapter`、thinking 用户配置和额外快照；这些与本设计冲突，实施时不得照搬。

本设计不修改旧文档，以免篡改历史阶段记录。新代码以本目录为审查依据，同时必须保持 0019/0022 已实现的 OpenAI 行为和测试通过。
