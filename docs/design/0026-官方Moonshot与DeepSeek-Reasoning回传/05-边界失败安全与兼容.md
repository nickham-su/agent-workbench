# 边界、失败、安全与兼容

## 不变量总表

| 场景 | 必须行为 | 禁止行为 |
|---|---|---|
| 同一兼容历史 | 只恢复连续兼容段 reasoning，按原 Assistant/Part 顺序插回 | 从全历史筛选相同模型、复制 text/tool call |
| Provider/config/model/protocol 切换 | 立即形成边界，不回传边界前 reasoning | 跨越后又恢复旧 reasoning 或自动角色转译 |
| 未验证模型 | preflight 在网络/streaming Assistant/工具前失败 | Registry 返回 null 后普通调用或关闭 replay |
| thinking/reserved keys | 能力表固定 payload；保存剥离、运行时忽略用户值 | 用户开关、冲突报错、disabled 分支或用户值覆盖 |
| reasoning-only Assistant | API 保留边界占位；仅满足完成条件才完成；Adapter 删除不可恢复空消息 | 丢弃 legacy 边界、向 Provider 发 `content: []` |
| 空 text | 持久化和 provenance 核验；不消耗 visibleIndex、不发到最终 SDK | 因无 delta 而漏 metadata，或变成可见 text |
| legacy/损坏 envelope | `assistantProvenance: null`，扫描硬停止 | 猜测来源、跨缺口继续恢复 |
| recovery continuation | 同 Run、同 immutable identity、已有 Part metadata identical 才续接 | 覆盖/补写旧 metadata，猜测 Part ID/position，混合新旧 Part |
| Retry/失败/cancel | 未完成 Assistant 不能进入 replay | 部分 Attempt 成为历史或为 metadata 重发模型 |
| compaction | 只使用当前实际 retained tail | 旁路补回已压缩 reasoning 或新增 Assistant anchor |
| 公开面/日志 | 最小 metadata、脱敏 | 请求 body、reasoning、tool output、凭证、完整 replay JSON/原始 SSE |

## Tool Calling 与原子完成时序

通用 transcript 的顺序是权威：

```text
Assistant reasoning + tool call
→ Tool result
→ Assistant reasoning + tool call
→ Tool result
→ Assistant reasoning + final text
```

reasoning 只插入对应 Assistant；不得改变 `toolCallId`、`providerToolCallId`、tool 参数、tool result 的角色/顺序或 call/result ID 关联。

本次必须固定以下提交顺序：

```text
finalizeAttempt() 成功
→ final flushAssistantParts() 成功
→ Runner 从已最终持久化的 tool_call Part 构造 queued execution 输入
→ API 在同一事务中 complete Assistant 并创建 queued ToolExecution
→ 后续运行循环才执行 ToolExecution
```

因此：

- `finalizeAttempt()` 失败时，不得执行 final flush、原子完成接口或工具创建。
- final flush 失败时，不得调用原子完成接口，也不得构造/创建 queued ToolExecution。
- 原子完成事务失败时，Assistant 与 ToolExecution 都不应出现单边已提交；不得重新请求模型“补齐 metadata”。
- retry/replacement 的失败 Attempt 不能执行工具副作用；后续成功 Attempt 才能按同一顺序进入工具循环。

测试必须断言数据库/API 可见状态：没有 completed Assistant + 缺失 queued execution，也没有 queued execution 指向未完成 Assistant。

### DeepSeek 第一版

DeepSeek 第一版对连续兼容段始终恢复所有可恢复 reasoning：

- 不依据 `hasTools`、本次工具数量或“上一轮是否实际调用工具”切换；
- 不预先实现 active tool continuation 检测；
- 工具多子轮必须通过 SDK mock 与官方端点验收，确保每个 Assistant 的 reasoning、tool call 和结果顺序合法。

如果 Spike 证明官方端点要求“缺 reasoning 的 active continuation 必须在请求前拒绝”，该 Provider/模型不能发布，直到另行评审最小 preflight 设计。第一版不得从 provider options 猜测工具，也不得临时加自动降级。

## reasoning-only、空 reasoning 与多 block

以下状态不得假定等价：没有 reasoning、空字符串 reasoning、多个 reasoning block、流开始未结束、SDK 将空字段归一化为缺失。

Spike 与闭环测试必须验证：

- Moonshot/DeepSeek 成功且存在非空 reasoning 时，`finalizeAttempt()` 授权 reasoning-only Assistant 完成，API 保留可定位 source，下一请求可恢复；
- 空 reasoning 不满足 reasoning-only 完成条件，不能伪造空内容；
- provenance 缺失、item type/identity 冲突或 final metadata 未 flush 时，reasoning-only Attempt 不完成；
- 多 block 按原始 `Part.position` 稳定回放；
- `text-start` 无 delta 仍创建空 text、写入 provenance、参与 Assistant 一致性核验，但不消耗 `visibleIndex`、不插入最终 SDK message；
- legacy/损坏 envelope 的 reasoning-only Assistant 在 protected PromptContext 仍生成空边界占位/source null，最终不会发送非法空 Assistant。

## Retry、hook 异常与失败边界

每个真实 `streamText()` 请求是独立 Attempt：

- 同一 model step retry 可复用 immutable context，但必须创建新 Attempt、新 streaming/replacement Assistant；不得复用 chunk map、Part ID 或临时 metadata。
- 工具子轮和下一用户调用重新执行 preflight/prepare 并新建 context/Attempt。
- hook 发生异常时，Runner 必须在下一次 flush 或 Assistant 完成提交前中止 Attempt；实现应尽快 abort 当前流。该本地 invariant 失败不重试模型，不得完成 Assistant/创建 ToolExecution。
- Provider stream/SDK 协议不完整由现有 retry classifier 决定是否有上限重试；网络/API 错误沿用现有 classifier。两者都不得触发异构历史角色转译或去 reasoning 自动降级。
- flush、terminal metadata 或原子完成的本地持久化失败不重发模型；Run 沿既有失败/恢复语义收敛，未完成 Assistant 不成为 history。

第一版不承诺新的公开稳定错误码。测试只断言：失败阶段、是否发出网络请求、是否 retry、是否完成 Assistant、是否创建 ToolExecution，以及错误/日志没有敏感内容。

### Recovery continuation

本期不改变 recovery 的总体状态机，但新 Provider recovery 必须比普通 retry 更严格：

- 只接受同一个原 Run、同一 `providerNpm`、`providerId`、实际模型、protocol、protocolVersion 的 immutable identity。
- 恢复前必须加载已有 streaming Assistant 的 text/reasoning/tool_call Parts，校验 Part ID、position、type 与可解析 provenance。既有 metadata 必须与当前 identity identical；缺失、损坏、不同 identity、item type 不匹配、position/Part ID 冲突均 fail closed。
- hook 发现既有 Part 时只幂等接受完全相同 replay metadata；不得覆盖、补写或把旧 Part 改绑到当前 identity。只有真正新创建的 Part 才能写当前 identity。
- recovery 校验/流/flush 任一失败后，该 streaming Assistant 不得 completed、不得成为 PromptContext replay source、不得创建 ToolExecution。
- 若当前 Runner 无法在复用已有 Assistant 前证明上述条件，Moonshot/DeepSeek 必须使用既有安全 replacement 路径；replacement 如果不能保证旧 Part 不会混入新 Attempt，则直接 fail closed。

不得把 recovery 当作“尽量延续可见文本”的理由而跳过 identity 或 provenance 校验。

## Fork、Revert、Compaction 与切换

### Fork/Revert

Adapter 只能使用 `ModelContextResolver` 输出的当前有效 blocks/messages/sources：

- Fork 仅使用目标分支链；Revert 仅使用新的 head 前链；
- superseded、其他分支、failed/cancelled/pending Assistant 永不进入 replay；
- Adapter 不得按 message ID 直接查询数据库回捞历史。

### Compaction

第一版不新增 Moonshot/DeepSeek Assistant retained-tail anchor。在 `agent-primary-projection.ts`，新 Provider replay descriptor 必须为 `undefined`/不兼容，不能伪装为 `openai_responses`。

在现有合法 anchor 与 retained-tail 规则下：

- 只恢复 API 本次 PromptContext 实际包含的 retained tail reasoning；
- 不绕过 compaction 把已摘要历史或 archive reasoning 补回；
- retained tail 内的 legacy/不兼容 Assistant 是硬边界；
- 新 Provider Assistant anchor 支持是后续独立需求，不因本期 Spike 自动纳入。

### Provider/config/model 切换

兼容 identity 必须完整比较：

```text
provider npm + api/protocol + protocolVersion + providerId + actual model
```

`Moonshot A → Moonshot B`、同 Provider 换模型、`Moonshot → DeepSeek → Moonshot`、OpenAI → 新 Provider、verified 模型 → 非表内别名均是边界。切换请求保留 provider-neutral text/tool history，但不带旧 reasoning。

目标端点对异构历史的接受性是发布门槛。第一版不得把 Assistant 改写为 User message、丢弃工具结果规避 `400`、或收到 `400` 后自动发送降级请求。

## Legacy、版本与隐私

- OpenAI 旧 envelope 按既有 parser 读取，并通过 OpenAI 回归测试；其 `version: 1` 仅在 provenance 投影中映射为 protocol version 1。
- Moonshot/DeepSeek 旧/未知/损坏 envelope、空 ID/模型、未知版本和额外字段均 fail closed，成为 `assistantProvenance: null` 边界；不做历史补写迁移。
- 新协议不兼容变更必须新增 version/protocolVersion，未知版本停止回放。
- envelope 不存 base URL、凭证、正文、工具参数或未知 metadata。debug/error/notice 不输出 reasoning、tool output、HTTP body、`provider_replay_json`、原始 SSE 或认证信息。
- 测试 fixture 只使用虚构 reasoning、工具结果和凭证占位。
