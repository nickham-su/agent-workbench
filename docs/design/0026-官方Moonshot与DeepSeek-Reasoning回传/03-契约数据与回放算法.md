# 契约、数据与回放算法

## 数据最小化与 envelope union

reasoning 正文只存在于既有 `AgentReasoningPart.text`。所有新 replay metadata 都不得复制：reasoning/text 正文、tool input/output/call ID、API key、base URL、headers、完整 provider options、HTTP body、原始 SSE 或未知 SDK metadata。

修改 `packages/shared/src/internal-contracts/agent-provider-replay.ts`，把 `AgentProviderReplayEnvelopeSchema` 扩为严格 provider discriminated union。OpenAI Responses 分支的 JSON 形状保持不变。

新 chat Provider 分支的概念形状固定为：

```ts
type ChatReasoningProviderReplayEnvelope = {
  version: 1;
  provider: {
    npm: "@ai-sdk/moonshotai" | "@ai-sdk/deepseek";
    api: "chat-completions";
    protocolVersion: 1;
    providerId: string;
    model: string; // 实际模型
  };
  item: {
    type: "text" | "reasoning" | "tool_call";
  };
};
```

约束：

- `version` 是 shared envelope 格式版本；新 Provider 的 `provider.protocolVersion` 是 replay 协议版本，两者都参与兼容判断。
- `providerId` 是稳定 Provider 配置 ID；`model` 是实际模型。二者不是显示名或 base URL。
- 新 Provider 的 `item.type` 必须与持久化 Part 一一对应；工具项使用 `tool_call`，不得伪装为 OpenAI `function_call`。
- 所有持久化 text/reasoning/tool_call Part 都必须有 envelope，**包括空 text**。空 text 不可见也不会被插入最终 SDK message，但仍参与 Assistant provenance 完整性核验。
- `normalizeProviderReplay()`、parser 和 serializer 必须按 discriminant 白名单重建；`additionalProperties: false`。新 chat 分支的 identity 一经写入不得变化。
- `serializePartProviderReplay()`、内部 flush schema、`StreamingAssistantPart`、update/tool replay union 必须同时支持新 `tool_call` 与既有 OpenAI `function_call`。

### OpenAI 兼容

OpenAI envelope 不增加 `protocolVersion` 字段，也不改变已有 `version: 1` JSON。API 在构造 OpenAI invocation provenance 时，把它的顶层 `version: 1` 映射为 `protocolVersion: 1`。新增 provenance 只能是 read-side 投影，不能收紧、迁移或破坏已有 OpenAI parser、normalizer、update compatibility 与回放算法。

## Provider Options 唯一规范化与合并

为避免 API、Web、Worker 对同一设置产生不同请求，shared package 必须提供唯一的纯函数与常量；建议置于既有 llm/settings 相关模块，具体路径由实施时按目录职责选择：

```ts
const RESERVED_REASONING_PROVIDER_OPTION_KEYS = new Set([
  "thinking",
  "reasoninghistory",
  "reasoningeffort",
]);

function canonicalTopLevelProviderOptionKey(key: string): string {
  return key.trim().replace(/[_-]/g, "").toLowerCase();
}

function sanitizeReasoningProviderOptions(value: unknown): Record<string, JSONValue>;

function mergeReasoningProviderOptions(
  rawNamespacePayload: unknown,
  fixedOptions: Readonly<Record<string, JSONValue>>,
): Record<string, JSONValue>;
```

语义必须固定为：

```ts
// capability 是 reserved fixedOptions 的唯一来源。
fixedOptions = capability.buildProviderOptions();

// Adapter.prepareInvocation() 调用/使用唯一 shared merge。
sanitizedUserOptions = sanitizeReasoningProviderOptions(rawNamespacePayload);
preparedProviderOptions = { ...sanitizedUserOptions, ...fixedOptions };

// preparedProviderOptions 可以是：
// { parallelToolCalls: true, thinking: { type: "enabled" }, reasoningHistory: "preserved" }
// Adapter 完整保留它；Runner 不修改、合并或丢弃内部 option，只包装 namespace。
```

实现约束：

- `rawNamespacePayload` 只接受 JSON plain object：对象原型只能是 `Object.prototype` 或 `null`，且所有递归值必须是 JSON primitive、array 或 JSON plain object。非对象、array 作为顶层、函数、Date、class instance、Map/Set 等返回空对象或被调用方拒绝；不得原样透传。
- 清理危险对象键至少 `__proto__`、`prototype`、`constructor`。清理必须覆盖 payload 内的递归 object，避免嵌套对象在后续 spread/SDK 处理时带来原型污染语义。
- reserved 判断**只对顶层键**使用唯一算法 `trim → 删除 '_' 与 '-' → lowercase`。规范化结果命中常量时整键移除；不递归移除普通嵌套 option 的同名键。
- `fixedOptions` 来自静态 capability，不接受用户对象引用；它也必须是 JSON plain object。合并是浅层、fixed-last。因 sanitized 对象中已不存在 reserved 键，`thinking`、`reasoningHistory`、`reasoningEffort` 只能由 fixed 整键写入，绝不深合并。
- API settings 保存和 Web UX 复用 shared sanitizer；API 是保存行为权威。Worker 的 Agent Adapter 在每次 `prepareInvocation()` 调用/使用 shared `mergeReasoningProviderOptions()`；Worker single-call 的 invocation preparation 也调用同一 merge。Worker 是运行时行为权威。
- 除 `mergeReasoningProviderOptions(rawNamespacePayload, fixedOptions)` 的 fixed-last 实现外，不存在合法的第二套合并：capability 不得直接返回最终 payload，Runner 不得再次合并、修改或丢弃 prepared 内部 option。

该函数的输入/输出都是 namespace 内部 payload；它绝不添加 `moonshotai` 或 `deepseek` 外层键。

## Invocation identity、Prepared invocation 与 Attempt

### identity

所有 Adapter 使用只读 identity：

```ts
type ProviderConversationStateAttemptContext = Readonly<{
  protocol: "openai-responses" | "moonshot-chat" | "deepseek-chat";
  protocolVersion: number;
  providerNpm: string;
  providerId: string;
  model: string;
}>;
```

它不含正文、base URL、凭证、用户 provider options、thinking mode 或 reasoning effort。唯一目的：实际请求的 Provider/模型身份必须与本 Attempt 全部 Part provenance 一致。

### mandatory Adapter contract

有 Adapter 时，`PreparedProviderInvocation` 必须为：

```ts
type PreparedProviderInvocation = Readonly<{
  messages: ModelMessage[];
  // 当前 Provider namespace 的内部 payload；绝不含 moonshotai/deepseek 外层键。
  providerOptions: Readonly<Record<string, unknown>>;
  includeRawChunks?: boolean;
  attemptContext: ProviderConversationStateAttemptContext;
}>;
```

`ProviderConversationStateAdapter.prepareInvocation()` 必须返回该对象；`createAttempt(context)` 必须接收同一只读 context。所有 Adapter，包括现有 OpenAI Responses，均返回 context；OpenAI 可只提供 identity 映射，不要求改变其既有 replay 处理。
对于新 Provider，Adapter 在 `prepareInvocation()` 中调用/使用 shared merge，完整保留返回的 `preparedProviderOptions`（它可包含合法非 reserved options）；随后在同一阶段处理 replay 和 `attemptContext`。Runner 只按 `providerOptionsKeyByNpm()` 原样包装该内部 payload 一次。

没有 Adapter 时 Runner 使用原始 messages/options 的独立 raw invocation 分支，且不创建 Attempt。不得用 optional context、假 noop context 或 mutable Adapter 字段模糊两条路径。

Runner 在每次真实 `streamText()` 之前按下列规则处理：

```text
有 Adapter：prepareInvocation → 得到 payload + context → createAttempt(context)
无 Adapter：原始 invocation → 不创建 Attempt
```

同一 model step 的网络 retry 使用相同 immutable context，但每次请求都新建 Attempt；工具子轮和下一次模型调用必须重新执行 `prepareInvocation()` 并取得新的 context。Adapter 不得缓存上一次调用的 context。

## Part materialization hook 与完成能力

`observeChunk()` 发生在 Runner 本地 Part 创建前，无法可靠给新 Provider 的静态 provenance 绑定对象。扩展 Attempt 增加通用 hook：

```ts
createPartReplay?(input: Readonly<{
  type: "text" | "reasoning" | "tool_call";
  partId: string;
  providerToolCallId?: string | null;
}>): AgentProviderReplayEnvelope | undefined;
```

Runner 行为：

- 创建 text/reasoning Part 后立即调用 hook；即使 `text-start` 后没有 delta，也必须创建空 text Part 并附 provenance。
- 组装并即将 push tool_call Part 时调用 hook。
- Moonshot/DeepSeek hook 从 context 生成静态 envelope；OpenAI 可以继续使用其 `observeChunk()` raw/event updates。
- hook 返回 item type 不匹配、identity 不匹配或抛异常时，Runner 必须中止 Attempt：最迟在下一次 flush 或 Assistant 完成提交前停止流/终止 Attempt，且不得完成 Assistant 或创建 ToolExecution。此类本地 invariant/hook 失败不应重试模型请求；测试必须验证失败阶段、无完成、无工具和脱敏诊断。

`finalizeAttempt()` 成功值必须泛化为：

```ts
type ProviderProtocolValidation =
  | Readonly<{ ok: true; allowsReplayOnlyAssistant: boolean }>
  | Readonly<{ ok: false; code: string; message: string }>;
```

Moonshot/DeepSeek 成功 Attempt 明确返回 `allowsReplayOnlyAssistant: true`；OpenAI 按其真实现有协议能力返回对应值。Runner 不按 npm 判断 reasoning-only Assistant。

当 Assistant 没有通用可见内容时，Runner 只有在以下条件同时成立才能完成它：

- `finalizeAttempt()` 返回 `ok: true` 且 `allowsReplayOnlyAssistant: true`；
- 至少存在一个 **非空** reasoning Part；
- 该 Assistant 所有 replay-capable Part 的 provenance 均存在、类型正确、与 context identity 一致；
- final flush 已成功持久化该版本的 Parts 与 metadata。

空 reasoning、provenance 缺失/冲突、metadata 未 flush 或协议不允许都必须使 Attempt 在完成前失败，不能只因有 reasoning Part 便完成。

### Recovery continuation 的 identity fence

Recovery continuation 不是新 Attempt 的空白 Part 创建。新 Provider 仅在以下条件全部成立时恢复既有 streaming Assistant：

- recovery 指向的 Assistant 属于同一个原 Run；
- 当前 `attemptContext` 与恢复时持有的 immutable identity 在 `providerNpm`、`providerId`、`model`、`protocol`、`protocolVersion` 上完全相同；
- 已有 text/reasoning/tool_call Part 的位置、Part ID、类型和 `providerReplay` 均可被加载、解析并校验；
- 每个已有 replay-capable Part 的 metadata 与当前 identity 相同，且 item type 与 Part 类型对应。

恢复时的 hook 规则与新建 Part 不同：

```text
命中既有 Part：仅 identical providerReplay 才幂等接受；
               metadata 缺失、损坏、类型/identity 不同、position 或 Part ID 冲突 → fail closed。
创建新 Part：才允许以当前 attemptContext 生成并附加新 metadata。
```

不得用当前 identity 覆盖、补写或“修复”已有 Part 的 provenance。恢复验证失败时，Assistant 不得 completed、不得进入 PromptContext replay、不得创建 ToolExecution。

如果现有 Runner 恢复机制不能在网络调用前证明上述已有 Part 续接安全，Moonshot/DeepSeek 必须改走现有安全 replacement 路径。replacement 只有在旧 Part 不会与新 Attempt Part 混入同一 Assistant 时才可用；否则直接 fail closed。不得猜测 continuation 的流位置、Part position、Part ID 或历史 identity。

## Assistant provenance 与 protected PromptContext

API 对每个投影到 provider-neutral `messages` 的 completed Assistant 都输出一个内部 source：

```ts
type InvocationProvenance = Readonly<{
  protocol: "openai-responses" | "moonshot-chat" | "deepseek-chat";
  protocolVersion: number;
  providerNpm: string;
  providerId: string;
  model: string;
}>;

type AgentApiPromptProviderReplaySource = {
  // 当前 provider-neutral messages 数组中的 Assistant message index，不是第几个 Assistant。
  assistantOrdinal: number;
  assistantProvenance: InvocationProvenance | null;
  parts: Array<
    | { visibleIndex: number; type: "reasoning"; text: string; providerReplay: Envelope }
    | { visibleIndex: number; type: "text"; providerReplay: Envelope }
    | { visibleIndex: number; type: "tool_call"; providerReplay: Envelope }
  >;
};
```

可信 `assistantProvenance` 的条件：

- Assistant 有至少一个 replay-capable Part；
- 所有 text/reasoning/tool_call Part（含空 text）均有解析成功、类型匹配的 envelope；
- 所有 envelope 的 `{ npm, api, protocolVersion, providerId, model }` 完全一致，且是已识别分支；
- Assistant 是当前有效链、已完成并实际被本次 PromptContext 投影。

任何 Part 缺失、冲突、损坏、unknown version/protocol 或 legacy 数据都使 `assistantProvenance: null`，是硬边界。Worker 不得从单个 reasoning Part 推测 Assistant 来源。

### reasoning-only 边界占位

若 completed Assistant 有任一原始 reasoning Part、但没有通用可见内容（非空 text 或 tool_call），protected PromptContext 必须保留 `content: []` 的 Assistant 占位，**即使** replay metadata 缺失、损坏或版本未知。对应 source 仍存在；不能可信回放时 `assistantProvenance: null`。

这是 API 边界定位对象，不是 Provider 合法消息。Adapter 必须先用 source/`assistantOrdinal` 计算连续段、插入可恢复 reasoning，再从最终 SDK messages 删除所有仅作边界定位且没有被恢复为合法内容的空 Assistant。不得把 `content: []` 直接发到 Moonshot、DeepSeek 或其他 Provider。

`visibleIndex` 仍与 `RuntimeTranscriptProjector` 一致：非空 text 与 tool_call 消耗 slot；reasoning 和空 text 不消耗。每个 source 的 `parts` 数组必须按原始 `Part.position` 升序，Adapter 对同一 `visibleIndex` 的多 block 以该稳定数组顺序处理。最终 Provider message 不插入空 text。

## 连续兼容段算法

输入是本次 context identity、provider-neutral messages 和每个 Assistant 的 source。`assistantOrdinal` 是 messages 数组索引，不能当作 Assistant 计数器。

```text
从最后一个 Assistant source 向前扫描：
  identity 与目标完全相同：
    收集该 Assistant 类型/位置均可验证的 reasoning parts
    继续扫描
  provenance 为 null、identity 不同、source/位置无法定位：
    立即停止

将已收集 entries 按 messages 索引升序、source parts 原始顺序插回对应 Assistant。
删除没有可恢复内容的边界空 Assistant，得到最终 SDK messages。
```

兼容比较必须同时包括 provider npm、API/protocol、protocolVersion、providerId 和实际模型。User/System/Tool result 不单独中断段；其相关 Assistant source 才是边界。

不得跨越 Provider/模型切换、Provider 配置切换、Moonshot → DeepSeek → Moonshot、legacy Assistant、损坏 envelope、未知协议版本或 provenance 缺口。只插 reasoning；text/tool_call 已在通用 transcript 中，不能重复。插入不得改变 tool call/result ID 或顺序。

## Compaction 与条件升级

默认不增数据库字段。新 Provider envelope 在 `packages/shared/src/agent-primary-projection.ts` 的 primary projection 中必须明确投影为 `undefined`/不兼容，绝不伪装成 `openai_responses`。第一版不新增 Moonshot/DeepSeek Assistant retained-tail anchor 能力。

在现有合法 anchor/retained-tail 规则下，Adapter 只从 API 本次实际投影的 retained tail source 恢复 reasoning；不得回捞被压缩历史。新增 Assistant anchor 是后续独立需求。

若 Spike 证明标准 SDK 事件无法区分协议必需的空/缺失 reasoning、无法维持多 block 顺序，或不能合法序列化已恢复的状态，必须停止常规实现并另行评审条件升级。不得预先添加 raw chunks、数据库字段或伪造空 reasoning。
