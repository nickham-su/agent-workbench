# 需求与产品契约

## 需求背景

Agent Workbench 的 Agent 会执行工具、追加消息，并在后续调用中理解当前有效上下文。对于目标 reasoning 模型，思考内容不只是展示文本：Provider 要求在后续请求中带回历史 Assistant reasoning，才能维持工具子轮与多轮对话的协议正确性。

当前项目已经完成官方 OpenAI Responses 的私有 replay，且具备以下基础：

- `reasoning-start`、`reasoning-delta`、`reasoning-end` 可写成 Assistant reasoning Part；
- `agent_message_part.provider_replay_json` 可保存严格白名单化 metadata；
- PromptContext 有与 `messages` 分离的 `providerReplay` side-channel；
- `ProviderConversationStateAdapter` 已用于 OpenAI 私有 reasoning 恢复。

本需求新增官方 Moonshot/Kimi 与 DeepSeek Provider。这里的“回传”严格指：**下一次请求重新向模型发送 Provider 所需的历史 reasoning**。仅 UI 展示、落库、调试输出或摘要模型可见均不算完成。

## 产品目标

### 必须实现

- 支持 npm 类型为 `@ai-sdk/moonshotai`、`@ai-sdk/deepseek` 的 Provider，且主调用只走各自官方 AI SDK 工厂。
- 两个新 Provider 的 Agent 主调用与 Worker 发起的 single-call 都固定开启思考；用户不能配置、关闭或覆盖该策略。
- 新 Provider 的每个持久化 Assistant `text`、`reasoning`、`tool_call` Part（包括空 text）都带同一 invocation provenance；正文不复制进 metadata。
- 只恢复当前有效上下文尾部的连续兼容段 reasoning，并恢复为标准 AI SDK `ModelMessage` reasoning Part；不得手写 Provider HTTP body。
- Moonshot 使用官方 Provider 的 preserved-history 语义；DeepSeek 第一版始终恢复连续兼容 reasoning，不按 `hasTools` 切换。
- reasoning 正文继续使用既有 `AgentReasoningPart.text` 保存和展示；默认不新增数据库字段。
- 只有精确模型能力表中的 verified 模型可作为这两个 Provider 的 Agent 主模型或 Worker single-call 模型；不在表中的调用在网络请求、streaming Assistant 创建和工具执行前明确失败。

### 用户可观察行为

- 选择已验证模型后，reasoning 与既有 reasoning Part 一样随流展示并随 Assistant 保存。
- 相同 Provider、相同配置实例、相同实际模型的后续 Agent 调用可携带此前保留的 reasoning。
- 工具连续子轮维持既有 Assistant tool call、Tool result、后续 Assistant 的顺序；reasoning 只是目标 Provider 的私有请求扩展，不改变 timeline 和通用消息角色。
- 切换到不兼容 Provider、Provider 配置或模型时，不发送旧 reasoning。目标端点是否接受剩余 provider-neutral 历史必须经过发布前联调；未验证前不得承诺任意切换可继续执行。
- 用户仍可在设置中编辑 Provider/模型的常规配置；第一版 Web 不展示 replay 状态、能力表或新的 capability API。保存后，未验证模型可存在于配置中，但 Agent/Worker single-call 发起时会明确失败而非降级普通调用。

## 固定思考与保留参数

### 产品决定

Moonshot 与 DeepSeek 的目标模型是思考模型，关闭思考会明显降低 Agent 的工具规划和代码任务表现。因此 Agent 与 Worker single-call 固定开启思考。

本期不设计：

- thinking 用户开关；
- `effectiveReasoningMode` 或 disabled 状态；
- thinking 配置优先级、冲突报错或 disabled replay 边界；
- `reasoningEffort` 默认值、性能档位或用户配置；
- Web replay capability 展示或 shared capability API。

### Reserved keys 的确定行为

下列键是 Moonshot/DeepSeek 的系统保留协议键：

```text
thinking
reasoningHistory
reasoningEffort
```

对这两个 Provider：

- API/settings 保存必须从 generic Provider Options 剥离这些键；同时处理大小写、下划线和连字符等规范化等价写法，避免遗留写法绕过。
- 既有已存的同类值在 Worker 运行时必须无条件忽略；下一次设置保存会清理它们。
- Web 不提供专门 thinking 控件；generic JSON/Options 的帮助、校验和提交前清理必须把这些键标为 reserved，不能把它们带到保存请求。
- 不为这些值产生“协议冲突”错误；系统静默剥离用户值并采用能力表给定的固定值。
- reserved 参数的唯一来源是 `capability.buildProviderOptions()` 返回的 `fixedOptions`；capability 不返回含用户 options 的最终 payload。
- shared `mergeReasoningProviderOptions(rawNamespacePayload, fixedOptions)` 是唯一的清理、合并语义。Adapter 必须在 `prepareInvocation()` 中调用/使用它，完整保留其返回的 `preparedProviderOptions`，并同时准备消息 replay 与 `attemptContext`。
- `preparedProviderOptions` 是**当前 Provider namespace 内部 payload**，不是含 namespace 的外层对象；Runner 不能修改、重新合并或丢弃其中的内部 option。

当 `sanitizedUserOptions` 为空时，Adapter 得到的 payload 例如为：

```ts
// Moonshot：PreparedProviderInvocation.providerOptions
{
  thinking: { type: "enabled" },
  reasoningHistory: "preserved",
}

// DeepSeek：PreparedProviderInvocation.providerOptions
{
  thinking: { type: "enabled" },
}
```

通常它还会保留合法非 reserved options：

```ts
// Adapter 完整保留 shared merge 的结果；Runner 不修改或丢弃内部 option。
{ parallelToolCalls: true, thinking: { type: "enabled" }, reasoningHistory: "preserved" }
```

Runner 才按 `providerOptionsKeyByNpm()` 包装一次：

```ts
// preparedProviderOptions 可能同时包含 parallelToolCalls 与 fixed reasoning options；Runner 原样包装。
requestBase.providerOptions = {
  moonshotai: preparedProviderOptions,
  // 或 deepseek: preparedProviderOptions
};
```

不得出现 `moonshotai.moonshotai` 或 `deepseek.deepseek` 双重 namespace。

### 非 reserved options 的保留与合并

用户仍可配置 Moonshot/DeepSeek **其他合法的 namespace 内 Provider Options**。这不是 thinking 配置入口。唯一行为语义为：

```ts
sanitizedUserOptions = sanitizeReasoningProviderOptions(rawNamespacePayload);
fixedOptions = capability.buildProviderOptions();
preparedProviderOptions = { ...sanitizedUserOptions, ...fixedOptions };
```

约束：

- 这是浅合并；`fixedOptions` 必须最后覆盖。不得对 `thinking`、`reasoningHistory`、`reasoningEffort` 做子字段深度合并。
- sanitizer 仅接受 JSON plain object 作为 namespace payload。非 plain object、数组、函数、Date、class instance 等非 JSON 对象语义不得进入请求。
- sanitizer 递归保留合法 JSON 值，并清理危险对象键，至少包括 `__proto__`、`prototype`、`constructor`；不得使 spread、序列化或 SDK 调用受到原型污染影响。
- reserved 匹配只针对 namespace payload 的**顶层键**：键名依次 `trim`、删除 `_` 与 `-`、转小写后，匹配 `thinking`、`reasoninghistory`、`reasoningeffort` 即整键删除。嵌套普通 option 不递归删除同名键；如果顶层 `thinking` 是一个嵌套对象，则该顶层对象整体删除。
- API 保存清理与 Worker 运行时清理是行为权威；Web 的清理/提示只改善 UX，不能替代前两者。
- Web、API、Worker 必须复用 shared package 中同一个纯函数与 reserved-key 常量，禁止各自实现相近但不同的规范化逻辑。具体文件位置由实现时按 shared 结构确定。
- Agent 主调用和 Worker single-call 对相同 raw payload 与 fixedOptions 必须使用同一个函数，得到字节语义等价的最终内部 payload。

### Recovery continuation 的产品边界

本期不重设计 recovery，但新 Provider 不得把恢复已有 streaming Assistant 当作普通新调用。只有同一个原 Run 且 Provider npm、Provider 配置 ID、实际模型、协议、协议版本均等于当前 immutable attempt identity 时，才允许安全继承。

恢复无法通过已有 Part provenance 校验时，用户不会获得“尽量接着写”的降级行为：Worker 必须使用既有安全 replacement 路径；若 replacement 也不能确保不混入旧 Part，则直接 fail closed。失败的 streaming Assistant 不得 completed、不得进入 PromptContext replay history、不得创建 ToolExecution。

## 术语

| 术语 | 定义 |
|---|---|
| 通用 transcript | `RuntimeTranscriptProjector` 输出的 Provider-neutral 历史，包含文本、工具调用与工具结果，不包含 reasoning。 |
| replay side-channel | PromptContext 中与 `messages` 平行的内部 `providerReplay`；不进入公开 API。 |
| provenance | 表示 Assistant 来自哪种协议、Provider 配置实例与实际模型的白名单 metadata。 |
| invocation identity | `{ protocol, protocolVersion, providerNpm, providerId, model }`；保证请求与落库 provenance 一致，不含正文、base URL、凭证或任意 options。 |
| replay-capable Part | Assistant 的 text、reasoning、tool_call。空 text 也属于此集合并参与 provenance 核验，但不属于通用可见内容。 |
| 连续兼容段 | 从当前有效历史尾部向前连续满足目标 invocation identity 与可信性规则的 Assistant 区间。只从该段恢复 reasoning。 |
| 实际模型 | `providerModelId` 非空时的 trim 后值，否则为配置模型 `id`。 |
| 边界占位 | protected PromptContext 为 reasoning-only Assistant 保留的空 Assistant message，用于定位/中断回放；它不是最终允许发给 Provider 的空消息。 |
| verified 模型 | 已写入 Worker 单一静态能力表，并通过锁定 SDK、固定参数、完整 replay 与官方端点验收的精确实际模型 ID。 |
| sanitizedUserOptions | 由 shared 纯函数从 raw namespace payload 得出的安全、非 reserved JSON plain object。 |
| recovery continuation | Worker 尝试继承同一 Run 的既有 streaming Assistant；其 Part/provenance 校验规则比新 Attempt 更严格。 |

## 严格支持范围与能力表

能力表是 Worker 内单一静态实现，是运行时唯一权威。其每项至少包含：

```ts
{
  providerNpm,
  model,               // 精确实际模型 ID，不是前缀
  protocol,
  protocolVersion,
  buildProviderOptions // 返回 namespace 内部的固定 payload
}
```

规则：

- 初始文档不伪造 verified 名单。Spike 完成后，必须把通过的精确模型 ID、锁定 SDK 版本和参数映射填入本目录的发布记录及 Worker 表。
- 对 `@ai-sdk/moonshotai`、`@ai-sdk/deepseek`，能力表不存在精确实际模型项时，Agent invocation preflight 和 Worker single-call preflight 必须失败，且不得发网络请求、创建 streaming Assistant、创建 ToolExecution 或让 Registry 返回 `null` 后按普通调用继续。
- 不能以模型前缀、显示名、base URL、自定义网关别名或 SDK “似乎识别”作为替代。别名只能作为表中的精确条目，且有独立测试/联调证据。
- 能力表不对 UI/API 暴露；Web 第一版仅保留既有配置能力，不显示 `verified`、`SDK-recognized` 等状态。
- 发布说明中的 verified 模型列表必须与 Worker 表逐项一致。能力表变更是协议行为变更，必须附 SDK mock、Worker 闭环和官方端点证据。

## 明确非目标

本期不得顺带实现或宣称：

- 用 `@ai-sdk/openai-compatible` 接入 Moonshot 或 DeepSeek；
- 未验证模型的“普通调用但不 replay”降级路径；
- 把 reasoning 无条件写入所有 `context.messages`、所有模型请求、single-call history、archive 或公开 API；
- 手工拼 Provider wire-level `reasoning_content`、`thinking.keep` 或工具 HTTP JSON；
- 将 Moonshot/DeepSeek reasoning 塞进 OpenAI encrypted replay 字段；
- 数据库 migration、消息级 replay 列、正文副本或任意未知 Provider metadata 落库；
- 跨 Provider 历史自动角色转译、收到 `400` 后去 reasoning 重试；
- 新 Provider Assistant 作为 compaction retained-tail anchor；
- DeepSeek active tool continuation preflight，除非 Spike 证明标准恢复不足且另行评审。
