# 开发任务拆分、依赖与交付门槛

按下列**依赖顺序**分批实现；每一批能独立编译／审查。改动只围绕这条需求，不顺便重构 Workspace、工具注册或 Provider 架构。具体行为以[业务矩阵](./01-需求与业务契约.md)、[实体与安全边界](./02-实体与安全边界.md)、[投影](./03-模型上下文与Provider投影.md)为准。

## 建立共享契约与历史兼容边界

- `packages/shared/src/contracts/agent-primitives.ts`、`contracts/settings.ts`、`contracts/agent-message.ts`：新可调用工具名 `view_image`，删除可配置／可新调用 `visual_analyze`；单独保留**仅用于读取历史消息／tool-call**的 legacy 名称校验，不能简单从所有 union 删除旧值而导致历史消息解析失败，也不能让旧值出现在新工具定义或可用工具白名单中。
- `packages/shared/src/internal-contracts/agent-api-read.ts`、`agent-api-message.ts` 及相关 RPC：严格定义工具输出 `text`／`error-text`／`image_ref` 及非空平坦成功组合；`image_ref` 只有 `type,path`。对 `view_image` completed 写回使用严格对象 `{type:"image_ref",path}`，不允许 nested JSON、Base64、任意属性。PromptContext 的**当前用户触发图** `AgentApiPromptAttachmentRefPartSchema` 增加必填 API 可信 `path`，保留 `workspaceId,attachmentId,mediaType,filename` 供关联／一致性校验；tool-result 输出支持有图但未物化的 path 变体；compaction source 的上传图片附件加可选可信相对 path、ToolExecution 增加**窄路径引用与 originRunId**，不可直接暴露整体 structuredResultJson。旧历史无可信 path 不生成该媒体分支，消息结构仍可读。
- 现有 user 上传 PromptContext image parts 最多 4 张的 tuple 定义可保持；并发 tool 图片合并成 user SDK 消息发生在 Worker、**不必将 API 的上传 user tuple 人为扩展为无界数组**，避免把普通 user 上传接口意外放宽。
- 基本测试／门槛：TypeBox 合法／非法对象边界（空 path、嵌套、数组 error-text、额外字段），API/Worker 双侧共享契约类型检查；历史 `visual_analyze` 可读但不执行；`npm run build -w packages/shared`。

## 迁移新上传图片的最终文件位置

- `apps/api/src/modules/agent/attachments/{agent-attachment-paths,agent-attachment-storage,agent-attachment-limits}.ts`、`apps/api/src/modules/agent/routes/agent-public.routes.ts`：仍按现有限制在 dataDir 临时目录完成 multipart、文件头与单／总量异步预校验；从 MIME 生成受控文件名。Workspace 确认并通过事务内业务判定后，才在可信 Workspace `.awb/agent/attachments/att_<id>.<后缀>` 同步、排他 hardlink 发布，核对目录及 inode；不能覆盖或按路径误删被别人置换的文件。
- `apps/api/src/modules/agent/lifecycle/{run-lifecycle-application,sqlite-run-lifecycle-persistence}.ts`：严格验证新 storageKey；`activateUserRun()` 采用 SQLite IMMEDIATE 事务，**先取得写锁并权威检查幂等、Session／标题／fork 冲突，再发布 final、写入附件／消息／Run，成功后入队 Worker**。普通冲突不发布 final；失败尽力清理 dataDir 暂存，DB 回滚不能留下可被误读的 message。发布后 SQL／进程／磁盘异常可能留下无 DB 关联的 final：Workspace 可写目录中无法原子保证“只删除指定 inode”，不得用路径删除冒险清理；保留有限脱敏诊断、人工核查，不建复杂孤儿持久状态／配额／定时清扫。老记录不改写、不批量清理。
- `apps/api/src/modules/agent/agent.composition.ts` 的受控附件内容读取：**实施前基线（设计时）**按 `storageKey === attachmentId` 判定并从旧 dataDir 取文件；现已改为从可信新 key 得 Workspace 相对 path；继续检验 Session 可见链及附件归属，安全打开新 Workspace 文件并验证原字节数、类型后响应；旧图片无安全可读文件时受控 404、不抛服务端异常。`apps/api/src/modules/workspaces/workspace.service.ts` 的 `removeWorkspaceFileDomains()` 安全删除整个 `workspaces/<dirName>`，应验证新 `.awb` 目录随其清理且不越界；预览服务保持 `.awb` 拒绝。
- `apps/api/src/modules/agent/read-side/model-context-resolver.ts`：按当前 Workspace 严格关联 message image part → `agent_attachment.id/workspace_id`，核对 MIME/filename/key 后从 `storage_key` **批量生成**新规范 `relativePath`；普通历史与 compaction 使用同一权威映射，旧记录返回无路径占位。当前触发 Run 由 `runtime-transcript-projector.ts` 发含 path 的 `attachment_ref`，缺 path 则本地失败，不从 filename 猜；Web 已授权预览仍走受控附件 ID 接口。
- `apps/agent-worker/src/runtime/agentAttachmentStorage.ts` 与 `runner.ts` 的 `materializePromptAttachments()`：**实施前基线（设计时）**只能从 dataDir 的 `agent/attachments/by_workspace` 读取上传用户图；现已使用**API 内部 PromptContext 显式 path + 当前 Run 的 workspacePath**，核验 Workspace ID、附件 ID 与 path 的一致性、真实目录包含／句柄、字节、MIME，绝不回退旧 dataDir 猜路径；Worker 启动依赖注入须保持此读取器，确保触发 Run 首次及重试时的 user file part 实际携图。
- 基本测试／门槛：PNG/JPEG/WebP 上传→DB 记录→`.awb` 实体→**API PromptContext 显式 path → Worker 真实 file bytes → 新建 Runner 与真实 API PromptContext 模拟恢复后仍能从原 path 读取 → 前端受控 GET 新附件**→下个 Run 路径占位；图片内容接口跨 Workspace、跨无权 Session、符号链接和文件置换；验证单连接与双连接争用下普通去重／冲突均在 final 发布前结束，发布后 SQL 异常仅回滚 DB 并保留待人工核查的文件，不误删替换文件，Workspace 删除不越界；图片真实字节不入普通日志；`npm run typecheck -w apps/api` 和 `-w apps/agent-worker`。

## 安全文件读取与工具执行写回

- `apps/agent-worker/src/runtime/tools/providers/builtin.ts`、`types.ts`、工具 schema/registry、`apps/agent-worker/src/runtime/runner.ts`：注册 `view_image({path})`；单路径安全打开、拒绝路径和祖先软链／TOCTOU、大小／签名／后缀检测。复用同一读取器在工具执行及模型请求前重读；工具执行成功只返回路径元数据，没有图像二进制和附加视觉模型请求。若需要文本和图像，严格用扁平数组；单图默认 `{type:"image_ref",path}`。
- `runner.ts` 的 `STRUCTURED_RESULT_TOOL_NAMES` 和 `apps/api/src/modules/agent/agent.composition.ts` 的同名白名单同步扩展，仅允许 `view_image` 通过服务端严格校验把路径写进 `agent_tool_execution.structured_result_json`；从 ToolExecution 读图以前核验其所属 Run/Session/Workspace、来源 toolCallId 和 completed 状态。不能把被截断 preview 当 path。工具原始 providerResult、错误捕获与 debug record 只包含纯文字路径数据；原有失败／取消／terminal 幂等语义保留。
- 基本测试／门槛：合法图片、伪造图片、空文件、目录、绝对路径、`../`、软链、换 inode、读取中替换、单张超 10 MiB、文件删除、不同 Workspace 运行上下文，以及写回恶意 structuredResult、伪造 run、重复终态写回；一项失败不影响同轮其他工具正确应答；`npm run typecheck -w apps/agent-worker` 与 `-w apps/api`。

## 普通消息、并发 Provider 与 reasoning 投影

- `apps/api/src/modules/agent/read-side/{model-context-resolver,runtime-transcript-projector,messages-context-projector}.ts`、`apps/api/src/modules/agent/agent.composition.ts`：resolver 从结构化权威字段**窄映射** tool imageRef、originRunId；新用户图片的 message part 只有 attachmentId／MIME／filename，须在可信 Workspace 下按 ID 批量关联 `agent_attachment.storage_key` 才能生成相对路径，旧记录无新格式则只给数量占位，不能用原 filename 拼路径或每图进行无界 DB 查询；当前 Run tool 图片才保留待物化引用，其他入口只给路径文字；queued/running assistant 边界及 legacy 工具结果保持原规则。`messages-context` 无 Run 权限不得自动发图。
- `apps/agent-worker/src/runtime/runner.ts` 与 Provider 调用准备层：先按原始 assistant ordinal 完成 Moonshot/DeepSeek reasoning 恢复并保持 preparedInvocation 消息／ordinal 不可变；**实施前基线（设计时）**在重试循环外物化用户图、构建含图片的 `requestBase`，现须保持**每次 attempt 开始、Provider 调用前重建**。每次重新读取全部用户图与工具图并重验 per-image 10 MiB／该次请求合计 20 MiB；OpenAI Responses／Anthropic 构造媒体 tool result；三种 Chat 入口（openai-compatible、moonshotai、deepseek）按每轮 call part 位置输出完整文本 tool replies，再追加一条交织 `[text label, file, ...]` 的 user 多图消息。Provider 失败进入现有自动重试；图片物化失败必须处于 Provider 重试 catch **之外**或有明确的本地错误类型优先重抛，不允许被重试分支吞并、复用上一 attempt 字节或重复修改 reasoning。
- 审查 `writeAssistantDebugRecord`／工具日志／API preview／错误信息不能包含媒体 Base64；SDK 序列化测试应校验 OpenAI Responses `function_call_output`、Anthropic `tool_result` 与三种 Chat 的 tool/user 顺序、callId 标签，不仅检查内存对象是否有图片；Moonshot/DeepSeek reasoning ordinal 与 SDK 末尾 user 边界需真实回归用例。
- 基本测试／门槛：单图仅媒体结果，双 view_image 并发**完成顺序反转**，一成一败、多工具混合、全部失败、三个成功图超合计 20 MiB、跨 Run 仅文字、**首轮远端报错后自动重试前删除／合法覆盖工具图及原用户图**（删图本地失败且不重试／不使用上轮 bytes，覆盖用新字节）、Provider 拒绝图片自动重试／达到上限终态；五种 Provider 都通过相应协议测试。

## 压缩、清理旧视觉配置与端到端验收

- 压缩：扩 `packages/shared/src/internal-contracts/agent-api-read.ts` 的窄 source、`apps/api/src/modules/agent/agent.composition.ts` 的单快照 source，`apps/agent-worker/src/runtime/compaction/{primary-materializer,tool-execution-result,types,planner,estimator-v1,summary-input-materializer,summary-input-to-model-messages}.ts` 的**实际使用到的路径**。工具图片块落入 prefix 时换成明确路径文本供摘要使用、**不携媒体**；同 Run retained tail 需要媒体才安全重读／计预算。`planner.ts` 的 `containsTriggerMedia` 与 `media_requires_resend(triggerMessageId)` **只保留原用户触发图片**，工具图不进入 trigger 搜索、不套用用户重发终态；若必要工具图无法安全保留，按一般本地失败诊断。回归 tool-only 图片块超尾部预算仍可正常摘要／不触发用户重发；普通 PromptContext 与压缩同一 ToolExecution 的路径／callId 顺序一致。
- 旧能力清理：删除 `builtin.ts` 独立 `generateSingleCallSummary` 的 `visual_analyze` 分支及专用 profile vision；`packages/shared/src/contracts/settings.ts`、`internal-contracts/agent-api-read.ts`、`apps/api/src/modules/settings/settings.service.ts`、`apps/api/src/modules/agent/agent.composition.ts`、`apps/web/src/features/settings/components/{AgentRuntimeSettingsPanel.vue,agentTools.ts}` 等同步移除 `visionModel`／`vision` 的**新配置及运行逻辑**。历史设置 JSON 中存在 vision 字段时安全忽略、规范化输出不再包含它；不让旧配置或旧历史工具名重新启用视觉旧路径。检查全仓与旧工具相关的测试、国际化字符串、工具定义与 UI 项，更新为新语义或删除，不留第二个视觉模型入口。
- 汇总测试／门槛：单图与并发多图的 API→Worker→模型请求→历史只留路径端到端；上传、内容预览、模型拒绝图片、文件失效、用新 Runner＋真实 API PromptContext 模拟 Worker 恢复数据流、压缩 prefix/tail；保留旧历史的消息／UI 可读性。执行 `npm run build -w packages/shared`，`npm run typecheck -w apps/agent-worker`、`-w apps/api`、`-w apps/web`，以及相关 workspace 的定向测试；必要时再执行 `npm run typecheck` 与 `npm run build`。详细逐项断言见[验收标准](./05-验收标准与测试矩阵.md)。
