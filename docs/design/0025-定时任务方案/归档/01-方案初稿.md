# 定时 Agent 任务方案初稿

## 背景与目标

- 在 Workspace 内配置周期性 Agent 任务，由系统按计划触发既有 Agent 执行链路。
- 首版目标是让个人开发者能够将已验证的独立任务或既有对话上下文中的任务周期性执行，并保留每次执行的独立 Session、Run 与历史记录。
- 定时任务只负责编排一次执行，不新建第二套 Agent 执行引擎；Session、RunLifecycle、Worker、运行恢复与 Workspace 删除围栏继续复用现有能力。

## Workspace 范围与入口

- 定时任务在 Workspace 页面内配置和管理。
- 任务始终绑定当前 Workspace：创建时由页面上下文确定 `workspaceId`，不提供跨 Workspace 选择器。
- 任务只能使用同一 Workspace 内的 Session、Message、Agent、Provider 和 Model 配置。
- 列表、编辑、启停、立即运行与执行历史均按当前 Workspace 展示和操作。
- 同一 Workspace 内的多个 Session 仍可能同时修改同一文件路径；首版不阻止这种并发，界面应提示用户避免配置相互冲突的写任务。

## 触发模式

### 新建 Session

每次触发执行以下流程：

```text
创建新的 primary Session
→ 发送任务预设 Prompt
→ 经既有 RunLifecycle 创建并启动 Agent Run
```

适用于任务上下文可以完全由预设 Prompt 表达的场景。

### 从历史 Message Fork

创建任务时，用户选择同一 Workspace 内的来源 Session 与来源 Message，并填写每次执行要追加的 Prompt。

每次触发执行以下流程：

```text
按 sourceSessionId + sourceMessageId 从不可变历史消息锚点 Fork 新 Session
→ 发送任务预设 Prompt
→ 经既有 RunLifecycle 创建并启动 Agent Run
```

- 不创建冻结模板 Session，也不复制 Message、Part、Tool Execution 或上下文快照。
- 任务保存 `sourceSessionId` 与 `sourceMessageId` 作为展示、血缘和创建时校验信息，以及后续内部 Fork 的锚点。
- 创建任务时必须验证：来源 Session 属于当前 Workspace、目标消息属于来源当前有效链、目标消息类型与终态合法、消息图和压缩上下文可用。
- 触发时使用受控的内部“按不可变消息锚点 Fork”能力，而不是直接套用公开 Fork 的来源当前状态限制。
- 因 Message 历史及其祖先关系不可变，来源 Session 后续继续对话、Revert、Compaction、当前 `head` 变化或正在运行，都不应影响已创建任务从该锚点恢复上下文。
- 内部 Fork 仍须保留消息图、上下文 root、压缩锚点和目标 Message 完整性的 fail-close 校验；数据损坏或锚点不可用时，本次执行启动失败并记录原因。

## 调度、并发与漏跑语义

- 调度器运行于 API 进程；SQLite 是任务定义、下次执行时间和执行实例的权威状态。
- 每个自动计划时点只允许创建一个 execution，以任务与计划时点的唯一性防止 tick 重叠、进程重启扫描或重复调度产生两个 Run。
- 同一任务存在 `starting` 或 `running` 的 execution 时，新的计划触发不创建 Session 或 Run：
  - 写入一条执行记录；
  - 状态为 `skipped`；
  - 原因为 `previous_execution_running`；
  - 正常推进任务的下一次计划时间；
  - 不排队、不合并、不补跑。
- 手动立即运行不改变 `next_run_at`。若同一任务已有 `starting` 或 `running` execution，则拒绝手动立即运行并提示任务仍在执行。
- 不同定时任务可以并行；同一 Workspace 的普通 Agent Run 或其他定时任务 Run 不阻止当前任务触发。
- 服务停机期间错过的计划时间不补跑。扫描恢复后，未产生 execution 的旧时点静默跳过，并将 `next_run_at` 推进到未来时点。
- 已创建 execution 但未能完成启动时，根据实际阶段记录 `failed_to_start`、`failed` 或其他明确状态；不自动重试。
- 已持久化的 Agent Run 在服务重启后仍由现有 Run 恢复机制处理，不为同一 execution 创建第二个 Run。

## 时间规则与时区

- 首版支持常用 UI 周期预设：每小时、每天、每周；高级模式支持五段 cron。
- 周期规则必须保留“本地墙钟时间 + IANA 时区”语义，例如每天 `09:00` 与 `Asia/Shanghai`。
- 前端默认按浏览器本地时区配置和回显；提交时将选定时区以 IANA 时区标识提交，而非只将 cron 换算为 UTC cron。
- 后端使用 cron 与 IANA 时区计算具体触发时刻；`next_run_at`、`scheduled_for`、开始和结束时间等具体时刻统一以 UTC 存储和传输。
- 前端展示 UTC 时间戳时转换为浏览器本地时间。
- 不能只存转换后的 UTC cron，否则夏令时地区的“每天本地固定时刻”语义会丢失。

## 建议的数据实体

### `scheduled_agent_task`

建议保存：

```text
id
workspace_id
name
enabled
trigger_mode                    # new_session | fork_message
prompt
schedule_expression
timezone
next_run_at
agent_id
provider_id
model_id
source_session_id               # fork_message 模式使用
source_message_id               # fork_message 模式使用
created_at
updated_at
```

- `workspace_id` 是任务的归属边界。
- Fork 模式的来源引用仅指向当前 Workspace 的不可变历史消息锚点，不引入模板 Session。

### `scheduled_agent_execution`

建议保存：

```text
id
task_id
scheduled_for
trigger_type                    # scheduled | manual
status
reason
session_id
run_id
created_at
started_at
finished_at
```

建议状态：

```text
starting
running
completed
failed
failed_to_start
skipped
```

- 自动触发记录应对 `(task_id, scheduled_for)` 建立唯一约束。
- `reason` 用于保存可诊断的跳过或启动失败原因，例如 `previous_execution_running`。
- execution 与任务定义分离，以支持去重、执行历史、失败诊断和关联 Session/Run 跳转。

## 执行流程

```text
扫描 enabled 且 next_run_at <= now 的任务
→ 在 SQLite 事务内判定同任务是否已有 starting/running execution
→ 创建 execution 或记录 skipped
→ 推进 task.next_run_at 到下一个未来时点
→ 按 trigger_mode 创建独立执行 Session
  ├─ new_session：创建新的 primary Session
  └─ fork_message：按不可变 source Message 锚点内部 Fork
→ 通过既有 SessionInteraction / RunLifecycle 发送 Prompt 并启动 Run
→ execution 关联 session_id、run_id 并进入 running
→ Run 进入终态后同步 execution 的完成、失败或取消结果
```

- 不得直接写入 `agent_run` 或绕过生命周期直接调用 Worker 入队能力。
- 必须继续走既有生命周期，以保留 Workspace 删除围栏、Session/Run 原子激活、Worker 入队补偿、取消和恢复语义。
- 创建 Session 或启动 Run 失败时，execution 记录为 `failed_to_start`，等待下一周期，不自动重试。

## Workspace 删除语义

- Workspace 删除时必须一并删除该 Workspace 的定时任务定义与执行历史。
- 删除过程中先建立既有 Workspace deleting fence，并停止该 Workspace 的后续定时调度。
- 正在运行的 Agent Run 继续交由现有 Workspace 删除流程收敛或取消。
- 在删除 Agent Run、Session、Message 等 Agent 数据之前，显式删除该 Workspace 的 `scheduled_agent_execution` 与 `scheduled_agent_task`，避免关联引用阻碍清理。
- 数据库外键可作为兜底，但业务删除流程仍需先完成调度停止和运行态收敛，防止删除过程中再次创建执行实例。

## 首版范围

- Workspace 内任务的创建、编辑、启用、暂停、删除和立即运行。
- 新建 Session 与历史 Message Fork 两种触发模式。
- cron / IANA 时区 / UTC 下一次执行时刻计算。
- 计划执行记录、跳过记录、启动失败记录与关联 Session/Run 的执行历史。
- API 进程内调度、SQLite 持久化与服务重启后的不补跑处理。
- Workspace 删除时的任务和执行历史清理。

## 非目标

首版不实现：

- Workspace 锁、同 Workspace 文件写入冲突预防、排队或 worktree 隔离。
- 同任务的 queue、replace、合并等重叠策略；仅采用运行中跳过。
- 自动重试、漏跑补偿、批量历史补跑。
- Redis、外部队列、分布式调度器或 n8n queue mode。
- RRULE、复杂日历规则、成本/Token 预算、连续失败自动暂停、通知与自动 PR。
- 从 tool call、tool result、reasoning part 精确 Fork，或工具操作重放。
