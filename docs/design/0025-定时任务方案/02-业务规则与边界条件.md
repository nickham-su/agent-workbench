## 时间与 UTC 规则

### 基础约定

- 所有 API 时间、数据库时间、`scheduled_for` 和 `next_run_at` 都必须使用 UTC epoch milliseconds；仅 Web 展示层转换为设备本地时间。
- 后端规则是保存瞬间依据浏览器当前 UTC offset 生成的**固定 UTC 周期**，不得保存 IANA 时区、Cron 或原始本地墙钟规则。
- 用户换时区或发生 DST 后，本地显示的时刻与星期可以偏移；不得尝试还原原设备的墙钟时间。
- 统一 weekday 编码：`0=周日`、`1=周一`、…、`6=周六`。UTC 规则、API、数据库 JSON 和前端本地编辑模型必须使用此编码。
- `minutesUtc`、`minutesOfDayUtc`、`slotsUtc` 必须升序、唯一、范围合法。相同 UTC 时刻只允许一个 slot。

### 单次提交的 local → UTC 规范算法

浏览器 `Date.getTimezoneOffset()` 的定义是 **UTC - local**，单位为分钟。例如 UTC+05:30 返回 `-330`，UTC-07:00 返回 `420`。一次表单提交必须只捕获一次：

```text
offset = new Date().getTimezoneOffset()
```

不得按各个未来日期分别读取 offset；那会把未来 DST 规则重新写入本应固定的 UTC 规则。

定义 `mod(a,n) = ((a % n) + n) % n`，`DAY=1440`。本地 `HH:mm` 转 `localMinute=60*HH+mm`。

| 类型 | 转换算法 |
|---|---|
| hourly | `minuteUtc = mod(localMinute + offset, 60)`；只保留分钟字段。 |
| daily | `minuteOfDayUtc = mod(localMinute + offset, DAY)`。 |
| weekly | `raw = localMinute + offset`；`dayDelta = floor(raw / DAY)`；`minuteOfDayUtc = mod(raw, DAY)`；`weekdayUtc = mod(weekdayLocal + dayDelta, 7)`；保存独立 `{ weekdayUtc, minuteOfDayUtc }`。 |

上述 hourly 公式是 daily 公式对小时取模；daily 本身不需要存 weekday。所有转换结果必须排序、去重、再提交。

必测向量：

| 本地输入 | offset | 转换结果 |
|---|---:|---|
| UTC+05:30，daily `00:15` | `-330` | `minutesOfDayUtc=[1125]`，即前一 UTC 日 `18:45`。 |
| UTC+05:45，weekly 周一 `00:15` | `-345` | `{ weekdayUtc:0, minuteOfDayUtc:1110 }`，即 UTC 周日 `18:30`。 |
| UTC-07:00，weekly 周六 `23:30` | `420` | `{ weekdayUtc:0, minuteOfDayUtc:390 }`，即 UTC 周日 `06:30`。 |
| UTC-07:00，hourly `00` | `420` | `minutesUtc=[0]`。 |

### UTC 结构、回显和预览

| 类型 | UTC 结构 | 校验 |
|---|---|---|
| `hourly` | `minutesUtc: number[]` | 每项 `0..59`，至少一项。 |
| `daily` | `minutesOfDayUtc: number[]` | 每项 `0..1439`，至少一项。 |
| `weekly` | `slotsUtc: { weekdayUtc, minuteOfDayUtc }[]` | weekday `0..6`、分钟 `0..1439`，至少一项，pair 唯一。 |

`weekly` 必须保存显式 slot，**不得**保存“UTC 星期集合 × UTC 时间集合”。跨日转换后使用笛卡尔积会产生用户从未配置的额外计划。

读取 weekly slots 时，前端以**当前一次渲染捕获的单一 offset**反解成 local `(weekday,time)` 并检查能否严格因式分解为“星期集合 × 共用时间集合”：

- 可以分解时，使用原型的星期多选和时间多选编辑器。
- 不可分解时，必须使用显式“星期 + 时间”成对编辑器；新增、修改、删除只影响一个 pair。
- 前端不得为沿用标准编辑器补出交叉组合，也不得静默丢弃 pair。
- 用户保存后，再按本次提交捕获的新 offset 整体转换为固定 UTC slots；这是有意的规则重写。

规则摘要使用该单一 offset 反解，因此它描述“当前设备的规则视图”。后续三次预览必须先由 UTC calculator 生成三个具体 instant，再用浏览器对**每个 instant 实际生效的时区规则**格式化；未来跨 DST 时，预览可以与固定-offset 摘要出现已接受的偏移。

### next-run 计算

- `next_run_at` 必须是严格大于计算基准 `nowMs` 的第一个 UTC instant。
- `nextRunAt(schedule, nowMs)` 必须是纯函数：输入已规范化 UTC schedule 和 `nowMs`，不得读取系统时钟、数据库或运行环境时区。
- UI 可复用纯函数作预览，但 API 返回的 `nextRunAt` 才是页面最终权威。
- 启用和从暂停恢复时，必须从服务端当前时刻重算第一个未来时点；不得补跑过去 slot。PUT 仅在规范化 UTC schedule 变化且 Task 已启用时重算，详见“暂停、编辑、删除竞态”。

## 自动调度与并发

### Scheduler 生命周期与扫描语义

Scheduler 必须有明确 phase：`starting` 与 `running`。

```text
Worker health-ready
→ Workspace 删除意图恢复及 fence 建立
→ 既有 Agent Run 恢复与终态对账
→ Scheduled execution/Run 对账
→ starting phase 首次扫描
→ running phase 周期扫描
```

- `starting` 首次扫描只将所有 `next_run_at <= now` 的 Task 直接推进到严格未来时点；不得写 execution、不得创建 Session/Run。这是停机漏跑策略。
- 首次扫描完成后才进入 `running`。`running` 的每次扫描对到期 Task 最多处理其当前持久化的**一个** `next_run_at`；不使用含糊的毫秒阈值区分“短暂延迟”。
- `running` 发现一个到期 `scheduled_for` 时，无论声明正常 execution 还是 `skipped`，都必须将 `next_run_at` 直接重算为严格晚于本次扫描捕获 `now` 的第一个未来 slot；该 slot 与未来 slot 之间错过的 slot 均静默跳过，不写 execution。
- 因此正常运行中某 tick 延迟仍会为当前持久化 `next_run_at` 声明一条记录；多 slot 长时间积压不会在一次扫描补出多条历史记录。

Scheduler 运行于 API 进程。单机单 API + SQLite 是首版前提，**不得**引入 Redis、外部队列、分布式锁或重型调度框架。tick 不得重入；SQLite 约束仍必须作为最终并发防线。

### 声明事务与重叠策略

对每个到期 Task，必须在一个 SQLite 事务内重新读取 Task、Workspace deleting 状态和当前 `next_run_at`，然后：

```text
确认 enabled=1 且 Workspace 未 deleting
→ 读取唯一的当前 scheduled_for=next_run_at
→ 检查同 Task 活动 execution
→ 插入 starting 或 skipped execution
→ 计算并写入 next_run_at=firstFuture(schedule, scanNow)
```

- 自动 execution 由 `(task_id, scheduled_for)` 的 scheduled partial unique index 兜底；两个 tick、重启扫描或未来多进程竞争不得产生两条记录。
- 同一 Task 的 `starting/running` 最多一条，由活动态 partial unique index 兜底。
- 写 execution、推进 `next_run_at`、同步 execution 状态都不得更新 Task 配置 `updated_at`。

| 条件 | 自动计划 | 立即运行 |
|---|---|---|
| 无活动 execution | 声明 `starting` 后编排。 | 持久化 `manual starting` 后尝试编排。 |
| 有 `starting/running` | 插入 `skipped`，`reason=previous_execution_running`；不建 Session/Run。 | 返回 `409 TASK_EXECUTION_ALREADY_ACTIVE`；不得创建 execution。 |
| 不同 Task 同时到期 | 可分别声明并行。 | 同左。 |

实际 Run 开始速度受 Worker concurrency 限制；调度器不得把它误报为同 Task 重叠，不得建立 Workspace 文件锁。

### 暂停、编辑、删除竞态

- 暂停必须写 `enabled=0,next_run_at=NULL`；不停止已编排/运行的 execution，且仍允许立即运行。
- 启用必须写 `enabled=1,next_run_at=firstFuture(schedule,now)`；暂停期间不得补跑。
- PUT 必须在同一事务内先把请求 schedule 规范化（排序、去重），再与当前持久化 schedule 做结构深度相等比较；不得以原始 JSON 字符串、数组顺序或客户端摘要判断是否变化。
- PUT 不直接修改 `enabled`。schedule 深度相等时，无论名称、Prompt、Agent、trigger mode、来源如何变化，都必须保留原 `next_run_at`，不得改变调度相位。
- schedule 不相等且 Task 已启用时，必须使用 PUT 事务捕获的服务端 `now` 写入 `firstFuture(newSchedule, now)`，替换旧 `next_run_at`。旧尚未声明 slot 从此废弃，不得产生 execution。
- Task 暂停时，无论 schedule 是否变化，`next_run_at` 必须保持 NULL；之后启用才按已保存的新规则和启用事务的 now 计算未来时点。
- 已声明 execution 必须使用声明时 `task_snapshot_json`，后续编辑不得改变其任务名、Prompt、Agent 或来源。
- 若 Scheduler 已先声明 execution，PUT 不得改变其 snapshot；若非 schedule PUT 先提交，原 `next_run_at` 保留，Scheduler 随后按新 Task 配置写该 slot 的 snapshot；若 schedule PUT 先提交，旧 slot 被新 `next_run_at` 替换。
- 删除遇到活动 execution 必须 `409 TASK_DELETE_EXECUTION_ACTIVE`；没有活动 execution 时同一事务删除 Task，execution 通过 `ON DELETE CASCADE` 删除。不得删除已创建的 Agent Session/Run。
- 事务提交后编排前，若 Workspace deleting fence 已建立，execution 必须 `failed_to_start/workspace_deleting`；Task 暂停或后续编辑不撤销已声明 execution。

## execution、Run 与轻量恢复

### 声明、预分配和幂等

首版不建设通用工作流引擎，不自动重发 Prompt，也不承诺外部副作用 exactly-once。但必须保证一个计划 slot 只有一个 execution，且 execution 不主动产生第二个 Run。

自动/手动非 skipped execution 声明时必须预分配 `session_id`、持久化完整 snapshot，并使用：

```text
clientRequestId = scheduled-execution:<executionId>
sessionTitle = buildScheduledExecutionSessionTitle(snapshot.taskName)
```

不能原样调用现有 `createPrimarySession()` 达到预分配，因为它当前自行生成 Session ID。Agent application 必须新增仅内部可用的受控接口：

- `createPrimarySessionWithExpectedId(...)`；
- `forkPrimarySessionFromHistoricalAnchorWithExpectedId(...)`。

它们必须复用 SessionInteraction/store 边界；scheduled-tasks 模块不得直写 `agent_session`，接口不得暴露为宽松公开 REST API。若同 ID 已存在，只有其 `workspaceId`、`kind=primary`、标题、fork 血缘（Fork 时）和声明输入均与该 execution 的预期值完全一致，才能当作幂等确认；ID 被不同 Session 占用必须 fail-close 为 `failed_to_start/session_id_conflict`。

### Task 名称与执行 Session 标题

`apps/api/src/modules/agent/session/session-title.ts` 的 `normalizeManualSessionTitle()` 是现有手动 Session 标题的权威行为。其规范化顺序必须保持不变：先将连续 JavaScript `\s` 空白压缩为一个普通空格，再 `trim()`；仅空白输入规范化后为空并被拒绝。因而 tab、LF、CR 及其他被 `\s` 匹配的空白会被规范化为空格，不是非法字符。空白压缩后仍存在的 `U+0000..U+001F`、`U+007F..U+009F` 控制字符必须以 `invalid_characters` 拒绝，例如 NUL、退格及不属于 `\s` 的控制字符。

该函数继续施加既有最终 50 长度上限。本功能只要求其长度计数明确使用 Unicode code point：若当前实现仍按 JavaScript 字符串的其他计数方式判断长度，实施必须在同一文件中升级为 code point 计数，并以兼容性测试锁定上述控制字符处理顺序；不得为定时任务收紧或改变现有手动 Session 标题的控制字符兼容语义。

后端必须在同一领域文件提供 `normalizeScheduledTaskName()`。它必须复用或抽取 `normalizeManualSessionTitle()` 所用的空白压缩和残留控制字符校验原语，禁止在 scheduled 模块复制一套顺序或语义不同的正则。该函数遵循相同的规范化与字符规则，但以 100 Unicode code points 为长度上限：

- 连续 `\s` 压缩为一个普通空格后再 trim；仅空白输入必须拒绝；
- tab、LF、CR 等被 `\s` 匹配的空白必须被压缩而非拒绝；
- 压缩后残留的 `U+0000..U+001F`、`U+007F..U+009F` 控制字符必须以 `invalid_characters` 拒绝；
- 以 Unicode code point 计数，最多 100；
- 将完整规范化名称写入 Task、execution snapshot 的 `taskName`、API 响应和列表/详情展示。

后端必须在 `session-title.ts` 增加权威函数 `buildScheduledExecutionSessionTitle(taskName)`；其参数必须是已经由 `normalizeScheduledTaskName()` 规范化并保存的 snapshot `taskName`，前端不得自行截断或拼接。函数必须按以下确定步骤执行：

```text
已规范化的 snapshot.taskName
→ 固定 suffix = " · 定时任务"（7 Unicode code points）
→ prefixCapacity = 50 - 7 = 43 code points
→ 取 taskName 的前 43 code points（不插入省略号）
→ prefix + suffix
→ 再调用 normalizeManualSessionTitle() 进行最终合法性与长度校验
```

expected-ID 创建/Fork 的幂等比较必须使用该函数返回的最终规范化标题。名称为 100 code points 时 snapshot 仍保存全部 100 个 code points，执行 Session 标题只保存确定性截断后的值。

### 状态与 Run 映射

状态为 `starting`、`running`、`completed`、`failed`、`cancelled`、`failed_to_start`、`skipped`。`starting` 必须允许直接收敛为 `completed/failed/cancelled`，以覆盖 Run 在回写前快速终态的恢复/对账。

| 当前状态 | 允许目标状态 | 约束 |
|---|---|---|
| `starting` | `running`、`completed`、`failed`、`cancelled`、`failed_to_start` | `completed/failed/cancelled` 只可由已持久化 Run 对账得出。 |
| `running` | `completed`、`failed`、`cancelled` | 必须以持久化 Run 终态为准。 |
| `completed`、`failed`、`cancelled`、`failed_to_start`、`skipped` | 无 | 终态不得回到活动态，也不得改为另一终态。 |

| 情形 | execution 状态与行为 |
|---|---|
| Run 尚未创建的前置失败：Agent/Fork/Session/Prompt 校验或创建失败 | `failed_to_start`。 |
| Run 已持久化，确定性 enqueue 拒绝，且可证明从未进入 work | `failed_to_start`。 |
| enqueue 返回 `AGENT_WORKER_ENQUEUE_UNKNOWN` 或无法证明 Worker 未接受 | 保持 `starting`，不得立即失败；按 `session_id + clientRequestId` 查找 Run 并对账。 |
| Worker 已进入 work 后 Run 失败 | `failed`。 |
| Run `completed` | `completed`。 |
| Run `cancelled` | `cancelled`，`reason=run_cancelled`。 |

**预分配 Session ID 冲突**：若同 Workspace 的无关 Session 占用了预分配 ID，execution 按 `failed_to_start/session_id_conflict` 收敛，不得启动 Run 或将该无关 Session 作为执行会话展示。公开 `sessionAvailable` 不能仅依据 Session ID 存在性；只有按 execution 的 `clientRequestId` 确认 Agent 的持久化 Run 归属（且已知 `runId` 一致）才可提供跳转。没有足够证据时即使 Session 存在也须禁用链接。

持久化 `agent_run` 是终态权威。当前 schema 已有 `status`、`execution_phase`、`intended_terminal_status`、`intended_terminal_code`、`intended_terminal_detail`、`terminal_result_code`、`terminal_result_detail` 等字段；分类适配层必须以这些持久化字段和“是否进入 work”的证据做判断。它必须将 `failed` 映射为：可证明从未进入 work 时 `failed_to_start`，否则 `failed`。不得虚构当前不存在的精确 result code；若现有字段不足，必须在 Agent lifecycle 边界新增稳定、受测的分类函数，而不是在 scheduled 模块猜测。

`AgentRunCompletedEventHub` 只能加速 UI/状态同步，不能作为唯一依据。每次启动恢复和周期扫描必须对账持久化 Run：

| 恢复发现 | 必须处理 |
|---|---|
| 有 `run_id` | 查询 Run，按上表收敛；不得建第二个 Run。 |
| 无 `run_id`，按 `session_id + clientRequestId` 找到 Run | 回写 `run_id` 并立即按 Run 收敛。 |
| 无 `run_id`，找不到 Run，陈旧 `starting` | `failed_to_start/startup_interrupted_before_run`；不得重发 Prompt。 |
| Session/Run 逻辑引用不存在 | 尚未启动则 `failed_to_start`；已有 Run 时按其最后持久化终态收敛；不得重建或猜测。 |

**缺失或冲突的已关联 Run**：execution 已存 `run_id`，或通过 `session_id + clientRequestId` 找到 Run ID，但 Run 记录缺失、归属不一致、两个引用冲突或查询异常时，不能仅凭数据库查询失败认定 Worker 没有接收或已停止。当前运行时接口不提供这一证明；首版在周期扫描和启动恢复后均保留 `starting/running` 及同任务活动互斥，按 execution ID 做限频安全诊断，不写猜测的终态、不重发 Prompt。仅当后续有可信 Run 事实时正常对账；解除无法恢复的活动记录需要另行受控处置，不得通过下一次调度绕过。

`skipped` 仅自动计划可产生，且 `session_id/run_id/started_at` 必须均为 NULL。其他状态均有预分配 `session_id`。所有终态必须写 `finished_at`；活动态 `finished_at` 必须为 NULL；`running` 及直接终态的已启动 Run 必须保留 `started_at`。

### 手动立即运行

- 手动 API 必须在启动尝试前事务内持久化 `manual starting` execution 和 snapshot；有活动 Task execution 时按上表 409 且不写记录。
- 启动成功或 enqueue unknown 时返回 `202 { execution }`。unknown 保持 `starting`，前端必须提示“已提交，正在确认运行状态”，不得提示确定失败。
- 同步可确定的前置/启动失败必须将 execution 收敛为 `failed_to_start`，HTTP 返回对应 4xx/503，并在标准安全 error details 中携带 `executionId`；历史必须保留该 execution。
- 立即运行不得改变 Task `next_run_at`，暂停 Task 也允许立即运行。

## Fork 历史消息锚点

### 来源成员关系算法

创建/PUT、`validate-source` 与每次执行前都必须重新做权威校验。来源 Session 必须是当前 Workspace 的 `primary` Session；算法不得读取其当前 `head`、`revision` 或空闲状态：

1. 若 `target.origin_session_id == sourceSessionId`，目标属于该 Session 的历史。这包括之后因 Revert 离开当前 head 的分支消息。
2. 否则，只有来源 Session 是由 Fork 产生，且 target 位于该 Session 固定 `forked_from_message_id` 的不可变祖先链中时，目标才属于它的继承历史；该祖先链可跨越更早 Session 的来源消息。
3. 任意同 Workspace 但不满足上述任一条件的 Message 必须拒绝；跨 Workspace 也必须拒绝且不得泄露信息。

从 target 的 immutable ancestry、context root、compaction retained anchors 推导上下文，不得读取来源当前 head。来源随后继续对话、Revert、Compaction 或正在运行不应影响仍可恢复的合法锚点。

### Fork 前置条件与失败

内部 Fork 必须创建新 primary Session，不修改来源 Session，不复制 Message、Part、Tool Execution 或上下文快照。除成员关系外，必须 fail-close 验证：

- target 是允许 Fork 的 `user` 或 `assistant` 终态消息；
- assistant target 不存在未完成 Tool Execution；
- 所需消息图无循环、断链或跨 Workspace 边；
- context root、compaction retained anchor 和所需历史内容均可解析。

任一失败写 `failed_to_start`，使用 `source_unavailable`、`source_anchor_invalid` 等稳定原因；不得回退到 current head、其他消息或空上下文。

## Agent、Workspace 与时间同步

- 每次触发必须重新解析 Task `agent_id` 的 user surface、Workspace enablement、默认模型、Provider/Model 和 API Key。失败必须 `failed_to_start`，不得自动暂停/删除 Task。
- Workspace 删除先建立 durable deleting fence。Scheduler 不得声明新 execution；现有删除流程收敛 Run 后，必须在删除 Agent 数据前显式删除 Task（execution 级联删除）。
- 服务端时间 API 仅返回当前 UTC instant，绝不返回服务器时区、API Key 或其他敏感信息。
- 前端记录 `t0`、`t1`、`rtt=t1-t0`、`offset=serverNow-(t0+t1)/2` 与最近成功时间；**固定每 30 秒**重新请求服务端时间。页面可见时每秒以最近成功同步基线推进服务端/设备显示；页面不可见时可以暂停每秒渲染和 30 秒请求。恢复可见时必须立即请求一次；该次成功后重置 30 秒周期，失败则保留既有 30 秒节奏并按下表归类。时钟和 interval 必须可注入测试。

| 条件 | 状态与文案 |
|---|---|
| `rtt <= 2000ms && abs(offset) < 60000ms` | `normal`；“时间同步正常”。 |
| `rtt <= 2000ms && abs(offset) >= 60000ms` | `warning`；“设备时间与服务端存在偏差”。 |
| `rtt > 2000ms` | `uncertain`；“网络延迟较高，时间偏差仅供参考”；不得显示正常。 |
| 请求失败，最近成功距今 `<120s` | `uncertain`；保留最后估算，显示“正在重新同步”。 |
| 从未成功，或最近成功距今 `>=120s` | `unavailable`；“时间同步不可用”。 |

定时任务只以服务端时钟和后端 `next_run_at` 为准，不以浏览器 offset 触发。
