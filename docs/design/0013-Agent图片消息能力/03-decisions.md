# 关键决策与取舍

返回 [README](./README.md)。本文件记录已裁决的设计选择、替代方案、指挥官意图对齐、已接受限制和未来触发条件。开发不得重新打开已经裁决的问题，除非产品前提或源码事实发生变化。

## 指挥官意图对齐

`AGENTS.md` 的“指挥官意图”明确：项目面向个人开发者、自托管 AI 开发闭环；在满足需求的前提下优先简单、直接、低成本、易部署和易维护；保护数据、工作区和运行状态；保持已验证的契约、事务和状态不变量；不为假设性未来需求引入重型一致性或分布式机制。

本方案的对应关系：

| 指挥官意图 | 本方案裁决 |
|---|---|
| 解决真实开发问题 | 直接支持粘贴截图交给 Agent，不要求先写 Workspace 文件 |
| 避免无效副作用 | 粘贴只本地暂存，发送时才上传 |
| 保持契约与状态不变量 | 纯文本 JSON 不变；消息、附件关系和 Run 在同一事务激活 |
| 保护工作区和数据 | 附件写入 `AWB_DATA_DIR` 独立目录，不污染 Workspace/Git；公共读取受控 |
| 选择更小改动 | 不做模型能力配置、历史图片重放、对象存储、缩略图或图片处理流水线 |
| 不提前分布式化 | V1 明确依赖 API/Worker 共享 `AWB_DATA_DIR` |
| 同一规则唯一权威 | Shared schema 负责协议；关系表负责附件引用；`triggerItemId` 负责原始 Run 判定 |
| 可验证和可回滚 | 多批实施，每批有测试、审查重点和回滚点 |

## 决策：粘贴阶段只保存在浏览器本地

### 选择

图片粘贴后只保存 `File` 对象，不上传；发送前可移除；刷新后丢失可接受。

### 原因

- 直接满足“避免上传无效图片”的产品目标；
- 不需要预上传 token、pending attachment、超时回收和孤儿附件管理；
- 移除是纯前端状态变更；
- 与文字草稿在发送前未提交的语义一致。

### 未选择

- 粘贴即上传：产生无效附件和清理负担；
- IndexedDB 持久化草稿图片：超出 V1 需求，增加容量和隐私边界；
- Base64 存入前端状态：额外内存与复制成本，没有收益。

## 决策：同一路径支持 JSON 与 multipart

### 选择

纯文本继续用 JSON；有图时同一 `/messages` 路径使用 multipart，`payload` 承载 JSON，`images` 为重复文件字段。

### 原因

- 消息语义仍是“发送一条用户消息”，不应拆成两套 endpoint；
- JSON 合同保持兼容；
- 单请求可以把消息接受和附件绑定收敛到一个业务边界；
- 应用层只处理规范化输入，不处理 HTTP 上传细节。

### 未选择

- 先上传再发消息：发送时仍需要两步，上传成功、消息失败会产生孤儿附件；
- `/messages-with-files`：长期形成重复 API；
- Base64 JSON：请求、日志、内存和 DB 风险更高。

## 决策：JSON `text` 必填，multipart `text` 可空

### 选择

保留现有 `AgentSendMessageRequestSchema` 的文本必填约束；新增 multipart payload schema。两者复用公共字段定义，路由后统一校验“文字或图片至少一个”。

### 原因

- 合法既有 JSON 调用不受影响；
- 仅图片消息不需要伪造文字；
- Shared contract 仍是权威；
- 避免路由和应用层各自维护一套字段规则。

## 决策：允许仅图片消息，标题回退为“新会话”

### 选择

允许空文字加图片。首条仅图片消息沿用当前 `toSessionTitleFromFirstMessage("")` 的 `新会话` 回退。

### 原因

- 用户可能只需发送截图；强迫输入无意义文字降低体验；
- 当前空文本标题已有明确、稳定的回退；
- 不引入 `图片消息` 等新的标题特例。

## 决策：图片只进入原始 Run

### 选择

只有 `agent_run.trigger_item_id` 对应的带图消息在该 Run 中产生附件引用。后续 Run 只收到原文字和固定英文占位。

### 原因

- 用户明确需求是发送图片，不是建设长期多模态记忆；
- 避免每轮重复传输历史图片和 Provider 成本；
- 避免旧图片让后续纯文本请求持续失败；
- 不需要历史图片预算、选择算法、能力状态、失败降级和 run 快照；
- 与当前 Compaction/Archive 的文本化语义一致；
- 后续可按真实需求增加显式“重新发送图片”，不必现在自动重放。

### 唯一权威

必须使用 `triggerItemId`。不得使用：

- 最后一条 user 消息；
- 最新可见消息；
- Session head；
- `item.runId` 的猜测；
- 前端传入的“当前附件”标志。

### 未选择

- 所有可见历史图片每轮重放：成本和失败面不可控；
- 历史预算内重放：引入消息原子选择、错误降级和可追溯性复杂度；
- 图片只展示不进入任何模型请求：不能满足核心功能。

## 决策：固定历史占位，不传不可信元数据

### 选择

后续 Run 的同一条 user 消息使用：

```text
[This user message included N image attachment(s). Their image contents are not included in this run.]
```

原文非空时追加在原文之后；原文为空时只保留占位。

### 原因

- 模型知道历史中存在图片，避免完全丢失语义；
- 固定英文模板不受 UI locale 和动态文案影响；
- 同一 user 消息内补充，不改变角色语义；
- 不传文件名、ID、哈希和路径，避免不可信输入污染与敏感信息泄露。

## 决策：提示只放图片预览，不使用列表 Tooltip

### 选择

会话列表只显示 icon 和数量；预览 Modal 中显示图片不会自动进入后续对话的说明。

### 原因

- 会话列表元素多，Tooltip 会增加实例、渲染负担和悬停干扰；
- 用户主动打开预览时，正处于理解图片语义的合适上下文；
- 列表保持轻量，不影响懒加载目标。

## 决策：不预判模型视觉能力

### 选择

不建设模型能力配置或探测；Provider 不支持时按现有运行失败路径反馈。

### 原因

- 当前模型配置没有能力字段；
- Provider 和 OpenAI-compatible 实现差异大，能力表容易失真；
- 用户接受低频运行时报错；
- 历史图片不自动重放，失败不会毒化后续纯文本会话。

### 未选择

- 模型能力矩阵；
- 动态探测与缓存；
- 自动切到 vision model；
- 跨 Provider 错误文本知识库。

### 边界

V1 不承诺专用图片错误码。不得用宽泛 `400/422/unsupported` 推断模型永久能力。

## 决策：独立附件存储，V1 共享 `AWB_DATA_DIR`

### 选择

附件位于 `AWB_DATA_DIR` 派生目录；API 和 Worker 共享数据目录。API 是附件元数据、关系和 Prompt 授权投影的唯一事实来源。内部 contract 只传 `workspaceId` 上下文与 `attachmentId/mediaType/filename` 引用；Worker 不查 SQLite、不调用内部附件 HTTP，通过可注入 `attachmentStorage`、统一安全路径 helper 和 `storageKey === attachmentId` 规则读取。

### 原因

- 不污染 Workspace 和 Git；
- 当前默认部署中 Worker 是 API 子进程，默认 Compose 同容器并共享数据卷；
- 比内部附件 HTTP 或对象存储更小；
- 传引用而非绝对路径，为未来替换存储保留契约稳定性；
- 可注入 storage 便于测试读取成功、缺失和越界。
- 只有 API 使用关系表与 `triggerItemId` 产生引用；Worker 只校验物理文件完整性，不自行做数据库授权。

### 未选择

- 写入 Workspace：生命周期和项目文件混合；
- Prompt 直接传绝对路径：内部协议耦合部署和物理布局；
- Prompt 传 Base64/bytes：内部 JSON 膨胀；
- V1 建设对象存储或内部下载 API：当前没有部署需求证据。

## 决策：关系表是唯一附件事实来源

### 选择

新增 `agent_attachment` 与 `agent_context_item_attachment`。公共 `user_message.attachments` 由关系查询投影；`output_json` 不保存附件 ID 列表。

### 原因

- 当前 `agent.store.ts` 已把 Context Item 的主要字段拆列，`output_json` 只是兼容路径；
- Fork 复制 Context Item，需要可靠复制关系；
- Workspace 删除和未来回收需要查询引用；
- 两份附件 ID 列表会漂移；
- 关系表可以用 FK、唯一位置和索引表达不变量。

### 未选择

- 只在 JSON 中保存附件：无法可靠查询和维护关系；
- 手工 `ref_count`：事务、Fork 和补偿时易漂移；
- 泛化资产库：超出消息附件需求。

## 决策：公共读取 `private, no-store`

### 选择

附件内容响应必须使用 `Cache-Control: private, no-store`。

### 原因

- 图片可能包含代码、凭证或用户私有数据；
- V1 没有权限版本、ETag 和附件撤销合同；
- Modal 生命周期内 Blob URL 已能避免同一次查看重复请求；
- 优先选择易审查的私有、无持久缓存策略。

### 未选择

- `private, max-age`：需要定义权限变化和删除后的缓存语义；
- 公开可缓存 URL/CDN：违反自托管数据边界；
- data URL 嵌入列表：破坏懒加载。

## 决策：V1 沿用现有幂等，不加请求指纹

### 选择

同 `clientRequestId` 仍返回第一次结果，不比较内容。

### 原因

- 这是当前纯文本已验证合同；
- 正常前端能保证新发送新 ID、网络重试旧 ID；
- 请求指纹需要流式哈希、schema 迁移、冲突合同和历史兼容；
- 当前没有相同 ID 错误复用的故障证据。

### 已接受限制

相同 ID 携带不同文字或图片时，服务端不会返回 409，而会去重到第一次结果。前端必须把发送尝试 ID 与草稿版本绑定：

- 请求结果明确成功后丢弃该 ID；
- 网络错误或 5xx 等“服务端是否接受不确定”的失败，草稿未变化时重试必须复用该 ID；
- 用户修改文字、粘贴或移除图片后，旧尝试 ID 必须失效，下一次发送生成新 ID；
- 明确的请求校验 4xx 后，修改输入再发送必须使用新 ID。

未来只有出现真实重复/错配故障时，才引入服务端 request fingerprint 和 409。

## 决策：只做字节和签名限制，不做像素解析

### 选择

V1 限制格式、数量、单张字节和总字节，校验签名；不解析像素与边长。

### 原因

- 当前仓库没有图片尺寸解析依赖；
- API/Worker V1 不做图片解码、压缩或转码；
- 增加完整 PNG/JPEG/WebP 尺寸解析或重型依赖超出当前故障证据；
- 字节限制已经控制上传和文件读取的主要资源边界。

### 已接受风险

小文件仍可能具有很高分辨率，Provider 可能拒绝，浏览器预览可能占用较多解码内存。未来触发条件：

- 出现可复现的高分辨率资源耗尽；
- Provider 分辨率拒绝成为常见失败；
- 引入服务端转码/缩略图；
- 产品要给发送前尺寸提示。

## 决策：轻量清理，不建设复杂 GC

### 选择

V1 实现：

- 请求失败清理 temp；
- DB 事务失败补偿删除已移动 final 文件；
- Workspace 删除清理附件记录并 best-effort 删除目录；
- 启动或现有维护入口清理超过宽限期的 temp。

不实现 attachment 状态机、ref_count、定时多阶段 GC 或跨节点协调。

### 已接受风险

进程在“final 文件已经移动、DB 尚未提交”的极窄窗口崩溃，可能留下无 DB 记录的 final 文件；V1 不扫描 final 目录做完整孤儿回收，该文件会在 Workspace 删除时清理。只有出现实际存储泄漏证据时才增加无引用 final 文件扫描。

## 决策：Fork 共享不可变二进制

### 选择

Fork 在复制 Context Item 的同一 SQLite 事务中复制关系行，新旧消息引用同一附件记录和物理文件。

### 原因

- 图片不可变，不需要复制 bytes；
- 避免存储倍增；
- 关系表能够表达多个 Context Item 引用；
- Clear/Archive 不等于删除，不应触发附件回收。

## 决策：已进入正常执行的原始 Run 每个实际 step 重新读取

### 选择

对于已经进入正常执行的原始 Run，Worker 每次拿到 Prompt Context 后将 attachment refs 物化为 bytes，不建立 Run 级 bytes 缓存；每个实际模型 step 和同一 Run 内部自动重试始终使用同一 trigger item 附件集合。本决策不表示所有启动恢复模式都读取附件，启动恢复只服从下节的条件化规则。

### 原因

- 每次 Run 最多 4 张、总计 20 MiB，边界明确；
- 避免缓存释放与并发内存状态；
- 每个 step 仍由相同 `triggerItemId` 产生同一引用集合；
- 读取失败必须显式失败，不能使用旧缓存掩盖文件问题。

## 决策：启动恢复服从现有 recovery mode

- 只有 `agentStartupRecoveryMode=recover` 且现有启动恢复流程继续该 Run 时，才保留同一 `runId`，并通过 `triggerItemId` 重新得到相同附件集合。
- `agentStartupRecoveryMode=fail` 时，按现有 fail-existing-runs 语义结束，不构建图片 Prompt、不调用 Worker storage、不读取附件。
- 除第一项条件成立外，启动恢复不得投影、物化或读取附件。
- 图片能力不得改变现有 recovery mode 的产品含义。

## 决策：附件物化失败不可重试

附件引用物化、路径校验和本地文件读取失败是本地确定性错误，不是 Provider 请求错误：

- 不调用 `streamText()`；
- 不进入模型请求自动重试；
- 直接走现有 Assistant/Run failed 收尾；
- 不静默丢弃 part；
- V1 不新增公共专用 error code，但内部错误/日志必须可诊断且不泄露绝对路径。

## 风险与应对

| 风险 | V1 应对 |
|---|---|
| Provider 不支持图片 | 运行失败但保留消息/附件；后续 Run 不自动带旧图 |
| Provider 私有限制更低 | 保持 Provider 错误；用户减少图片或重新发送 |
| 图片含敏感信息 | 独立受控存储、鉴权读取、no-store、日志不记录内容 |
| Multipart 资源滥用 | 路由级 parts/数量/单图/总量限制与流式终止 |
| 扩展名/MIME 伪造 | 服务端签名检测决定 mediaType |
| API/Worker 路径越界 | attachmentId 安全格式、DB storageKey、dataDir containment、可注入 storage |
| 附件物化/读取失败 | 本地确定性、不可重试；不调用 Provider，直接按现有 failed 收尾 |
| 历史列表流量 | 只返回元数据，点击后逐张 Blob |
| Fork 后附件误删 | 关系行复制，Clear/Archive/Revert 不删 |
| 物理文件丢失 | 原始 Run 或预览明确失败，不静默忽略 |
| 同 ID 内容错配 | 前端发送尝试管理；接受 V1 服务端不校验，按故障证据升级 |
| 高像素图片 | 接受 V1 限制；按真实资源/Provider故障升级尺寸解析 |
