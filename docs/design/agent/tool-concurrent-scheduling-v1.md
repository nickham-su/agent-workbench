# Agent 工具并发调度一期方案(v1)

## 背景 / 问题

- 当前 agent 运行时采用 context item + step-loop 模型,同一步 assistant 可以返回多个工具调用,worker 会先创建对应 `tool` context item,再执行工具.
- 现状实现以“逐条执行”为主,多个工具调用即使彼此独立,也会在 worker 中串行完成,导致总 wall-clock 时间被拉长.
- 串行执行对轻量工具影响不大,但对 `bash` 与 `subtask` 两类高耗时工具影响明显:
  - `bash` 的典型耗时场景包括测试、lint、类型检查、构建.
  - `subtask` 的典型耗时场景包括并发调研、并行拆分子问题后汇总.
- 如果为了支持并发而额外引入新的工具协议、context item 层级或前端结构,会把改动范围扩散到 API / Worker / Web 多处,一期实现成本偏高.

## 目标

- 在**不修改现有工具协议、context item 模型和前端结构**的前提下,提高 agent 工具执行阶段整体性能.
- 重点优化 `bash` 与 `subtask` 两类高耗时工具.
- 保持现有 step-loop、prompt 组装主结构、context item 展示方式不变.
- 将并发能力收敛为 **worker 调度层优化**,尽量不引入新的对外抽象.
- 保持失败可见且可追溯: 工具成功或失败都进入 context item,再由模型自行纠错与补救.

## 非目标

- 本期不新增 `parallel` 元工具.
- 本期不新增 `groupId`、`batchId`、额外并发元数据协议.
- 本期不新增外层 batch context item.
- 本期不调整 prompt 组装主结构,不在 `messages` 中新增并发调度语义字段.
- 本期不改前端结构与渲染层级,前端仍按既有 tool item 展示与刷新.
- 本期不做复杂冲突分析,例如文件级资源锁、命令依赖图、工作区冲突检测等.
- 本期不追求“并发零出错”; 允许并发执行失败,只要错误能完整反馈给模型即可.

## 用户 / 模型语义

### 对模型仅保留一条核心规则

> 同时返回多个工具调用 = 允许并发。

说明:

- 若多个工具调用彼此独立,模型可以在同一次回复中同时返回多个工具调用.
- 若工具调用之间存在依赖关系,模型不应同时返回,而应等待前序结果后再继续调用.
- 不向模型暴露任何运行时内部实现细节,包括但不限于:
  - 运行时是否会做分段.
  - 哪些工具会真正并发执行.
  - 并发上限是多少.
  - 是否会自动拆段或保守降级为串行.

### 语义边界

- 模型同时返回多个工具调用,表示它**允许运行时尽量并发**.
- 运行时保守降级为部分串行执行,**不违反模型意图**.
- 真正需要避免的是反方向的偏差: 模型本来保守串行,运行时却擅自激进并发.

## 总体方案

### 核心思路

- 对同一步 assistant 返回的多个工具调用,worker 视为一个待调度序列.
- 不改变 tool call 的外部协议与存储模型.
- 在 worker 内部根据工具类型做保守调度:
  - 仅 `bash` 与 `subtask` 参与真正并发执行.
  - 其他工具即使同一步同时返回,也按串行执行.
- 并发只是执行优化,不是新的对话语义或新的数据模型层级.

### 为什么只让 `bash` / `subtask` 真正并发

- 这两类工具往往是工具阶段的主要耗时来源,并发收益最明显.
- 其他工具通常较轻量或与工作区改动更直接,第一版即使保持串行,也仍可通过“同一步同时返回多个调用”减少模型往返与 token 消耗.
- 一期先聚焦高收益路径,避免把并发范围扩展到过多工具类型后增加调度复杂度.

## 调度规则

## 待调度序列

- 同一步 assistant 结束后,worker 已获得该 step 的工具调用列表.
- 这些工具调用按模型原始返回顺序形成一个待调度序列.
- 工具 context item 仍按既有方式创建,保留现有顺序语义与 prompt 组装基础.

## 分段规则

worker 按原始顺序扫描待调度序列:

- 连续出现的 `bash` / `subtask` 构成一个**并发段**.
- `bash` 与 `subtask` 各自独立成段,彼此互相打断.
- 遇到其他工具时:
  - 该工具单独形成一个**串行段**.
  - 同时打断当前并发段.
- 段与段之间严格串行执行.

示例:

```text
read -> bash -> bash -> write -> subtask -> bash -> subtask -> apply_patch
```

切分后:

```text
[read]
[bash, bash]
[write]
[subtask]
[bash]
[subtask]
[apply_patch]
```

其中:

- `[bash, bash]`、`[subtask]`、`[bash]` 为并发段.
- `[read]`、`[write]`、`[apply_patch]` 为串行段.

## 分段上限

- 并发段采用统一上限: `3`.
- 当连续的 `bash` / `subtask` 数量超过上限时,自动拆成多个并发段依次执行.
- 超过上限时:
  - 不报错.
  - 不让当前 step 失败.
  - 不要求模型重试或重组调用.

示例:

```text
bash1 -> bash2 -> bash3 -> bash4 -> subtask1 -> subtask2 -> subtask3 -> subtask4
```

若上限为 3,则拆为:

```text
[bash1, bash2, bash3]
[bash4]
[subtask1, subtask2, subtask3]
[subtask4]
```

## 执行策略

- 并发段内部采用 `allSettled` 语义执行.
- 串行段继续沿用单工具执行路径.
- 并发段完成后再进入下一段.
- 所有段执行完成后,才进入下一次模型调用.

## 错误处理

### 单工具失败

- 单个工具失败只影响该工具本身.
- 不取消同段内其他工具.
- 不阻断后续段执行.

### 并发段失败语义

- 并发段不是新的持久化实体,无需单独落库“段状态”.
- 段内每个工具仍独立维护自己的 `queued -> running -> completed|failed` 状态流转.
- 并发段的完成条件是该段所有工具都已收敛到终态.

### 结果回写

- 所有成功结果与失败结果都按现有方式写回各自的 context item.
- 后续 prompt 仍按既有 tool result 组装逻辑进入上下文.
- 模型可基于成功与失败结果自行判断是否需要重试、补救、回退或改用串行策略.

### 设计取舍

- 本方案接受并发执行中的失败,前提是错误信息完整、可诊断、可被模型消费.
- 收益优先于“并发零失败”,不在一期引入复杂冲突分析或强约束阻断.

## 对现有架构的影响

## 不变部分

以下结构保持不变:

- 现有 AI SDK native tools 协议.
- context item 模型与 `agent_context_item` 主表结构.
- tool item 的创建方式与主链顺序.
- prompt `messages` 主结构与 tool result 组装方式.
- 前端对 tool item 的展示、轮询与刷新逻辑.
- 现有 artifact / 日志按单工具项归档的方式.

## 变更集中点

本期改动主要集中在 worker 调度层:

- `runModelStep()` 之后,`executePendingTools()` 的执行方式从“逐条执行”调整为“按段调度”.
- `executeTool()` 的单工具执行逻辑尽量复用现有实现.
- 对 API / DB / Web 侧的改动应控制为零或接近零.

## 与既有 step-loop 设计的关系

- 现有设计是“先记录 tool item,再执行”.
- 本方案不改变“先记录后执行”的大原则.
- 仅改变“执行阶段如何调度已创建的多个 tool item”.
- 因此这是对现有 step-loop 的**局部增强**,而不是新的运行时模型.

## 实现要点

## Worker 调度入口

建议在现有 `executePendingTools()` 附近完成以下改造:

1. 保持 pending tool 的收集逻辑不变.
2. 将当前 step 的 pending tools 视为一个有序序列.
3. 扫描序列并生成执行段:
   - 连续同类的 `bash` 或 `subtask` -> 并发段.
   - 其他工具 -> 串行段.
4. 对并发段按上限 `3` 自动拆段.
5. 逐段执行:
   - 并发段走 `allSettled`.
   - 串行段走原有单工具路径.
6. 全部段执行完后,再继续主 loop.

## 工具顺序语义

- tool item 仍按模型声明顺序创建.
- prompt 仍按 item 顺序回放 `tool-call` 与 `tool-result`.
- 实际完成先后顺序不影响上下文重建顺序.

## 可观测性

- 即使并发执行,每个工具仍保留自己的状态更新、输出文本、artifact 与 debug log.
- 无需为并发段新增独立 UI 或新的 context item 类型.
- 如需调试并发调度,建议仅在 worker debug log 中补充“本次 step 的分段结果”,不进入对外协议.

## 兼容性

- 由于不新增元工具与元数据协议,旧的 prompt / tool schema / 前端消费逻辑无需感知并发能力.
- 即使未来关闭并发调度,也可以平滑退回逐条执行,不影响会话数据兼容性.

## 测试建议

## 单测

建议优先覆盖 worker 调度层的纯逻辑与执行行为:

### 分段逻辑

- 连续 `bash` 构成并发段.
- 连续 `subtask` 构成并发段.
- `bash -> subtask` 会拆成两个并发段.
- `subtask -> bash` 会拆成两个并发段.
- 非并发工具会打断并发段.
- 超过上限 `3` 时会自动拆成多个段.

### 执行行为

- 并发段内部多个工具会被并发启动.
- 串行段不会被并发调度.
- 并发段中一个工具失败,其他工具仍会继续执行并落库.
- 段与段之间保持顺序执行.

### 回归行为

- 只有一个工具调用时,行为与当前实现一致.
- 同一步多工具但都不是 `bash/subtask` 时,行为与当前实现一致.
- tool item 的最终状态、输出文本、artifact 路径与既有语义兼容.

## 集成验证

建议补充最小集成场景:

1. 同一步返回两个 `bash`,验证总耗时接近二者最大值而不是累加值.
2. 同一步返回两个 `subtask`,验证二者可并发收敛并分别写回结果.
3. 同一步返回 `bash + subtask + write`,验证 `bash` 与 `subtask` 会拆为两个并发段,`write` 在后续段串行执行.
4. 同一步返回超过 3 个 `bash/subtask`,验证自动拆段且不报错.
5. 并发段中部分工具失败,验证后续模型可收到失败结果并继续补救.

## 风险

## 运行时资源占用上升

- 并发 `bash` 与 `subtask` 会提高 CPU、IO、模型请求或子任务执行的瞬时并发度.
- 统一上限 `3` 的目的就是限制这一增长,避免一次 step 内吃光系统资源.

## 并发失败率上升

- 相比完全串行,并发执行更容易暴露隐藏的环境依赖、命令竞争或子任务资源争用问题.
- 本方案接受这类风险,只要求错误结果能够被完整记录并反馈给模型.

## 调试复杂度增加

- 单步内多个工具可能同时进入 `running`,日志时间线比串行更复杂.
- 但由于不引入新协议或新层级,复杂度仍主要局限在 worker 内部.

## 后续演进

### 可演进方向

- 调整并发段上限,例如按环境或配置动态设置.
- 将可真正并发执行的工具范围扩展到更多类型.
- 为 worker 调度增加更丰富的 debug 可视化与统计指标.
- 在后续版本中引入更细粒度的并发控制,例如资源锁、冲突探测或按工具类型分别限流.

### 明确延期到后续版本的内容

- 并发元工具/显式 batch 协议.
- group 级元数据与持久化.
- prompt 中显式回灌并发组语义.
- 前端并发批次可视化.
- 复杂冲突分析与自动规避.

## 小结

- 一期方案选择最小侵入路径: **不改协议、不改存储、不改前端,只增强 worker 调度**.
- 对模型只保留一条极简语义: **同时返回多个工具调用 = 允许并发**.
- 对运行时则采用保守实现: **仅 `bash` / `subtask` 真正并发,其余工具仍可同一步返回但按串行执行**.
- 通过“并发段 + 串行段 + 统一上限 3 + 自动拆段 + allSettled”,在可控范围内拿到最主要的并发收益.
