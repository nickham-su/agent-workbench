# 接口、数据与不变量

## 接口草案的适用规则

本章 TypeScript 是职责与不变量草案，不要求逐字符照搬。最终实现可按既有文件组织、类型别名、依赖注入风格微调，但不得：

- 让 Adapter 获得数据库或 API 写入能力；
- 让 Adapter 覆盖 Runner 的模型、工具、超时、abort 或重试控制；
- 绕开共享的状态更新兼容性校验；
- 将私有 state 并入 Provider-neutral `messages`；
- 放宽失败后禁止 `completeAssistant` 的规则；
- 绕开 [08-PhaseC协议快照与完整性闭环.md](./08-PhaseC协议快照与完整性闭环.md) 的快照与 terminal completion 规则。

### 当前类型来源与输入只读性

- 当前 Worker 中 `ExecutionProfile` 是 `apps/agent-worker/src/runtime/apiClient.ts` 对内部 `AgentApiExecutionProfileResponse` 的类型别名；其 `model` 是 API 最终解析后的模型，包含 Session 模型覆盖结果。
- 当前 `PromptContext` 同样是 `apiClient.ts` 对 `AgentApiPromptContextResponse` 的别名；`messages` 与 `providerReplay` 来自 `packages/shared/src/internal-contracts/agent-api-read.ts`。
- Phase C 在私有 PromptContext 增加 state source/diagnostics 时，不得把它们加入公开 Message、Timeline、Archive 或 messages-context schema。
- Adapter 不得修改 `context`、`context.messages`、`context.providerReplay`、profile 或传入 options。接口输入必须以 `Readonly`、只读数组或防御性复制表达；输出必须为新对象/新数组。

## 核心接口草案

```ts
import type { JSONValue, ModelMessage } from "ai";

// 仅由 Adapter 选择结果表达；没有适配器时为 null，不伪造 "noop" protocol。
type ProviderConversationStateProtocol =
  | "openai-responses"
  | "deepseek-chat-thinking";

type ToolsDisposition = "omitted" | "present-non-empty";

type ProviderReplaySource = Readonly<{
  entries: readonly AgentApiPromptProviderReplaySource[];
  diagnostics: readonly ProviderConversationStateDiagnostic[];
}>;

type PreparedProviderInvocation = Readonly<{
  messages: readonly ModelMessage[];
  providerOptions: Readonly<Record<string, JSONValue>>;
  directives: Readonly<{
    includeRawChunks?: boolean;
  }>;
}>;

type ProviderProtocolValidation =
  | { ok: true }
  | {
      ok: false;
      code: string;
      message: string; // 只允许安全摘要
      classification: "TransientProtocol" | "TerminalProtocol" | "Invariant";
      retryable: boolean;
    };

type OpenAiInvocationInput = Readonly<{
  protocol: "openai-responses";
  profile: Readonly<ExecutionProfile>;
  messages: readonly ModelMessage[];
  history: ProviderReplaySource;
  providerOptions: Readonly<Record<string, JSONValue>>;
}>;

type DeepSeekInvocationInput = Readonly<{
  protocol: "deepseek-chat-thinking";
  profile: Readonly<ExecutionProfile>;
  messages: readonly ModelMessage[];
  history: ProviderReplaySource;
  providerOptions: Readonly<Record<string, JSONValue>>;
  toolsDisposition: ToolsDisposition;
}>;

type ProviderInvocationInput = OpenAiInvocationInput | DeepSeekInvocationInput;

interface ProviderConversationStateAdapter {
  readonly protocol: ProviderConversationStateProtocol;

  prepareInvocation(input: ProviderInvocationInput): PreparedProviderInvocation;

  createAttempt(input: Readonly<{
    protocol: ProviderConversationStateProtocol;
    profile: Readonly<ExecutionProfile>;
    // 仅 DeepSeek Attempt 接收此字段；OpenAI 不构造虚假的 omitted 工具事实。
    deepseek?: Readonly<{ toolsDisposition: ToolsDisposition }>;
  }>): ProviderConversationStateAttempt;
}

interface ProviderConversationStateAttempt {
  observeChunk(chunk: unknown): Readonly<{
    updates: readonly ProviderConversationStateUpdate[];
  }>;

  finalizeAttempt(): ProviderProtocolValidation;
}
```

### 按协议判别的输入规则

- OpenAI Adapter 只接收 `OpenAiInvocationInput`，不接收 `toolsDisposition`，Phase A 不得构造虚假的 `"omitted"`。
- DeepSeek Adapter 只接收 `DeepSeekInvocationInput`，必须依据同一次最终 `streamText()` 请求的 toolSet 快照派生 `toolsDisposition`。
- TypeScript 最终可使用函数重载、discriminated union 或两个 Adapter-specific 接口实现；必须保留“OpenAI 无工具事实、DeepSeek 必须有工具事实”的类型级区分。

### Registry 草案

```ts
interface ProviderConversationStateAdapterRegistry {
  select(profile: Readonly<ExecutionProfile>): ProviderConversationStateAdapter | null;
}
```

选择规则：

- 官方 `@ai-sdk/openai` 的固定 Responses 路径返回 OpenAI Adapter。
- 默认 Compatible、Anthropic 以及没有状态协议的调用返回 `null`，而不是 Noop Adapter；`null` 表示不存在 Provider Conversation State 协议。
- 最终模型 `options.protocolAdapter === "deepseek-chat-thinking"` 时返回 DeepSeek Adapter，且只能与 `@ai-sdk/openai-compatible` 组合。
- Registry 不得让多个 Adapter 通过模糊 `matches()` 竞争；必须使用最终 profile 的确定协议键。
- 非默认协议无 Adapter 时抛出 Configuration 错误；不得退回 `null` 或默认行为。

### Update 草案

```ts
type ProviderConversationStateUpdate =
  | {
      target: {
        kind: "stream-part";
        id: string;
        partType: "text" | "reasoning";
      };
      envelope: ProviderConversationStateEnvelope;
    }
  | {
      target: {
        kind: "tool-call";
        providerToolCallId: string;
      };
      envelope: ProviderConversationStateEnvelope;
    };
```

规则：

- Update 只“建议将哪个私有 envelope 附着到哪个既有 Part”，不携带 position 创建指令。
- Runner 必须先确认 target 存在、Part 类型匹配、tool-call ID 匹配，才可应用。
- metadata-only update 合法，适用于 OpenAI terminal event 的 final-only 密文和 DeepSeek finish 后的 completion metadata。
- 一个已存在的 Part 收到不兼容 update 时必须抛出 Invariant 错误，不得以最后写入为准。

### 不变量错误草案

```ts
class ProviderConversationStateInvariantError extends Error {
  readonly classification = "Invariant";
  readonly retryable = false;
}
```

应统一归类为此错误的情况包括：

- 同一 stream part ID 类型从 text 变 reasoning 或反向变化；
- Provider 请求给已结束的旧 Part 追加 delta，导致需要重排 position；
- metadata 指向不存在或类型不符的 Part；
- Provider 原生 item identity 变化；
- tool-call replay identity 与 AI SDK `toolCallId` 不一致；
- 已确定的版本化字段被修改或回退为未知；
- Adapter 返回不属于选定协议的 Envelope；
- shared `assertProviderConversationStateUpdateCompatible()` 拒绝更新；
- DeepSeek 对同一 Part 在完成后尝试变更 `contentSource` 或 `completion`。

此类错误不得自动 retry，因为重试无法修复本地状态与 Provider 数据的矛盾。

## 数据实体与兼容策略

### Phase A：保持现有持久化契约

以下内容在 OpenAI 等价迁移阶段不改名、不迁移、不改变 JSON：

- SQLite：`agent_message_part.provider_replay_json`；
- 内部 PromptContext：`providerReplay`；
- shared contract：`AgentProviderReplayEnvelope`；
- 现有 OpenAI Envelope：`version: 1`、`provider.npm`、`provider.api`、`providerId`、`model` 与 item union。

这是有意的兼容策略：概念上使用 “Provider Conversation State”，不等于必须制造无业务收益的数据库迁移。

### Phase C：快照迁移与 DeepSeek 判别联合

Phase C **必须**实施 v21 → v22 的 `agent_message.provider_protocol_snapshot_json` 非破坏性迁移；快照语义、事务、回滚和旧历史策略以 [08-PhaseC协议快照与完整性闭环.md](./08-PhaseC协议快照与完整性闭环.md) 为准。

现有 OpenAI Envelope：

```ts
type OpenAiResponsesStateEnvelopeV1 = {
  version: 1;
  provider: {
    npm: "@ai-sdk/openai";
    api: "responses";
    providerId: string;
    model: string;
  };
  item:
    | { type: "reasoning"; itemId: string; encryptedContent: string; summaryIndex?: number }
    | { type: "text"; itemId: string; phase?: "commentary" | "final_answer" }
    | { type: "function_call"; itemId: string };
};
```

DeepSeek Envelope：

```ts
type DeepSeekThinkingStateEnvelopeV1 = {
  version: 1;
  provider: {
    npm: "@ai-sdk/openai-compatible";
    protocol: "deepseek-chat-thinking";
    providerId: string;
    model: string;
  };
  item: {
    type: "reasoning";
    contentSource: "reasoning-part-text-v1";
    completion: "complete-v1";
  };
};

type ProviderConversationStateEnvelope =
  | OpenAiResponsesStateEnvelopeV1
  | DeepSeekThinkingStateEnvelopeV1;
```

- DeepSeek replay payload 是关联 Assistant reasoning Part.`text`，Envelope 不得重复保存 `reasoningContent` 原文。
- `completion: "complete-v1"` 只能由 DeepSeek Attempt 观察到 allowlist finish 后写入；`reasoning-end` 不足以写入。
- 如真实 AI SDK mock SSE 不能证明 delta 拼接文本等于完整 `reasoning_content`，Phase C 必须停止并另立私有实体/锚点设计，不得静默回放摘要或部分文本。

### 状态诊断与损坏策略

现有 OpenAI `parseAgentProviderReplay()` 对损坏/未知数据返回 `null`，Phase A 必须保持该容错读取行为。Phase C 的私有 read-side/PromptContext 必须返回成功条目、Message protocol snapshot 与**不含原始 JSON**的诊断。

建议最小诊断：

```ts
type ProviderConversationStateDiagnostic = {
  messageId: string;
  partId: string | null;
  position: number | null;
  classification:
    | "invalid-json"
    | "unsupported-version"
    | "schema-invalid"
    | "missing-required-metadata"
    | "missing-reasoning-text"
    | "incomplete-reasoning-text";
  protocol?: string;
  providerId?: string;
  model?: string;
};
```

分层行为：

| 数据情况 | OpenAI Phase A | DeepSeek experimental |
|---|---|---|
| 合法但协议/Provider/模型不匹配 | 正常跳过 | 正常跳过 |
| 不可解析、未知版本或 schema 非法，且无法安全识别目标协议 | 保持现有安全跳过 | 正常跳过；不能凭损坏原文猜测它属于 DeepSeek |
| v22 snapshot 明确为匹配 DeepSeek、scope 内 reasoning Part 的 Envelope 整体缺失 | 不适用 | `missing-required-metadata`，请求前 Configuration fail closed |
| 匹配 DeepSeek 的 Envelope 缺 `contentSource` / `completion` 或必要 identity | 不适用 | 请求前 fail closed |
| 匹配 DeepSeek 的 reasoning Part text 缺失、为空或未完成 | 不适用 | 请求前 fail closed |
| 合法且匹配 | 消费 | 消费 |

已 completed 的旧 `NULL` snapshot 不属于 DeepSeek 强保证范围：不得猜测为 DeepSeek，也不得作为 DeepSeek replay source；它不阻塞普通 transcript/read-side 读取。

升级时仍为 active Run 的 v21 streaming Assistant 若为 `NULL` snapshot，则不是普通历史兼容分支：recovery 必须不发 Provider 请求、不从 settings 补写，并经 fenced fail-converge 收敛为非 running。详细矩阵见 08。

### 异构历史与新写入

- 同一有效消息链允许混合多协议历史；读取时不删除非当前协议记录。
- 新写入必须严格拒绝非法 Envelope；读侧容错不等于写侧宽松。
- 损坏数据不会自动“修复”、覆盖或删除；如需运维修复，应另行设计。

## 更新兼容性的唯一权威

共享内部契约层必须提供唯一函数，例如：

```ts
assertProviderConversationStateUpdateCompatible(previous, next)
```

Adapter、Runner 和 Store 不得各写一套等价规则。职责分配：

| 层 | 职责 |
|---|---|
| Adapter | 根据 chunk 产生候选 Envelope/Update |
| Runner | 确认 Update 目标存在、Part 类型、顺序和 tool-call 身份 |
| shared contract | 判断两份 Envelope 是否允许增量更新 |
| Store | 持久化前再次调用 shared contract，防御 Worker/API 边界错误 |

OpenAI 兼容性规则必须维持：

- version、Provider npm/api、providerId、model、item type、itemId 一旦确定不可变；
- `summaryIndex` 与 text `phase` 只允许 unknown → known 或 known → 相同；
- 已知字段不得改值或回退为 unknown；
- reasoning 的 encrypted content 可由终态事件补齐或更新；
- 任何不符合上述规则的更新失败关闭。

DeepSeek 兼容性规则：protocol/providerId/model/item type/contentSource/completion 一旦确定不可变；`completion` 不允许 absent → complete 之外的任意值，也不允许 complete → absent。新 DeepSeek reasoning Part 在 allowlist finish 前不写 Envelope，因此 completion 的首写是 terminal metadata update。

## 状态来源、位置与可见索引

- SQLite Part 的 `position` 是 Assistant 内部输出顺序的唯一权威，必须保持唯一且不可重排。
- 普通 transcript 投影跳过 reasoning；私有 replay source 通过 `assistantOrdinal + visibleIndex` 表示 OpenAI reasoning 应插入对应 Assistant 可见 part 前的位置。
- DeepSeek Adapter 必须从同一有效 Assistant 的 `position` 有序 reasoning Parts 读取可见 payload，并仅使用 v22 snapshot 匹配、scope 内、Envelope completion 完整且 diagnostics 完好的条目。
- reasoning 不递增 OpenAI `visibleIndex`，text 和 tool-call 递增；同一 visible index 的多个 reasoning 以 Part.position 保持顺序。
- replay-only Assistant（无可见文本/工具调用但有有效 OpenAI reasoning state）必须以空 Assistant 占位保留，且仅限 completed Assistant。
- non-completed Assistant、pending tool Assistant、已 superseded 分支均不得进入 state source。
