# 需求与产品语义

## 需求背景

当前 Agent 使用完整、当前有效的消息历史调用模型。对官方 OpenAI Responses API，模型回复中存在不能作为普通文本处理的 Provider 状态：加密 reasoning、原生 text item 身份、function-call item 身份以及终态状态。0019 已实现如下方式：

```text
普通 transcript
  + 私有 providerReplay
  → Worker 在调用前按 OpenAI profile 注入
  → 最终 AI SDK messages
```

该设计已经满足以下关键业务语义：

- 完整 transcript 是每次调用的基线，不依赖 `previous_response_id` 或服务端 conversation 引用链。
- OpenAI encrypted reasoning 是不透明敏感数据，只作为后续同一兼容 Provider 会话的回放输入。
- failed、cancelled、superseded、未完成或本地提交失败的 Assistant 不能成为后续回放来源。
- compaction、普通 single-call、公开 read-side 不接收私有 replay。

近期将接入 DeepSeek Thinking 及其他需要回传 reasoning 或原生对话状态的 Provider。若继续把每个协议分散写入 Runner，会造成协议判断、流式采集、终态校验和请求物化规则不断堆积。因此需要在**不破坏现有隔离**的前提下提取轻量适配边界。

## 问题定义

本设计解决的问题不是“让所有模型都看到 reasoning 文本”，而是：

> 对于有 Provider 专属对话续接协议的模型，如何安全保存、严格匹配、按本次实际调用条件物化并验证私有状态，同时不污染通用消息、公开接口和非目标调用路径。

Provider 的续接状态可能包括：

- OpenAI Responses 的加密 reasoning 和原生 item identity；
- DeepSeek Thinking 的 `reasoning_content` 的协议匹配 metadata；
- 未来 Provider 规定必须回传的其他版本化、不透明或敏感字段。

这里必须区分“可见 reasoning 文本”和“私有协议状态”：DeepSeek 第一版将完整 reasoning 文本作为既有 Assistant reasoning part 的 `text` 保存并展示；但与何种协议、Provider/模型匹配、是否完整可回放相关的 metadata 仍不是普通 transcript 语义，必须独立保存。

## 术语

| 术语 | 定义 | 是否可公开 |
|---|---|---:|
| 普通 transcript | 用户文本、System、Assistant 可见文本、工具调用和工具结果构成的 Provider-neutral 历史 | 可以，遵循既有消息权限 |
| Provider Conversation State | 供特定 Provider 协议续接的私有、版本化 metadata；当前存储字段仍名为 `providerReplay` | 不可以 |
| Envelope | 经过 TypeBox 严格校验、白名单化的单个 Provider 状态对象 | 不可以 |
| 有效模型上下文 | 由 ModelContext Resolver 解析出的当前动态上下文；0020 启用后可包含摘要 S、retained tail B 与摘要后消息，不等同于完整 Timeline | 视内容而定 |
| 物化 | 根据当前 profile 和调用条件，把兼容私有 state 和其关联的可见 Part 组合为最终 AI SDK 入参 | 仅 Worker 内部 |
| Adapter | `ProviderConversationStateAdapter`；只实现 Provider 的对话续接协议 | 内部 |
| Attempt | 一次真实 `streamText()` 请求及其独立临时协议状态；重试必须新建 | 内部 |
| 可见 reasoning | 已持久化在 Assistant reasoning part.`text` 中、可由当前消息 UI 展示的文本 | 是；受既有消息可见性规则约束 |
| 最终 AI SDK 入参投影 | 供 debug 使用的、严格脱敏且可截断的结构化摘要；不是 HTTP body | 仅本地 debug |
| toolsDisposition | 同一请求最终 `toolSet` 的发送事实：`"omitted"` 或 `"present-non-empty"` | 内部 |

## 产品与业务规则

### 普通 transcript 与私有状态

- `context.messages` 必须保持 Provider-neutral；它不携带 OpenAI 密文、任意 provider options 或私有 Envelope。
- 私有 state 必须通过 `context.providerReplay` 独立传输；本设计概念上称为 Provider Conversation State，但 Phase A 保留当前字段名和 JSON 形状。
- 公共消息模型中的 reasoning part 只能包含产品允许展示的文本，不得含 OpenAI 密文、原始 Provider metadata 或任意 provider options。
- 任何调用方若不显式取得 `providerReplay`，默认不应看见私有 state。

### DeepSeek 第一版的明确产品决策

DeepSeek Thinking 的 `reasoning_content` 与 OpenAI encrypted reasoning 不同：它是明文，第一版**有意作为可见 reasoning 展示，并持久化到既有 Assistant reasoning part.`text`**。这与当前 Compatible Provider 的 reasoning 展示语义一致。

- DeepSeek `provider_replay_json` 不重复保存 reasoning 原文；仅保存严格白名单的协议、Provider ID、最终模型、版本及回放匹配所需 metadata。
- DeepSeek 回放时，从已匹配的同一 reasoning Part.`text` 取得 payload，物化为 AI SDK reasoning part。
- 这会使完整 DeepSeek reasoning 进入当前 Agent 消息的既有可见面，包括 UI 及公开消息 read-side 已有的 reasoning 展示路径。它不是加密内容，不能承诺与 OpenAI 相同的私有性。
- 因此产品、隐私和用户告知层面必须明确：启用 experimental DeepSeek Thinking 会保存并展示 Provider 返回的明文 reasoning。不得将其表述为“内部推理绝不展示”。
- debug 仍不应完整重复 dump 这段文本，详见 [05-失败矩阵日志与安全.md](./05-失败矩阵日志与安全.md)。
- 未来如需隐藏 DeepSeek reasoning，属于独立的产品与数据模型变更：需要新增私有实体/锚点、迁移与 read-side 策略；不得在本方案中半隐藏、半复用 `part.text`。

DeepSeek 的“可见”不等于“可回放”：Phase C 的 Assistant 协议快照把最终协议、Provider 和模型冻结到具体消息；仅在已知允许 finish 后、`complete-v1` metadata 已强制 flush 的 completed Assistant，才可作为 replay source。流中断、取消或失败 Attempt 的部分 reasoning 虽可能已经暂时显示，却绝不可被后续请求回放。强保证和诊断规则以 [08-PhaseC协议快照与完整性闭环.md](./08-PhaseC协议快照与完整性闭环.md) 为准。

### 匹配与有效范围

仅当 Envelope 同时满足以下条件时，当前 Adapter 才可消费：

- 协议匹配；
- Provider 配置 ID 匹配；
- 最终 Provider 模型 ID 匹配；模型 ID 的规范化规则必须与现有 `providerModelId` 优先、内部 `model.id` 回退的规则一致；
- 所属 Assistant 是 `completed`；
- 所属消息仍在当前有效模型上下文中；
- Envelope 通过当前版本严格校验；DeepSeek experimental 还必须满足 Message 协议快照、关联 reasoning Part.`text` 和 `complete-v1` 的完整性要求。

合法但不匹配并不删除历史数据，而是正常跳过。历史 state 允许异构共存，例如同一 Session 曾分别使用 OpenAI 与 DeepSeek；只有当前 Adapter 的兼容记录可被消费。

### DeepSeek experimental 回放范围

DeepSeek Thinking Phase C 的唯一暂行 scope 是：

> 当前有效模型上下文中，最后一条 User 消息之后、当前请求之前的全部兼容 Assistant reasoning parts。

由此导出：

- 首轮请求在最后一条 User 消息之后没有 Assistant reasoning，故没有回放。
- 同一用户任务的工具循环中，工具结果后的后续模型请求回放该范围内全部兼容 reasoning。
- 新 User 消息出现即切断更早 reasoning 的 DeepSeek 回放；旧消息保留在普通 transcript 中，但其 reasoning 不再作为本次 DeepSeek replay。
- Provider ID、最终模型、协议不匹配的 reasoning 不消费。
- compaction 后仍以 ModelContext Resolver 的当前有效上下文为边界；retained tail 中满足 scope 的 reasoning 可以回放，仅 Timeline 可见但未被 resolver 选入的旧 reasoning 不补回。
- Phase C 仅为 **experimental**。Phase D 真实服务联调是否认该 scope 时，必须同步修改 Adapter、fixtures、验收标准和本文档；在此之前不得宣称 stable。

### compaction 与 single-call 隔离

- `getMessagesContext()`、自动压缩、摘要生成和 shared single-call 只使用 Provider-neutral messages。
- 这些路径不得因为未来引入 Adapter 而取得或透传 `providerReplay`。
- `protocolAdapter` 是 Agent 最终模型调用的模型级配置；single-call/compaction 默认不得启用 DeepSeek Thinking 特化，也不得通过普通 `providerOptions` 旁路启用。
- compaction 后只以 ModelContext Resolver 的有效上下文为准；retained tail 可按正常规则携带 Provider state，resolver 之外的旧 state 不得额外补回。
- 普通 single-call 即使使用官方 OpenAI，也不自动拥有 Agent Session 的 Provider state；除非未来另立设计并明确授权。

## 目标

- 将 Provider 专属对话续接规则集中为可注册、可测试的 Adapter。
- 保持 OpenAI Responses 当前请求、持久化、终态门禁及隔离行为等价。
- 为 DeepSeek Thinking 提供明确、实验性且可验证的接入路径。
- 将私有 state 的读写、兼容性、Attempt 生命周期和失败处理变为可审查不变量。
- 让 debug 能确认最终 AI SDK 请求是否包含 state，同时严格保护 OpenAI 密文、凭证和附件；对可见 DeepSeek reasoning 限制重复记录。

## 非目标

- 不把所有 Provider 调用、工具执行或重试框架抽象成插件系统。
- 不改变公开 API、Timeline、Archive 的消息内容；DeepSeek 的可见 reasoning 仅走现有 reasoning Part 展示语义，不新增公开字段。
- 不在 Phase A 修改数据库列名、迁移既有 JSON 或重命名内部字段。
- 不实现 OpenAI 的服务端 response 引用链、`previous_response_id`、WebSocket 续接或增量 tool-result 请求。
- 不根据 `baseURL`、模型前缀、Provider 显示名自动猜测 DeepSeek 协议。
- 不在本方案内实现隐藏 DeepSeek reasoning 的私有存储模型。
