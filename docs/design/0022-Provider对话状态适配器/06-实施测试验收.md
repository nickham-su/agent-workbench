# 实施、测试与验收

## 实施总原则

- 每个 Phase 必须可独立审查、测试和回滚。
- 不得把等价重构、日志语义变化、DeepSeek 协议接入、持久化 schema 演进混入同一 Phase。
- 每个 Phase 合并前应保留或补齐可证明行为的自动化测试；没有测试证据不得以“结构更清晰”替代验收。
- 实现过程不应修改公开消息契约来偷渡 Provider 私有 state。

## Phase A：OpenAI 等价提取

### 目标

建立 `ProviderConversationStateAdapter`、Attempt 和 Registry，将现有 OpenAI Responses 专用请求准备、chunk metadata 采集和终态校验迁入 Adapter；可观察行为保持不变。

### 建议实施步骤

- 在 `apps/agent-worker/src/runtime/` 下按现有 provider 模块风格新增 Adapter 接口、Registry 与 OpenAI Adapter 文件；Registry 无适配器时返回 `null`，不得新增伪装真实 protocol 的 Noop Adapter。
- 以当前 `openai-responses-replay.ts` 的纯函数为迁移起点，保留可单测的请求 options、消息注入、chunk/update、terminal status 函数。
- 将 Runner 中 profile 判断、`applyOpenAiResponsesReplay`、`collectOpenAiResponses*`、terminal flag 逐步替换为 Adapter 的 `prepareInvocation`、Attempt `observeChunk`、`finalizeAttempt`。
- 保持 Runner 的 Part 创建、`position`、flush、retry/replacement、completeAssistant 控制位置不变。
- 保持实际调用顺序不变：replay 注入 → 附件物化 → 工具发现；不得提前 list tools，也不得改变 MCP 发现副作用时机。
- 保持现有 `provider_replay_json`、`providerReplay`、TypeBox schema、SQLite migration 及公开 read-side 不变。
- 明确 Update target 校验与 shared compatibility function 的调用点；Store 继续作为持久化防线。
- 在所有旧测试通过后，增加等价断言而非只测试新接口。

### 涉及区域

- `apps/agent-worker/src/runtime/runner.ts`
- `apps/agent-worker/src/runtime/providers/openai-responses-replay.ts`
- 新增 Adapter/Registry 文件
- `packages/shared/src/internal-contracts/agent-provider-replay.ts`
- 必要时仅做无行为变化的类型导出整理
- OpenAI replay、streaming flush、retry/recovery、API read-side 和 store 测试

### Phase A 验收

- 相同 fixture 下最终 AI SDK 入参和 mock HTTP body 与重构前等价。
- 多 reasoning item、多 summary segment、text/tool-call identity、terminal encrypted content 补齐均不回归。
- 缺 `response.completed`、failed/incomplete、unknown finish 仍拒绝当前 Attempt 提交，并保持现有 Runner retry/replacement 语义。
- retry replacement 后旧 Attempt state 不会进入新 Attempt 或最终 history。
- Adapter 选择、初始化或 `prepareInvocation` 失败时：不创建 Assistant、不发送模型请求；且 Phase A 不触发工具发现。
- 附件失败仍发生在工具发现之前：不创建 Assistant、不发送模型请求，也不触发工具发现。
- 共享 compatibility 抛出的 Invariant 不进入 retry；普通 Provider 网络错误仍按现有 retry/replacement 策略处理。
- Compatible、Anthropic、compaction、single-call 不获得 OpenAI state。
- 现有数据库中的 OpenAI replay 无迁移即可读取并回放。
- debug 日志行为不变；不得夹带 Phase B 的最终 request 投影。

### 回滚边界

仅回滚新增 Adapter 接线与等价重构文件；不依赖数据库数据格式、设置或日志格式变化，故可独立回滚。

## Phase B：Assistant Debug Record 安全投影

### 目标

以唯一 `projectAssistantDebugRecord()` 安全投影完整 Assistant Debug Record，而不只替换 `request`。它统一覆盖 running、completed、failed 记录中的最终 AI SDK request、response、toolCalls、error 与 record 级状态，解决注入前 messages、response/tool/error 旁路泄露和全记录体积失控的问题。

### 建议实施步骤

- 新建专用 projection 函数；禁止复用通用 JSON stringify 作为唯一防线。
- 定义 `projectAssistantDebugRecord()` 的输入边界和固定输出字段，统一投影 request、response、toolCalls、error；禁止任一写入路径直接携带原对象。
- 定义并测试 reasoning、provider options、headers、附件、base64、长文本、工具 input/result、response、错误对象与字符串化 JSON 的字段级脱敏与截断策略。
- running、completed、failed 三处日志均改用同一投影函数。
- 明确 `request` 不是 HTTP body；默认不保留 `sourceMessages`。
- OpenAI 密文固定脱敏；DeepSeek reasoning 即使在 UI 可见，也不记录任何文本预览，只记录存在性、Unicode code point 长度和省略原因。
- 对完整 canonical Debug Record（不是 request 子对象）执行 256 KiB 硬上限和固定降级顺序；若仍超限只输出结构摘要。
- 保留现有 `sanitizeForDebugDump()` 作为末级防线，但不得依赖其覆盖所有新增形态。

### Phase B 验收

- 对 OpenAI replay，日志能断言最终 request 存在 reasoning 与 replay 标志，但 sentinel 密文永远不出现。
- 对 DeepSeek `response.reasoningText` 及 request reasoning，日志不出现任何正文或预览，仅保留存在性、Unicode code point 长度与固定省略标记。
- request、response.reasoningText、tool input、tool result、`Error.message` 与字符串化 JSON 各自的 sentinel 均不得出现在最终 running/completed/failed Debug Record。
- 附件/base64、Authorization/API key、Provider replay、错误字符串均有负向泄露测试；普通 response.text、tool input/result 与错误字符串均遵守 4 KiB UTF-8 单字段截断和敏感键清理。
- 超过 256 KiB 的完整 Debug Record 按固定优先级降级，并在仍超限时只输出稳定结构摘要；不得仅验证 request 子对象。
- 日志写入失败不改变模型请求、flush 或完成行为。

### 回滚边界

日志仅是 debug 可观测性；可独立回滚至旧日志语义，不影响状态协议或持久化。

## Phase C：DeepSeek Thinking Adapter（experimental）

### 前置条件

- Phase A 和 Phase B 已独立完成并通过回归。
- 已针对当前 AI SDK 版本建立真实 SDK + mock fetch/SSE fixture。
- mock SSE 已证明单次响应中全部 `reasoning-delta` 拼接得到的 reasoning Part.`text` 与完整 `reasoning_content` 一致、未摘要、未改写、未截断。不能证明时 Phase C 停止，另立“独立私有状态实体/私有锚点”设计。
- DeepSeek 设置、模型最终解析、Session 模型覆盖和 Factory 的显式 `protocolAdapter` 方案已完成 schema 评审。
- Assistant protocol snapshot、DeepSeek `complete-v1` metadata、设置 UI 告知和私有 diagnostics 均已有实现计划；缺任一项不得宣称 Phase C experimental 完成。

### 建议实施步骤

- 在最终 Provider Model 的 `options` 引入受白名单保护的 `protocolAdapter`；缺失等价于 `default`、保存时省略默认值。仅允许 `@ai-sdk/openai-compatible + deepseek-chat-thinking`，settings 保存拒绝非法组合，Worker/Factory 再防御。
- 增加 protocol-specific thinking/reasoningEffort schema；规范值为 `low`/`high`/`max`，默认 `high`；历史别名 `minimal`/`medium`/`xhigh`/`ultra` 在保存时规范化。拒绝非法枚举和 `topP` 的非 `0.95–1.0` 值；准备时移除 `temperature`、`presencePenalty`、`frequencyPenalty` 并产生不含值的诊断。
- 增加受限 `ProviderModelFactory`：在模型创建前解析最终模型配置，为 DeepSeek 安装经 mock body 验证的 `transformRequestBody` 或等价受控机制。single-call/compaction 不进入该分支。
- Registry 对 `deepseek-chat-thinking` 显式映射；缺失或不支持时 fail closed。
- 实施 v21 → v22 非破坏性 schema 迁移：在 `agent_message` 新增不可变 `provider_protocol_snapshot_json`，建立私有查询索引，并在 create/replacement/recovery 链路原子写入/校验快照。不得只扩展 Envelope 而省略快照。迁移/回滚详见 08。
- v21 遗留 active Run + streaming Assistant 升级 v22 时，`NULL` snapshot 不得由 settings 回填或续跑；必须 fenced recovery/fail-converge 收敛为非 running，且不发 Provider HTTP，保留旧消息后允许用户发起新 Run。
- 扩展私有 Envelope 为严格判别联合，DeepSeek Envelope 只保存 `contentSource: "reasoning-part-text-v1"` 与 `completion: "complete-v1"` metadata，不重复保存 reasoning 原文；保持旧 OpenAI JSON 可读可写。
- 扩展私有 read-side/PromptContext 以提供无原始 JSON 的 state diagnostics 与 Message snapshot；实现 scope 内 snapshot 匹配 DeepSeek state 损坏时请求前 fail closed。
- 实现 DeepSeek 静态准备顺序：最终模型协议解析 → Factory 静态校验/创建 model → Registry 选择/初始化 Adapter → 工具发现 → `toolsDisposition` → `prepareInvocation` → 附件物化 → streamText。前四步的静态失败不得触发工具发现；依赖 disposition 的 prepare 失败在工具发现后仍不得创建 Assistant/发送请求。
- 实现 scope：当前有效链、最后一条 User 之后、当前请求之前的全部兼容 Assistant reasoning Parts；新 User 切断旧 reasoning；compaction 保持有效链语义。
- 实现 DeepSeek Attempt：reasoning delta 先写可见 Part.text；仅 `stop`/`tool-calls` finish 后写 `complete-v1` metadata 并强制 flush；EOF 无 finish/unknown/error/abort/timeout/取消都不得成为 source。
- 实现模型设置 UI、API 文档与 warning：“实验性：Provider 返回的完整 reasoning 会保存并显示在此 Agent 会话中。”；不得使用私有/隐藏措辞。
- 补齐 API/Worker/SQLite、迁移、Factory、UI、切换、损坏状态和失败测试。

### Phase C 验收

- mock HTTP 验证最终 Chat Completions 请求含受控 `thinking`、`reasoning_effort`、合法 `top_p`、`reasoning_content`、`tool_calls`、`tool_call_id`。
- mock body 验证 `toolsDisposition` 与最终 HTTP `tools` 字段一致；空集合省略 tools，且不回放 reasoning。
- 证明 stream `reasoning-delta` 拼接文本等于最终完整 `reasoning_content`；这是 experimental 接入的硬前提。
- mock HTTP 覆盖 `reasoningEffort` 默认 `high` 和最大档 `max`，并证明 Factory 只发送规范值；覆盖历史兼容别名保存后规范化。
- 首轮、同 User 工具循环、多轮工具调用、无工具、空工具、新 User 切断、compaction、Provider/模型/协议切换均有测试。
- v21 → v22 升级、新建、recovery、replacement、settings 改变后的快照不变、superseded/compaction 隔离均有数据库测试。
- v21 active Run + streaming Assistant 升级 v22 的集成测试证明：不发 Provider HTTP、不补写 snapshot、Run 和 Assistant 最终均不再 running；旧 Message 与 `NULL` snapshot 保留且用户可新建 Run。另验证 completed 旧 `NULL` snapshot 只是不参与 DeepSeek replay，不阻塞普通读取。
- scope 内 snapshot 匹配的整体 Envelope 缺失、未知版本、缺 metadata/`complete-v1`、缺或不完整 reasoning 文本全部请求前 fail closed；不匹配、旧 `NULL` snapshot 或不可识别归属的损坏状态正常跳过。
- reasoning-end 后 EOF、unknown/不允许 finish、error、abort、timeout 均没有 `complete-v1`，不得 complete；allowlist finish 的 terminal metadata 必须 flush 成功后才 complete。
- `temperature`、`presencePenalty`、`frequencyPenalty` 不出现在最终 HTTP body，且有无值结构化诊断；非法 `topP` 被拒绝而非夹紧。
- DeepSeek reasoning 以现有 Part.`text` 可见、可持久化；私有 Envelope 不重复存原文。
- UI、API 文档和设置保存均标为 experimental，显示“完整 reasoning 会保存并显示”的告知；非法 npm/协议组合与历史配置兼容均有测试。
- DeepSeek private metadata 不泄露到非目标 Compatible Provider、Anthropic、compaction、single-call、Archive 或 debug 原文；debug reasoning 无预览，只记录存在性/Unicode code point 长度/省略原因；可见 reasoning 仅按现有 UI/read-side 语义出现。
- Phase C 始终标记 experimental；不得宣称 stable。

### 回滚边界

- 默认回滚是继续运行支持 v22 schema 的应用二进制，关闭或回滚 DeepSeek feature flag、模型设置/UI 入口和 `deepseek-chat-thinking` 协议消费；既有异构私有历史保留但不消费。
- 当前 v21 二进制采用严格 schema version/列匹配，不能启动 v22 数据库；不得将“关闭 feature”误解为可直接回退旧二进制。
- 不得降写 schema version、删列、重建表或删除历史 JSON。未来若要求二进制回退，必须先有另行设计的前向兼容预备版本及自动化验证，不属于本 Phase 默认承诺。

## Phase D：真实 DeepSeek 最小联调与稳定门禁

### 目标

验证真实服务行为，重点不是“请求成功一次”，而是确认 experimental scope、工具规则和参数特化。**Phase D 成功是从 experimental 升为 stable 的硬门禁。**

### 最小场景

- thinking 启用的首次请求；
- Assistant reasoning + tool call → tool result → 下一次请求；
- 多轮工具调用；
- Assistant 有 reasoning 但无实际 tool call 后，下一次携带 tools 的请求；
- 不携带 tools 的连续对话；
- 新 User 消息后的 scope；
- Provider ID、模型、协议切换；
- 缺失/错误 reasoning 的服务端错误表现；
- 不支持参数移除、`top_p` 边界与 thinking/reasoning_effort 的实际 body 行为。

### 联调纪律

- 使用专门测试账号/环境；不得记录 API key、完整 reasoning、用户私有代码或真实 replay 原文。
- 将确认过的 request/response 结构抽象为脱敏 fixture，补进 mock 测试。
- 若真实结果否定 scope、工具或参数假设，先同步修订 Adapter、Factory、fixture、验收标准和设计文档，再重新联调；在完成前保持 experimental。

## 代码审查标准

### 架构与边界

- `messages` 保持 Provider-neutral；仅 DeepSeek 已批准的可见 reasoning Part.`text` 走既有消息语义，私有 metadata 不进入公开契约。
- Adapter 不获得数据库、API 写入、工具执行或 Run 状态控制能力；输入为只读。
- Registry 使用显式协议键；默认无状态协议返回 `null`，不存在基于 URL/名称/模型前缀的猜测。
- `protocolAdapter` 是最终模型级配置；settings、Worker、Factory 均拒绝非法 npm 组合。
- compaction/single-call/messages-context 未取得私有 state，且不启用 DeepSeek 特化。
- Phase C 的 v22 Assistant protocol snapshot 在创建/replacement/recovery 中原子写入或校验，且不依赖后续 settings。

### Attempt、一致性与失败

- 每次 `streamText()` 新建 Attempt；retry/replacement/recovery 不复用临时状态。
- Runner 仍是 Part.position、flush、retry、complete 的唯一权威。
- Update target 与 shared compatibility 两层校验都存在。
- Invariant 不可 retry、不可 replacement 掩盖、不可完成。
- TerminalProtocol 当前 Attempt 不可完成；OpenAI Phase A retry/replacement 语义与当前一致。
- terminal metadata 成功 flush 后才允许完成。

### 协议、数据与 DeepSeek experimental

- OpenAI Phase A HTTP body 与旧行为等价，且 replay→附件→工具发现顺序不变。
- 旧 `provider_replay_json` 可继续读取；无无意义 schema 迁移。
- 新 Envelope 严格白名单、带版本/协议/Provider ID/模型；DeepSeek 不重复保存 reasoning 原文，且有 `complete-v1`。
- DeepSeek scope、toolsDisposition、snapshot 匹配的损坏 state fail-closed 和新 User 切断均按本文固定规则实现。
- Factory 是 DeepSeek HTTP 特化唯一入口；mock fetch 证明最终 body。
- `temperature`、presence/frequency penalty 已移除，topP 只允许 0.95–1.0，thinking/reasoningEffort 只来自协议白名单；最终 effort 仅 low/high/max。
- reasoning-end 不等于完整；只允许 finish allowlist 生成 completion metadata，强制 flush 后才能 complete。
- DeepSeek 保持 experimental，未提供 Phase D 证据不得标 stable。

### 安全与日志

- `projectAssistantDebugRecord()` 是 running/completed/failed 的唯一 debug 写入投影入口；其 request 是最终 AI SDK 入参投影，不是 HTTP body。
- OpenAI 密文、凭证、附件/base64、超长文本、tool input/result、response、错误对象与字符串化 JSON 均已测试脱敏。
- DeepSeek reasoning（包括 `response.reasoningText`）虽可见，debug 无文本预览，只保留 present、Unicode code point 长度和 omitted 原因。
- 4 KiB 单字段、256 code point filename、整份 Debug Record 256 KiB 硬上限及固定降级优先级均有确定性测试和 sentinel 证据。
- 公开 read-side、Archive、日志测试未泄露私有 metadata 或 OpenAI sentinel。

## Definition of Done 与证据要求
