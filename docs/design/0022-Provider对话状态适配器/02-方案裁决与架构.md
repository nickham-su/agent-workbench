# 方案裁决与架构

## 方案比较

| 方案 | 描述 | 优点 | 不接受的风险或成本 | 结论 |
|---|---|---|---|---|
| 通用 messages 内嵌私有 state | API 直接把 Provider replay 写进所有 `context.messages`，由各 Provider 自行忽略 | 局部代码看似更短 | 密文/metadata 进入 compaction、single-call、日志、错误和非目标 Provider 路径；每个消费者都要过滤；切换 Provider/模型仍须校验 | 不采用 |
| 独立 state + 调用前 Adapter | 普通 transcript 与私有 state 分离，Worker 根据本次 profile 物化 | 安全边界集中；默认隔离非目标路径；可扩展多个协议 | 需要维护私有 Envelope、映射和 Adapter | 采用 |
| 完整 Provider 执行插件 | Adapter 接管模型创建、请求、流、工具、重试和落库 | 表面统一 | 破坏 Runner 的事务与状态权威；抽象范围过大 | 不采用 |
| Provider-specific Prepared History API | API 直接产出按 Provider 物化的请求 | 可减少 Worker 局部组装 | API 变成 profile-aware，扩大私有状态流转和审计面 | 暂不采用 |

DeepSeek 可见 reasoning Part.`text` 是已明确的产品例外：它可见不代表其协议 metadata 可进入通用 messages。私有 state 仍独立传输，Adapter 仍是唯一将 “已匹配 metadata + 同一 Part 文本” 变成 DeepSeek replay 的路径。

## 关键裁决

### 不把私有 state 放入通用 messages

通用 messages 是多个路径共享的输入：主 Agent、compaction、single-call、日志、附件物化、后续插件和错误诊断。将 Provider 专属 state 放入其中会使“默认不传播”变成“默认传播、每处负责剔除”。这违反最小权限原则。

DeepSeek reasoning 文本本身按产品决策可见，但其 `protocolAdapter`、Provider/模型绑定、完整性诊断和回放资格仍不能因文本可见而被降级为普通消息字段。未来 Compatible Provider 可能序列化、拒绝或误解释 reasoning part；因此只有目标 Adapter 才可在符合条件时把这类 Part 作为 replay 输入。

### Adapter 不接管整个调用

Runner 目前负责：工具快照、流式 part 顺序、消息 flush、retry/replacement、abort/timeout、`completeAssistant` 和 API 栅栏写入。将这些交给 Adapter 会产生多套成功提交和重试语义。

Adapter 只能解释 Provider 协议，并向 Runner 返回有限、可验证的数据。Runner 必须始终是：

- Assistant 消息创建、更新、完成或失败的唯一写入协调者；
- 工具定义、执行和工具结果的唯一协调者；
- retry、replacement、recovery、timeout、abort 的唯一控制者；
- 最终是否允许成功提交的唯一裁决者。

### 显式模型级 `protocolAdapter`

`protocolAdapter` 归属**最终解析出的 Provider Model**，而非 Provider 全局配置、base URL 或 Session 临时猜测。模型字段缺失等价于 `"default"`，保存时建议省略默认值，避免历史 JSON 噪声。

```text
AgentProviderModel.options.protocolAdapter
  = "default" | "deepseek-chat-thinking"
```

约束：

- `deepseek-chat-thinking` 仅允许 `@ai-sdk/openai-compatible`；settings 保存时拒绝非法组合，Worker/Factory 再次防御。
- Session 模型覆盖必须使用最终解析模型的该字段，不能沿用默认模型或 Provider 级字段。
- 官方 `@ai-sdk/openai` 的 Responses 协议继续由 npm 与固定 `responses()` 调用路径确定，不要求也不允许用户通过此字段选择。
- Phase A 不增加该配置；选择非默认协议时，Registry/Factory 不存在、初始化失败或 profile 不支持必须 fail closed。
- 禁止静默回退为无 Adapter；否则会悄悄丢失 Provider 要求的续接状态。
- Adapter 在一个 Model Step 内选择一次并固定；不得一次请求内切换协议解释器。

### 受限 `ProviderModelFactory`

DeepSeek 请求特化必须有唯一可执行路径：在模型创建前解析最终模型级 `protocolAdapter`，由受限的 `ProviderModelFactory`（最终命名可按项目风格调整）创建 model。

其职责仅包括：

- 对 `@ai-sdk/openai-compatible + deepseek-chat-thinking` 安装受控 `transformRequestBody`，或使用经当前 AI SDK mock HTTP 证明确实等价的机制；
- 将协议配置白名单中的 `thinking`、`reasoning_effort` 写入最终 HTTP body；
- 防御 npm/协议非法组合；
- 维持已有 OpenAI `responses()`、普通 Compatible `chatModel()` 与 Anthropic 创建路径。

其明确不能做：

- 接受 Adapter 提供的任意 model、baseURL、fetch 或 SDK 实例；
- 让 Adapter 修改 model/baseURL/apiKey；
- 让普通 `providerOptionsByKey` 未经验证地透传 thinking 特化；
- 将 DeepSeek 特化自动带入 shared single-call/compaction。

若后续证明当前 SDK providerOptions 可以可靠生成相同 HTTP body，才可替代 `transformRequestBody`；替代的前提是保留 mock fetch 对最终 body 的断言，不能仅靠类型通过。

### 分阶段而非一次完成

OpenAI 等价迁移、日志语义变化、DeepSeek 新协议、持久化 schema 演进具有不同风险模型。混在一次变更中会使回归无法归因。阶段定义见 [06-实施测试验收.md](./06-实施测试验收.md)。

## 目标架构

```text
SQLite 当前有效消息链
  ├─ Runtime transcript source
  │   └─ RuntimeTranscriptProjector
  │       └─ PromptContext.messages
  └─ Assistant Message protocol snapshot + provider_replay_json
      └─ 私有 read-side + 非敏感状态诊断 + DeepSeek 完整性检查
          └─ PromptContext.providerReplay / providerReplayDiagnostics

Worker / Runner
  ├─ 按最终模型解析 protocolAdapter
  ├─ ProviderModelFactory 创建受限 model
  ├─ Phase A：replay 注入 → 附件物化 → 工具发现（顺序不变）
  ├─ Phase C：Factory/Registry 静态校验 → 工具发现 → toolsDisposition → Adapter 物化 → 附件物化
  ├─ Registry 选择 Adapter 或 null
  ├─ 构造 RuntimeStreamRequest
  ├─ attempt = adapter?.createAttempt(...)
  ├─ streamText()
  │   └─ attempt?.observeChunk(chunk) → metadata update / protocol signal
  ├─ flush 私有 metadata 与普通 Part
  ├─ attempt?.finalizeAttempt()
  └─ Runner 通过全部门禁后 completeAssistant()
```

## 完整调用链与顺序

### Phase A：必须保持现有顺序

当前 `runModelStep()` 的实际顺序是：

```text
replay 注入
→ 附件物化
→ toolRegistry.listTools()
→ 构造 toolSet / request
→ streamText()
```

Phase A 必须逐项保持此顺序和外部可观察行为：

- Adapter 选择或 `prepareInvocation()` 失败发生在工具发现之前；不得创建 Assistant，不得发送模型请求，不得触发 MCP 工具发现副作用。
- 附件物化失败发生在工具发现之前；不得创建 Assistant，不得发送模型请求。
- 工具发现保持在附件物化之后；不得为了预留 DeepSeek 而重排。
- 日志仍保持旧语义；Phase A 不修改 debug dump。

### Phase C：为 DeepSeek 引入的明确顺序变化

DeepSeek 是否回放取决于最终请求是否实际携带 tools，因此仅在 Phase C 对 **DeepSeek 特化路径**允许调整为：

```text
解析最终模型与 protocolAdapter
→ ProviderModelFactory 创建 model
→ Registry 选择并初始化 Adapter
→ 工具发现，生成唯一 toolSet 快照
→ 从该快照推导 toolsDisposition
→ prepareInvocation（决定回放）
→ 附件物化
→ 使用同一 toolSet 构造并发送 streamText 请求
```

- Factory 静态校验、非法 npm/协议组合、缺 Registry 条目和 Adapter 初始化失败必须在工具发现之前失败：不创建 Assistant、不发送模型请求、不触发 MCP/工具发现副作用。
- 依赖 `toolsDisposition` 的 DeepSeek `prepareInvocation()` 失败发生在工具发现之后；此时仍必须不创建 Assistant、不发送模型请求。
- `toolsDisposition: "present-non-empty"` 当且仅当最终请求的 `tools` 字段来自非空 toolSet；空工具集合必须是 `"omitted"`，请求中不得发送空 `tools: {}` 或 `[]` 作为等价物。
- DeepSeek Adapter 不得重新查询工具；它只能消费这次即将发送请求的 snapshot 派生事实。
- mock HTTP body 必须证明 Adapter 收到的 `toolsDisposition` 与最终 HTTP `tools` 字段完全一致。
- 此顺序变化是 Phase C 的行为变化，必须新增附件失败、MCP/工具发现副作用、Adapter prepare 失败的顺序测试；不得回填为 Phase A 的“等价重构”。

### 请求参数优先级

从低到高：

```text
已验证的模型/Provider 通用配置
→ 模型级 protocolAdapter 白名单配置
→ Adapter 的协议状态物化与受限 directive
→ Runner 的执行不可变量
```

具体限制：

- Adapter 可返回最终 messages、有限 provider options 规范化结果及如 `includeRawChunks` 的明确 directive；不可设置 model/system/tools/abortSignal/maxRetries/超时。
- `ProviderModelFactory` 是 DeepSeek HTTP 特化的唯一写入点；Adapter 不直接拼接 HTTP body。
- Runner 固定 `maxRetries: 0`，避免与自定义 retry 双重执行。
- OpenAI Adapter 必须继续强制 `store: false` 与 `include: ["reasoning.encrypted_content"]`，并过滤 0019 排除的服务端引用字段。
- DeepSeek Thinking 强制值优先于通用用户字段；详细参数规则见 [04-OpenAI等价迁移与DeepSeek预留.md](./04-OpenAI等价迁移与DeepSeek预留.md)。

### Attempt 生命周期

一次 `streamText()` 是一个独立 Attempt。`createAttempt()` 必须在每次真实请求前创建，不能跨重试、replacement 或 recovery 复用临时协议状态。

```text
Attempt 创建
→ observeChunk 零次或多次
→ 对 DeepSeek：观察 allowlist finish 后生成 completion metadata，并强制 flush 所有待写更新
→ finalizeAttempt
→ Runner 决定提交、重试、替换或失败
```

每个 Attempt 独立拥有：

- 原生 reasoning item 到本地 part ID 的映射；
- `completed`、`failed`、`incomplete`、unknown finish 等协议终态；
- 本 Attempt 的 token/临时协议统计；
- 尚未落库的 metadata 更新。

### Chunk 处理与提交门禁

- Runner 继续依据 AI SDK 标准 chunk 创建/追加 text、reasoning、tool-call Part，决定 `position`。
- Adapter 只观察 chunk 并返回附着私有 metadata 的更新或协议状态；不得自行创建业务 Part 或重排 position。
- Runner 必须验证更新目标存在、Part 类型一致、tool-call ID 一致，再应用更新。
- raw terminal 事件可以生成多个 metadata-only 更新。应用后必须强制 flush，才可进入 finalize。
- `finalizeAttempt()` 返回失败、Adapter 抛出、flush 失败、取消、timeout 或 Runner 本地不变量失败时，禁止成功提交。
- DeepSeek 的 `reasoning-end` 不能通过 complete 门禁；只有 `stop` 或 `tool-calls` finish reason 可以形成 `completion: "complete-v1"` update。
- DeepSeek EOF 无 finish、unknown/不允许 finish、error、abort、timeout 或取消属于 TerminalProtocol；不得 complete。完整闭环见 08。

## retry、replacement 与 recovery

### 错误分类

| 分类 | 示例 | 允许 retry | replacement | 允许完成 |
|---|---|---:|---:|---:|
| Configuration | 非法 protocolAdapter/npm 组合、Factory 初始化/配置校验失败、DeepSeek 必需 state 诊断失败 | 否；除非外部配置/数据被修复后重新发起 Run | 否，因请求前无有效输出 | 否 |
| Invariant | shared `assert...Compatible` 冲突、Part/identity/tool-call ID/顺序冲突 | 否 | 否；不得以 replacement 掩盖数据矛盾 | 否 |
| TransientProtocol | 普通 Provider 网络错误、可恢复的流 transport error；具体由 Runner 既有策略判定 | 可以，由 Runner 决定 | 若该 Attempt 已 flush 输出，必须先成功 replacement | 否，该 Attempt 不可完成 |
| TerminalProtocol | OpenAI 缺 `response.completed`、failed/incomplete、unknown finish；Adapter finalize 拒绝 | 保持当前 OpenAI Runner 的既有 retry 判定，不得因 Phase A 改变；每次为新 Attempt | 若 Runner 按既有策略重试且已有输出，必须 replacement | 否，该 Attempt 不可完成 |

DeepSeek EOF 无 finish、unknown/不允许 finish、stream error、abort、timeout 与取消同属 TerminalProtocol；其部分 reasoning 即使已流式显示，也不能带 `complete-v1` 进入后续 replay。

- `assertProviderConversationStateUpdateCompatible()` 或其改名后的共享兼容函数抛出的错误必须归类为 Invariant，绝不可按网络错误重试。
- Adapter 给出的 `retryable` 仅为建议；Runner 的取消状态、重试上限、replacement 结果和本地错误仍可否决。

### replacement

若失败 Attempt 已经将输出 flush 到 Assistant：

```text
失败 Attempt
→ replaceStreamingAssistant(old, new)
→ replacement 成功
→ 清空旧 orderedParts、版本、计数、Attempt state
→ 新 Attempt
```

- replacement 失败必须终止该 Run，禁止继续在旧 Assistant 上重试。
- replacement 成功前，旧输出不是成功历史，不能成为 replay source。

### recovery

- recovery 只能遵循既有 streaming Assistant 恢复语义；Adapter 不能借此复用上一次网络 Attempt 的临时状态。
- 从数据库重新构建的 `providerReplay` 只包含 completed Assistant 的有效历史；未完成流不能作为回放来源。
- Phase C 升级后遇到 v21 遗留 active Run 的 streaming Assistant 且 snapshot 为 `NULL` 时，不存在安全的协议 provenance，故不得根据当前 settings 推断协议、补写 snapshot 或续发 Provider 请求。
- 必须由既有 fenced recovery/fail-converge 路径将该 Run 和 streaming Assistant 原子收敛为非 running 状态；保留原消息和 `NULL` snapshot，允许用户另起新 Run。该收敛若因 fence 失效被忽略，不得越权重试写入。
- 这项升级收敛不等同于 replacement：不得为遗留 `NULL` snapshot 消息创建可继续请求的 replacement。详见 08。
