# 数据与实体设计

## 存储分层与权威性

```text
Agent 业务域（可破坏性重建）
    └─ agent_run / message / tool / session 业务状态

API 主 SQLite 的 Analytics 域（长期查询权威）
    ├─ analytics_*_fact / execution / worker / git / domain_state
    └─ dashboard_*_10m / dirty bucket

Worker 私有 Delivery Outbox SQLite（可靠交付日志，非查询权威）
    └─ 仅模型 begin/finish 标准 DTO，最终 ACK 后投递至 API 主库 Fact
```

- `AGENT_DOMAIN_TABLES` 和 `clearAndDropAgentDomain()` 可删除 Agent 表；Analytics schema 独立维护 `ANALYTICS_SCHEMA_VERSION`，不加入 Agent 域，不强 FK 到 Agent 表。
- **API 主库 Analytics Fact 才是查询、聚合和重建的权威。**Worker Delivery Outbox 只保证模型 DTO 最终交付，不能被 Dashboard 查询或作为聚合来源。
- 所有主库 Analytics 时间使用 UTC Unix ms。全部枚举/原因码以 [指标口径](./02-指标口径.md) 为唯一字典。

## API 主库长期事实

以下 DDL 为字段和约束合同。可加索引、受控诊断列，但不得放宽唯一性、状态语义或存敏感正文。

### Run、Session、消息

```text

- workspace_id text not null
- session_id text not null
```

- Run Fact 创建和业务 Run 创建同一事务；常规终态与 domain rebuild 收敛也同事务更新 Fact 与 Dirty。

- Session/Message 用业务 ID 幂等写入；消息只存 user 元信息，不复制正文/parts。

### Run Execution

```text
analytics_run_execution
- execution_id text primary key
- run_id text not null
- workspace_id text not null
- run_kind text not null check (受控 run_kind)
- parent_run_id text null
- attempt_no integer not null check (attempt_no >= 1)
- worker_instance_id text null

- queued_at integer not null

```

约束：

- `unique(run_id,attempt_no)`；部分唯一索引保证同一 Run 至多一个 `queued/running` Execution。
- queued 无 start/end；running 有 `started_at` 无 end；ended 有 `ended_at/end_reason`，开始前结束允许 `started_at=null`。
- `effective_ended_at` 是唯一可计时长终点，要求 `started_at <= effective_ended_at <= ended_at`。
- `exact` 要求 `effective_ended_at=ended_at`；`unknown` 要求 `effective_ended_at=null`。本期不支持 bounded，不得由最后日志/心跳推断。
- Agent rebuild 关闭时：`ended_at=发现时刻`、`effective_ended_at=null`、`end_time_quality=unknown`、`end_reason=agent_domain_rebuilt`。

索引：

```text

analytics_run_execution(state, updated_at)
analytics_run_execution(workspace_id, run_kind, parent_run_id, started_at)
analytics_run_execution(worker_instance_id, state)
```

### 工具

```text
analytics_tool_fact
- tool_execution_id text primary key
- run_id text null
- tool_name text not null
- status text not null check (受控 tool_status)
- created_at integer not null
- started_at integer null
- completed_at integer null
- duration_completed_at integer null
- updated_at integer not null
```

- 本期不存 `workspace_id`，从 schema 层禁止工具 Workspace 查询/归因。
- `completed_at` 表示业务或恢复状态收敛时间；正常可观察 completed/failed/cancelled 时可等于真实终态。
- `duration_completed_at` 仅真实观察到工具终态时写入；工具时长唯一公式是 `duration_completed_at-started_at`。
- Agent rebuild/恢复将 queued/running Tool Fact 收敛为 `unknown` 时可写 `completed_at=发现时刻`，**必须**写 `duration_completed_at=null`，因此不会把收敛时间算成时长。
- 调用、状态和时长样本始终按 `created_at` 桶归属。

索引：`analytics_tool_fact(tool_name,created_at)`、`analytics_tool_fact(updated_at,status)`。

- `timeout_kind` 仅 timed_out；failure_kind 仅 failed；total derived 仅输入输出均存在且相加一致。
- `cache_comparable=1` 要求 input/cache-read 均非空且语义验证；`cache_write_verified=1` 才允许 cache-write 非空。

### Git Fact、scan、generation

```text
analytics_git_commit_fact(repo_id, commit_sha, committed_at, is_merge,
  files_changed, insertions, deletions, first_observed_at, last_observed_at,
  primary key(repo_id,commit_sha))

analytics_git_scan(scan_id primary key, repo_id, generation, status,
  started_at, completed_at, coverage_incomplete, covered_from,
  coverage_reason, error_code, unique(repo_id,generation))

analytics_git_scan_source(scan_id, source_kind, source_id, ref_count, status,
  error_code, primary key(scan_id,source_kind,source_id))

analytics_git_scan_membership(scan_id, repo_id, commit_sha,
  primary key(scan_id,repo_id,commit_sha))

analytics_git_repo_state(repo_id primary key, current_generation,
  current_scan_id, next_generation not null check(next_generation >= 1), updated_at)
```

- `analytics_git_scan_source` 不存绝对路径、URL、ref 名或 Git 输出。
- **领取 generation**：开始 scan 的短事务读取 `next_generation`，创建该 generation running scan，并将 `next_generation=next_generation+1`；失败不回退、不复用 generation。
- current 仅在全部 eligible source 成功后才可切换。切换的**同一个 Analytics transaction**必须写入/校验 Commit Fact、完整 membership、本 Scan 的 `coverage_incomplete/covered_from/coverage_reason`、`status='completed'/completed_at`、`current_scan_id/current_generation` 和所有 Git Dirty。
- 上述 transaction 任一步失败必须整体回滚，旧 current pointer、旧 membership 和旧 completed Scan 不变；running Scan 只能在独立、受控失败事务写 `failed/error_code`，不得留下部分新 generation 供查询。
- coverage 仅存 `analytics_git_scan`。API 从 Repo State current_scan_id join current scan 获取，不在 Repo State 冗余 coverage。

索引：

```text

```

## Domain State、聚合与 Dirty

### Domain State

```text
analytics_domain_state
- domain text primary key check (受控 analytics_domain)
- collection_started_at integer null
- backfill_status text not null check (受控 backfill_status)
- backfill_cursor text null
- backfilled_from integer null
- backfill_before integer null
- job_status text not null check (受控 job_status)
- last_job_started_at integer null
- last_job_succeeded_at integer null
- last_error_code text not null check (受控 analytics_error_code)
- rebuild_from integer null
- rebuild_to integer null
- updated_at integer not null
```

- 下表是**唯一权威 domain 映射**；九个列出的 domain 均必须有一条 State 行。`collection_started_at` 是新 Fact 开始采集/双写时间；`backfill_*` 是各自的回填水位，不能用一个全局起点代替。

| domain | State 行与回填 | Dirty domain / 聚合表 | API freshness / coverage 来源 |
| --- | --- | --- | --- |
| `model` | 有；不回填旧 Attempt，`collection_started_at` 起 | `model` / `dashboard_model_10m` | State 提供 job/freshness；coverage 的全局 gap/incident/历史损失健康计数分别实时读诊断表，并派生 `degraded` |
| `run` | 有；可从业务 Run 回填 | `run` / `dashboard_run_10m` | 全部取 State |
| `execution` | 有；不回填旧 Execution，`collection_started_at` 起 | **无 Dirty、无聚合表** | State 是原始 Execution collection coverage 权威，供实时 queued/running 与 agent duration coverage 复用；不返回 `pendingDirtyCount` |
| `agent_duration` | 有；不独立采集或回填起点，`collection_started_at` 必须为 null 并引用 `execution` coverage | `agent_duration` / `dashboard_agent_duration_10m` | job/rebuild freshness 取自身 State；coverage 引用 execution State |
| `tool` | 有；可回填可信旧 Tool | `tool` / `dashboard_tool_10m` | 全部取 State |
| `message` | 有；可回填 user Message 元信息 | `message` / `dashboard_message_10m` | 全部取 State |
| `session` | 有；可回填安全 Session 元信息 | `session` / `dashboard_session_10m` | 全部取 State |
| `worker` | 有；不回填旧 Worker 生命周期，`collection_started_at` 起 | `worker` / `dashboard_worker_10m` | 全部取 State |
| `git` | 有；`collection_started_at=null`、`backfill_status=not_applicable`；State 只表示 scan/job freshness，不表示历史回填覆盖 | `git` / `dashboard_git_10m` | freshness 取 State；coverage 仅逐 Repo current Scan |

- API 对可回填域返回 `backfilledFrom/backfillBefore/backfillStatus`；不回填域返回 `collectionStartedAt/backfillStatus='not_applicable'`。`agent_duration` 返回其 job 状态和 `coverageSource='execution'`，不得伪造独立采集起点。
- Git historical coverage **不读本表**，仅 `repo_state.current_scan_id` join completed current Scan；无 current Scan 时不是零或完整覆盖。
- `backfill_cursor` 只保存安全、可排序 ID/时间游标，不保存正文、路径或 SQL。

### 聚合与 Dirty

```text
dashboard_model_10m(bucket_start,provider_id,model_id,...)
dashboard_run_10m(bucket_start,workspace_id,run_kind,...)
dashboard_agent_duration_10m(bucket_start,workspace_id,...)
dashboard_tool_10m(bucket_start,tool_name,...)
dashboard_message_10m(bucket_start,workspace_id,...)
dashboard_session_10m(bucket_start,workspace_id,session_kind,...)
dashboard_git_10m(bucket_start,repo_id,...)
dashboard_worker_10m(bucket_start,...)

analytics_dirty_bucket(domain,bucket_start,dimension_key,state,marked_at,
  mark_version,claimed_by,claimed_at,claim_expires_at,claimed_version,
  attempt_count, primary key(domain,bucket_start,dimension_key))
```

- 每张聚合表主键等于全部维度；不同归属规则不得混表。
- Fact/状态与 Dirty 同一事务；每次标脏递增 mark_version。
- claim 从 pending/过期 claimed 条件领取，写 claimed_version=mark_version 和 lease。
- 投影写入后仅 `mark_version=claimed_version` 才能删除 Dirty；否则释放 pending 保留新版本。
- `execution` 是原始实时状态与 coverage domain，**绝不创建** `domain='execution'` Dirty，且没有独立聚合投影。它的 queued/running/ended 迁移仍必须可靠写入，但并非每次迁移都标脏。
- `agent_duration` 是唯一的 Agent 时长 Dirty domain。仅当顶层 user Execution（`run_kind='user' AND parent_run_id IS NULL`）的可靠有效区间新增、修正或清除时，在同一事务标记旧/新区间并集 `[started_at,effective_ended_at)` 所相交的十分钟桶；清除可靠终点时按变更前可靠区间清理历史投影。
- `subtask`、`manual_compaction` 与其他非顶层 user Execution 不生成 `agent_duration` Dirty；唯一例外是显式修复并清除先前错误写入的历史时长投影，此时仅标记该错误投影涉及的桶。

## Worker 私有模型 Delivery Outbox

### 路径与隔离

新增 `analyticsWorkerDeliveryOutboxPath(dataDir)`（建议命名）到 `apps/api/src/infra/fs/paths.ts` 或由同一 paths 基础设施导出的共享等价函数，使用 `AWB_DATA_DIR` 派生 Worker 专用目录和 `analytics-delivery.sqlite` 文件。不得在 Worker 中写死绝对路径、`/data` 或散落 JSON 文件。

- Worker 私有 SQLite 与 API 主数据库隔离；只有 Worker 进程打开它。
- 它是可靠交付日志，不是 Dashboard 权威事实、不是聚合源、也不通过 API 读取。
- 文件权限、父目录创建、SQLite journal/锁策略必须最小权限；路径不可由客户端控制。

### 单写者所有权与 fence

```text
worker_analytics_outbox_owner
- singleton integer primary key check (singleton = 1)
- owner_instance_id text not null
- fence_token integer not null
- acquired_at integer not null
```

- Worker 启动首先以 OS 独占文件锁配合 SQLite 短事务取得此 Outbox 的唯一所有权；事务将 `owner_instance_id` 更新为本实例，并单调递增 `fence_token`。实现也可采用等价的 SQLite 独占锁，但必须同时满足本节 fence 语义。
- Outbox 的创建、状态迁移、sender 领取、ACK、gap 写入和清理均携带当前 `owner_instance_id + fence_token` 条件。条件不匹配即失败；新 owner 成功取得 fence 后，旧实例被视为不可再写，不能以重试覆盖新状态。
- 无法取得独占锁或当前 fence 的 Worker 不得标记 ready，也不得开始模型执行；它可以退出并由既有 ProcessManager 受控处理。
- 启动顺序固定为：**取得独占所有权和 fence → 处理恢复遗留状态 → 启动 sender、宣布 Worker ready → 允许模型执行**。这不是依赖 SQLite 单进程偶然写入成功的约定。

### Outbox 实体

```text
worker_analytics_model_delivery
- delivery_id text primary key
- event_id text not null unique
- model_call_id text not null
- phase text not null check (begin | finish)
- execution_id text not null
- run_id text not null
- turn_id text not null
- step integer not null
- attempt_no integer not null
- provider_id text not null
- model_id text not null
- started_at integer null
- payload_json text not null
- state text not null check (prepared | reserved | provider_invoked | pending | delivering | acked | quarantined)
- owner_instance_id text not null
- fence_token integer not null
- attempt_count integer not null default 0
- next_attempt_at integer not null
- created_at integer not null
- last_attempt_at integer null
- acked_at integer null
- quarantine_code text null
```

- `unique(model_call_id,phase)`；`prepared/provider_invoked` 仅允许 `phase='begin'`，`reserved/pending` 仅允许 `phase='finish'`。`delivering/acked/quarantined` 保留原 phase，由 phase 决定恢复为 `provider_invoked` 或 `pending`。
- prepared 必须 `started_at is null` 且 staging payload 不含该字段；finish `reserved` 必须无终态字段、`started_at is null`、payload 仅为无敏感 reservation envelope，sender 严禁投递。`provider_invoked` begin 与所有物化 finish（`pending/delivering/acked/quarantined`）必须 `started_at is not null`，并与可投递 DTO 内值相同。
- Outbox schema 必须以 SQLite `check` 与 Worker 内部 union 同时限制上述 phase/state/started_at 组合；不能只依赖 sender 代码约定。

```text
worker_analytics_model_attempt_reservation
- model_call_id text primary key
- execution_id text not null
- run_id text not null
- turn_id text not null
- step integer not null
- attempt_no integer not null
- provider_id text not null
- model_id text not null
- reserved_future_rows integer not null check (reserved_future_rows in (0,1))
- reserved_bytes integer not null check (reserved_bytes >= 0)
- consumed_bytes integer not null check (consumed_bytes >= 0)
- created_at integer not null
- owner_instance_id text not null
- fence_token integer not null
```

- 每个 Attempt 的标准化 begin、finish、可选 gap DTO 合计最大持久化预算固定为 **64 KiB**；它是 admission 和 reservation 的保守上界，DTO 超过该预算必须在调用 SDK 前拒绝，且不得截断或保存额外内容。
- reservation 只表示**当前有效**预留，绝不保留 `released` 历史行；资源使命完成即在 owner/fence transaction 直接删除该行。完整身份使孤立 reservation 可以安全比对并收敛。
- 创建 Attempt 的同一 owner/fence SQLite transaction 必须同时插入 begin `prepared`、finish `reserved` 与此 reservation。初始 `reserved_future_rows=1` 为唯一可选 Gap 的逻辑行槽位；prepared/reserved envelope 的确定字节 charge 同 transaction 写入 `consumed_bytes`，`reserved_bytes=64 KiB-consumed_bytes`，避免已物化字节与未消费预留重复计入 admission。任一写入失败整体回滚，不得调用 Provider。
- promotion 成功时，`prepared → provider_invoked` transaction 立即释放唯一 Gap 槽位（`reserved_future_rows: 1 → 0`），但保留 reservation 的未消费字节以保障 reserved finish 物化。finish `reserved → pending` 使用该字节预留；其 DTO 完整物化后在**同一** owner/fence transaction 删除 reservation。begin/finish ACK 不负责正常路径 reservation release。
- 逻辑 Gap 物化时 `reserved_future_rows: 1 → 0`，因“一个逻辑槽位变一个物理 Gap 行”不增加有效行占用；Gap 使用相应字节 charge 后删除 reservation。所有删除和状态迁移均按 owner/fence 条件幂等执行。

```text

- model_call_id text not null
- unique(model_call_id)
- execution_id text not null
- run_id text not null
- turn_id text not null
- step integer not null
- attempt_no integer not null
- provider_id text not null
- model_id text not null
- started_at integer null
- gap_kind text not null check (受控 model_delivery_gap_kind)
- detected_at integer not null
- created_at integer not null
- state text not null check (pending | delivering | acked | quarantined)
```

- incident 是 API 已认证 delivery 遭遇永久 `409/422` 时的主库健康诊断，不是 Fact、Gap 或聚合输入。它只记录安全 envelope 中可得的 event/model_call ID、phase、受控错误码和时间，绝不复制 DTO payload、原始错误或任何正文。
- 每个 Worker→API begin、finish、gap delivery 必须在业务 DTO 解析前，从已认证 envelope/header 取得必填、非空、受控格式的稳定 `delivery_event_id`。`delivery_event_id` 是主库 incident 的 `NOT NULL UNIQUE` 幂等键，和业务 DTO 内的 `event_id` 同值但属于传输层前置条件。
- API 在认证和 transport event ID 合法时，即使 body 无法解析，也必须以 `delivery_event_id` 幂等写入 `model_call_id=null` 的 model-domain incident；同一 event 重放返回原 `incidentId`，不重复计数。若 transport event ID 缺失或非法，返回受控协议错误、持续安全告警并 fail-closed，**不创建 incident、也不允许 Worker quarantine**，直到 Worker 协议/实现修复。
- API 必须先在主库 transaction 持久化或重放读取 incident，才能返回带 `incidentId` 的永久错误；该 transaction 失败时返回可重试故障，Worker 不得 quarantine。Worker 只有收到有效 `incidentId` 后才可将 begin、finish 或 gap delivery quarantine；response 丢失时使用相同 transport event ID 重试，取得同一 `incidentId`。
- 条件状态机：初始 `resolution=null/resolved_at=null`；仅允许一次 `null → replayed` 或 `null → confirmed_missing`，且必须在**同一 transaction**同时写入 resolution 与 `resolved_at`。同 resolution 重试返回原 `resolved_at`，不得重写时间；两个 resolution 不可互相覆盖。`confirmed_missing` 仅允许一次 `loss_repaired_at null → 非空`，写入稳定 `loss_repair_generation`；重复同 generation 幂等成功，不同 generation 冲突。`replayed` 不得写 loss repair 字段；其他非法 resolution/resolved_at 字段组合必须由 DB CHECK 和持久层拒绝。
- 可信完整 Fact 重建要修复历史缺失时，必须显式列出并验证目标 incident ID；在**同一主库 transaction**写入对应 Fact/Dirty 与该 incident 的 `loss_repaired_at/loss_repair_generation`。不得按数量批量减计或由普通重启、清理、本地 quarantine 删除推断修复。
- 建议索引 `analytics_model_delivery_incident(resolved_at,occurred_at)`、`analytics_model_delivery_incident(delivery_event_id)`、`analytics_model_delivery_incident(resolution,loss_repaired_at)`。`deliveryIncidentCount` 的唯一 SQL 口径是 `count(*) where resolved_at is null`；历史不可逆缺失数实时定义为 `count(resolution='confirmed_missing' AND loss_repaired_at IS NULL)`，即 `historicalLossCount`。`confirmed_missing` 迁移提交后 incident count 减一、historical loss 加一；`replayed` 仅使 incident count 减一。

- Worker gap delivery 与 API gap 表只记录稳定 ID、受控 kind 和时间；建议主库索引 `analytics_model_delivery_gap(detected_at,resolved_at)`、`analytics_model_delivery_gap(model_call_id)`。它既不是 Fact 也不是聚合输入，不能进入 request_count、模型聚合、时间范围或 Provider/Model 筛选。
- `gap_id` 是主键，`event_id` 用于重放幂等，`unique(model_call_id)` 保证每个 Attempt 最多一个 Gap；`gap_kind` 仅是该唯一 Gap 的分类，三个合法 kind 严格互斥。相同 `model_call_id` 重放只有 gap kind 与完整身份完全一致时才返回原 Gap；kind 不同或任一身份冲突均为不变量损坏，必须隔离/fail-closed，不得覆盖、更不得新增第二行。Gap DTO 保存完整的非敏感调用身份 `execution_id/run_id/turn_id/step/attempt_no/provider_id/model_id`；promotion 两类还必须携带非空 `started_at`，prepared ambiguous 合法为 null。API 必须验证 `execution_id` 存在且其 `run_id` 匹配，并逐项校验 DTO 与同一 `model_call_id` 已有 Fact 的不可变身份。
- 未 resolved 主库 gap 的**全局**数目是 model domain `deliveryGapCount`，不随公开 API 的 `[from,to)`、Provider、Model 或趋势粒度变化。它与全局 unresolved `deliveryIncidentCount`、由 incident 实时查询的 `historicalLossCount` 都是采集健康诊断，不是所选范围模型指标；三者任一非零均使 model coverage degraded。
- 发生可观察 gap 时，Worker 先尝试本地 transaction 写 `worker_analytics_model_gap_delivery`，再由 sender 投递 `POST /internal/analytics/model-delivery-gaps`。API 在一个 Analytics transaction 幂等写入主库 gap、立即检查同一 call 的可信 Fact 并按下述规则写 `resolved_at`，再更新 model Domain State 安全诊断后 ACK；它不标模型 Dirty，因为 gap 不修改模型数值 Fact。网络/5xx/db busy 退避，`409/422` quarantine。gap 写入本地 SQLite 也失败时，只能输出无敏感故障码；不可凭空生成请求或承诺 coverage 可检测所有崩溃。
- Fact 与 gap 的解析是同一主库 Fact+Dirty transaction 的一部分：`post_call_promotion_uncertain` / `post_call_promotion_failed` 仅在完整身份（含非空 `started_at`）一致的 begin **或完整 finish** 成功写入时 resolve；`prepared_expired_ambiguous` 默认永久 unresolved，只有之后同 call、其已记录的完整非时间身份一致的可信 Fact 成功写入才 resolve（prepared 本身依法没有 `started_at`）。Fact 先存在时插入 gap 在该 gap transaction 中立即 resolve，不得短暂增加未 resolved 数；gap 先存在时 Fact 成功即 resolve。身份冲突永不 resolve。
- resolved gap 自 `resolved_at` 起保留 30 天后可清理；unresolved gap 永不自动清理。清理 resolved 行不会改变 coverage，因为它们已不参与 `deliveryGapCount`。

`payload_json` 仅是 schema 验证后的标准 begin/finish DTO：完整不可变身份、不可变 `started_at`、受控 status/reason、Token、cache flags。它不得含 Prompt、回复、Reasoning、原始 usage、原始 error、工具内容或路径。prepared begin 的 `payload_json` 不含 `started_at`，且 `started_at` 列为 null；晋级后在同一 Outbox transaction 填入二者。

约束与顺序：

- `event_id` 稳定且唯一；建议由 `model_call_id + phase` 派生。`unique(model_call_id,phase)` 防止重复交付。
- begin 初始为 `prepared`，finish 同 transaction 初始为 `reserved`；sender **严禁**选择或投递二者。只有 begin 可处于 `prepared/provider_invoked`，finish 只有物化为 `pending` 才可投递。`provider_invoked`/`pending` 被 sender 领取时变为 `delivering`。
- Provider 调用边界越过前，Worker 必须在同一 owner/fence transaction 提交 prepared begin、reserved finish、reservation 实体、一个 gap 行逻辑 reservation 与 64 KiB 字节 reservation。完成 admission 后，晋级、finish 物化或 gap 物化不得因普通逻辑容量阈值被拒绝；它们仍可能遭遇不可预测的真实 SQLite/I/O 故障，并按故障恢复合同处理。
- 调用 SDK 前在内存取高精度 `attempt_boundary_at`，执行 `streamTextFn(request)`。若返回 stream 或同步 throw后 promotion 成功，则在同一可达控制流 transaction 将 prepared 晋级 `provider_invoked` 并写 `started_at=attempt_boundary_at`，同时释放 Gap 槽位；随后才消费 stream 或将预留 finish 更新为 pending。同步 throw也因此计一次 Attempt。
- 若 SDK 调用后 promotion 未成功、但 Worker 仍能操作 Outbox，必须在**一个 owner/fence SQLite transaction**中：使用唯一 Gap 槽位物化 `post_call_promotion_failed` 或 `post_call_promotion_uncertain`、删除/终结 prepared begin、删除未使用 reserved finish、删除 reservation，然后 commit。成功后绝不得遗留 prepared，后续 handoff 也不得为该 Attempt 再建 `prepared_expired_ambiguous`。
- 上述 promotion Gap transaction 的任一步失败或进程崩溃均整体回滚：promotion Gap 不存在，prepared/reserved/reservation 都保留。此后新 owner handoff 才在同一唯一槽位物化 `prepared_expired_ambiguous`，并删除 prepared/reserved/reservation。故 promotion Gap 与 prepared-expired Gap 对同一 Attempt 在有效状态下互斥；恢复发现二者同时存在即视为不变量损坏，安全停机/隔离，不得 ready。
- provider_invoked 与 reserved finish 的崩溃恢复必须使用 reserved 行物化 `interrupted` 或 `unknown` finish，再在该 owner/fence transaction 删除 reservation；不得重新 admission。孤立 reservation 必须按同 call 的 begin/finish/gap 可证明状态收敛：prepared 走 handoff，provider_invoked+reserved 走受控 finish，已物化 finish 或唯一 Gap 则删除 reservation；身份冲突安全停机，绝不永久残留。
- SDK 调用返回/抛错后而晋级前的崩溃、或晋级 transaction 失败，是不能与外部 SDK 消除的极窄窗口。可观察失败写 `analytics_model_delivery_gap(post_call_promotion_failed|post_call_promotion_uncertain)`，使模型 coverage degraded；不得自动投递 prepared 或伪造 Fact。此设计选择不制造幽灵，不承诺 exactly-once。
- finish 必须有与 begin 相同的 non-null `started_at`；无 invoked begin 时不得创建 finish。若 SDK 后晋级失败，不能可靠创建 finish，必须受控收敛 Run 并保留/写 gap。
- 同一 model_call 的 begin 必须先于 finish 创建；finish 允许在 API 未收到 begin 时送达，由 API 完整身份补建 Fact。
- delivery 重放使用同 event_id；API ACK 仅在主库 Fact/状态与 Dirty 同 transaction 成功后返回。
- 409 身份/终态冲突、422 DTO 不合法等永久错误必须由 API 先创建 `analytics_model_delivery_incident` 并返回 `incidentId`，Worker 才进入 `quarantined`，不无限重试；安全记录受控 quarantine_code/incident ID。网络/5xx/db busy 使用指数退避和 next_attempt_at。
- begin 和 finish 的投递可乱序到 API；API 规则确保结果正确。Outbox sender 对同一 model_call 应优先发送 begin，短暂失败不阻塞其他 call；finish 不得覆盖冲突 begin。
- model delivery 的 acked 行在固定 24 小时保留窗口后批量清理；**本地** gap delivery 一旦获得 API ACK 即表示已可靠写入主库，也固定保留 24 小时后清理，绝不查询主库 gap 是否 resolved。主库 gap 的 unresolved/resolved 和 resolved 后 30 天留存仅由 API 主库管理；清理本地 ACKed gap 不改变主库计数或 coverage。`quarantined` 的 30 天仅是告警和人工诊断期限，**不是自动删除期限**：未成功交付的 quarantined 是权威 delivery，只能在人工受控导出/确认丢弃，或修复后成功 ACK 的流程中清理。保留策略不含内容。

容量与 fail-safe：

- 固定默认配置合同：有效行配额最大 **100,000**、最大 **256 MiB**、磁盘剩余扣除 reservation 后必须**严格大于** **512 MiB**、标准 Attempt reservation **64 KiB**、acked 保留 **24h**、quarantined 告警/人工诊断期限 **30d**。实现可使用受控配置键覆盖，但默认值、单位与含义不得变化。
- 有效行占用 = `worker_analytics_model_delivery` 的全部物理未清理行 + `worker_analytics_model_gap_delivery` 的全部物理未清理行 + `worker_analytics_model_attempt_reservation` 的物理行 + 所有 reservation 的 `reserved_future_rows`。新 Attempt 同一 transaction 物化 begin、finish reserved、reservation 实体，并新增一个未来 Gap 逻辑槽位，固定消耗 **4** 个有效容量单位：当前有效占用 **99,996** 可准入，提交后恰为 100,000；99,997、99,998、99,999 或 100,000 均拒绝。
- 字节 admission 使用 SQLite 逻辑已用空间，而不是主文件历史高水位：`(page_count - freelist_count) * page_size + WAL 大小 + SHM 大小 + 所有 reservation.reserved_bytes + 新 Attempt 64 KiB < 256 MiB`；达到或超过即拒绝。新 Attempt 的 64 KiB 是其总预算，写入 prepared/reserved 后以 `consumed_bytes` 反映实际 envelope charge 并仅将未消费部分留在 `reserved_bytes`，因此该公式不重复计算已物化字节。磁盘检查使用当前剩余空间减去所有 reservation 的 `reserved_bytes` 和新 64 KiB 后仍**严格大于** 512 MiB。所有计算、清理与 reservation 写入在同一 owner/fence admission transaction 序列化，不能依赖进程内计数。
- Worker Outbox 首次建库前必须设置 `PRAGMA auto_vacuum=INCREMENTAL`；既有库迁移需在受控维护窗口完成相应重建/启用，不能假定运行时切换立即生效。清理允许清理的 ACK 行后，在非请求关键路径受控执行 WAL checkpoint 与 `PRAGMA incremental_vacuum`，回收 freelist 页面。禁止在每次 admission 或请求路径执行 full `VACUUM`，避免长时间独占和抖动。
- 创建 Attempt 前固定按以下顺序执行：清理超过 24h 的 acked model delivery 和 ACK 超过 24h 的本地 gap delivery；绝不删除 prepared、reserved、provider_invoked、pending、delivering、quarantined 或未 ACK gap；随后运行有效行、逻辑 SQLite 已用空间+reservation 和磁盘 admission。不得删除未 ACK 或 quarantined delivery/gap 腾空间。
- admission 成功后，预留 finish、晋级和 gap 物化不得再被上述逻辑阈值拒绝；仅真实 SQLite 打开/写入/I/O 故障可失败。SQLite admission/写入失败则拒绝调用 Provider。
- Provider 调用前必须先本地 transaction 持久化 prepared begin；这不等同于 API Analytics 暂时故障阻断 Provider。调用后晋级/finish 落盘失败时请求不能撤回：记录安全 gap/错误码、有限重试并受控收敛 Run；不得记录 usage 原始内容补救。
- Worker sender 在 owner fence 建立并完成遗留 prepared 处理后启动。新 owner 在同一恢复 transaction 将所有既有 delivery/gap 行改写为新的 `owner_instance_id/fence_token`，旧 fence 的 SQL 条件更新因此全部失败；随后将遗留 delivering 释放为可投递状态。prepared 仅在 ownership handoff 时转 gap 后清理，绝不恢复发送。API 仅为 invoked begin/finish ACK 后 Fact 才可由 Execution/Worker/Run 收敛 unknown/interrupted。
