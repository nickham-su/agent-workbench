# 实施计划

每阶段完成开发、测试、审查后才进入下一阶段。不得为提前展示页面跳过长期 Fact、Dirty 原子性、Execution handshake 或准确查询。

## 阶段：Analytics Schema、枚举与双写底座

### 目标

建立独立长期 Analytics schema、受控枚举、最小 Fact 与可靠 Dirty；完成安全初始回填协议。

### 修改范围

- `apps/api/src/infra/db/`：Analytics schema/version/迁移与重建边界。
- `apps/api/src/modules/agent/`：Session、消息、Run、工具事务双写。
- 新增 `apps/api/src/modules/analytics/` store/service/dirty/outbox 边界。
- `packages/shared`：受控 enum 与内部 DTO 契约。

### 关键步骤

- 建 `ANALYTICS_SCHEMA_VERSION`，确认 Analytics 不进 `AGENT_DOMAIN_TABLES`、无强 FK。
- 建 Fact、Dirty lease、`analytics_domain_state`、`analytics_model_call_fact(execution_id,status,updated_at)` 索引、DB check；同步 TS union、TypeBox、DTO。
- 在业务事务写 Session/Message/Run/Tool Fact 与 Dirty；不可变身份冲突拒绝。
- 工具真实终态写 `duration_completed_at`；恢复/rebuild unknown 仅写 completed_at，不写可靠时长终点。
- 按 `model|run|execution|agent_duration|tool|message|session|worker|git` 建 Domain State；实现 `collection_started_at`、watermark、先双写后回填。agent_duration 覆盖引用 execution，Git State 仅 job freshness；按逐表矩阵处理旧 running/null。
- 编写 Agent rebuild 前收敛 hook 的接口，但在下一阶段接入 Execution。

### 验收门槛

- Fact 与 Dirty 原子性、枚举同步、回填并发、Agent schema rebuild 隔离测试通过。
- Analytics schema/日志/API 无敏感正文列或字段。
- 不存在“业务成功但最小 Fact/Dirty 丢失”的容错分支。

### 回滚

- 可隐藏 Dashboard/暂停聚合，不能删除 Fact。
- 修复事务问题后重试业务，不得改为静默忽略 Fact/Dirty 失败。

## 阶段：Execution、handshake 与 Agent 域重建

### 目标

建立 queued/running/ended 权威 Execution，保证真实开始后才执行，支持恢复、重建和实时 Run 查询。

### 修改范围

- `analytics_run_execution`、内部 start 契约。
- lifecycle application/persistence、Worker runner、local fallback、ProcessManager exit、Agent schema rebuild 边界。

### 关键步骤

- handoff 创建 queued Execution 原始事实；execution 不创建 Dirty。
- Worker `startRun()`、nested `processNestedRunWithController()`、local `AgentRuntime.startRun()` 执行 await start handshake。
- handshake 未确认不进入 `processRun`；失败交 API/recovery 收敛。
- 终态/取消/入队失败/恢复/exit/rebuild 关闭 Execution；只支持 `exact|unknown`，用 `effective_ended_at` 隔离离线时长。顶层 user 可靠切片新增、修正、清除才标 `agent_duration` Dirty；subtask/manual compaction 不标。
- 在 `rebuildAgentDomain()` 的同一 transaction 收敛未结束 Execution、running Run Fact、queued/running Tool Fact、相应 Dirty 后再 drop/create/校验；失败整体回滚。
- 完成当前 queued/running 原始查询。

### 验收门槛

- user/subtask/manual compaction/recovery/local fallback 均有正确 Execution。
- start handshake、未知结束、API+Worker 同时停机、rebuild 全部通过。
- 顶层 user 时长不含子任务/manual compaction，且无恢复间隔。

### 回滚

- 不得回退为 `agent_run.status` 或 created/updated 时间统计。
- handshake 失败不得继续模型/工具执行。

## 阶段：模型 Attempt 与 Worker restart

### 目标

实现请求级模型指标及不重复的 Worker 重启统计。

### 修改范围

- 模型/Worker/restart Fact、Worker 私有 Delivery Outbox、internal API、Worker runner、ProcessManager、`paths.ts`。

### 关键步骤

- 在 `paths.ts` 同一派生体系新增 `analyticsWorkerDeliveryOutboxPath(dataDir)`；Worker 私有 SQLite Outbox 不得直写 API 主库，也不是查询权威。
- 建立 Outbox 独占 owner lock 与 `owner_instance_id/fence_token`；启动严格按取得 fence、立即处理遗留 prepared、启动 sender/ready、允许模型执行。未取得 fence 不得执行，旧 owner 写入必须失败。
- 每次 `streamTextFn(request)` 生成含 execution_id 的完整身份 Attempt；调用前单 transaction 写无 started_at 的 prepared begin、reserved finish、reservation 实体、Gap 槽位和 64 KiB reservation。以 delivery 行+Gap 行+reservation 行+逻辑槽位的四单位做 100,000 admission（99,996 可准入、99,997 拒绝），以逻辑 SQLite 已用空间+WAL+SHM+reservation 做 `<256MiB` admission，并扣 reservation 后校验磁盘 `>512MiB`；成功才调用 SDK。
- SDK 返回或同步 throw 后立即晋级 provider_invoked，并将已预留 finish 物化为同一 started_at DTO；API Fact+Dirty transaction 后 ACK。admission 成功后 finish/Gap 不得被逻辑满额拒绝；身份或 started_at 冲突严格 `409`。
- 实现 delivery ID/event ID、唯一 `(model_call_id,phase)`、gap 的 `gap_id/event_id/model_call_id` 唯一约束、prepared/provider_invoked/pending/delivering/acked/quarantined、指数退避和 ACK。Gap kind 仅是唯一 Gap 分类；kind 或身份不同的同 call 重放必须隔离/fail-closed，不能共存或覆盖。resolved gap 30d 后可清理，unresolved 不自动清理；quarantined 30d 仅告警/人工期限，不能自动删除。
- prepared/reserved 永不投递；handoff 的每条遗留 prepared 必须在同 transaction 用预留 Gap 物化、清理 prepared/reserved、删除 reservation，任一步失败 fail-closed 且不计 request；活跃 prepared 不按 TTL 清理。post-call promotion 失败必须以互斥 transaction 物化 promotion Gap 并清理 prepared/reserved/reservation；若回滚才允许 handoff 建 prepared-expired Gap。`provider_invoked+reserved` 恢复为 interrupted/unknown finish 后删除 reservation，孤立 reservation 按可证明状态收敛。
- 首次建 Outbox 前启用 `auto_vacuum=INCREMENTAL`；ACK 清理后在受控路径 checkpoint + incremental vacuum，禁止请求路径 full `VACUUM`，用逻辑已用空间保证清理后可恢复准入。
- 实现 API 主库 `analytics_model_delivery_incident`：begin/finish/gap 均以认证 envelope 的 `delivery_event_id` 作 `NOT NULL UNIQUE` transport 幂等键，body invalid 且 ID 有效可记录无 model_call ID incident；ID 缺失/非法 fail-closed、不建 incident、不 quarantine。对 `resolution/resolved_at` 建 DB check；resolution 迁移同 transaction 同时写两列、相同 resolution 保留原 resolved_at、不同 resolution 冲突。`deliveryIncidentCount` 固定按 `count(*) where resolved_at is null`，historical loss 由未修复 confirmed-missing incident 查询；可信重建必须指定 incident IDs 并和 Fact/Dirty/repair generation 同 transaction。
- ACKed model delivery 与 ACKed local Gap 均保留 24h 后清理；本地 Gap 清理不查询主库 resolved。绝不删未 ACK、reserved、unresolved 或 quarantined 腾空间。
- prepared 打开/写入/空间/容量失败必须拒绝 Provider；SDK 后晋级/finish 本地失败不得重发 Provider，有限重试后按 Execution/Worker/Run 可证明状态收敛。
- 实现 usage normalize、cache comparable/verified、分状态可靠时长。
- 实现基于 Worker/Execution/Run 可证明状态的 Attempt 收敛；无 total timeout 不做 TTL。
- 实现稳定 worker instance/restart attempt；初次启动与自动重启分离、outcome 唯一结算；`restart_scheduled` 仅内部诊断，排除公开聚合。

### 验收门槛

- retry、timeout、cancel、interrupted、identity/start时间冲突、execution/run 校验、cache coverage、无 total timeout、乱序/重放/ACK/quarantine 测试通过。
- API 暂时不可用不阻断 Provider；Outbox begin 本地不可持久化则不调用 Provider，主库 Fact/Dirty 不丢失。
- Outbox owner/stale fence、handoff 与 promotion 全步骤故障注入、同 call 的两 promotion kind 与 promotion/prepared-ambiguous 双 Gap 损坏检测、活跃 prepared 不清理、99,996/99,997 行配额、64KiB/256MiB/512MiB 边界、长期清理后重新准入、admission 后 finish/Gap、孤立 reservation 收敛、quarantined 不自动删除、Worker/API 重启恢复、pre-call crash 不计数、同步 throw 计数、post-call gap 降级且不伪造 Fact、Gap 本地 ACK 清理、transport event ID/response lost/body invalid/缺失 ID、incident resolution check/幂等/计数切换/原子回滚、incident repair generation、全局 coverage、隐私审计测试通过。
- restart ready failure+exit 不双计，normal stop 不计 crash。

## 阶段：准确聚合、趋势与查询 API

### 目标

实现十分钟缓存、lease、可用桶判断、准确 Fact 回退和后端趋势点。

### 修改范围

- `dashboard_*_10m`、Dirty worker/job state、Analytics query/API/TypeBox。

### 关键步骤

- 按 domain 实现可组合 SQL、显式空投影、封闭/Dirty/rebuild 可用桶判定。
- 实现 lease claim、重算投影+删除 Dirty 原子提交、48h 兜底与全量重建。
- 实现每个范围片 Fact/聚合二选一、Fact 安全预算与 `ANALYTICS_DATA_INCOMPLETE`。
- 实现 `10m/hour/day/week/month`、默认规则、最大点数、IANA day/week/month 点。
- 返回按 domain freshness/coverage，拒绝不支持 filter。

### 验收门槛

- Dirty/缺失/open/rebuild 桶回退、dataIncomplete、跨桶、DST、逐点趋势等价测试通过。
- 聚合删除后可从 Fact 重建；任何旧投影不会冒充准确。

## 阶段：Git Fact、全 source scan 与 generation

### 目标

建立准确的 current-reachable Git 集合、coverage 与 Git 聚合。

### 修改范围

- Git Fact/scan/source/membership/repo state、scanner、调度、Git 聚合。

### 关键步骤

- 开始时快照 Mirror 和关联 Workspace source；扫描全部 eligible source。
- 开始短 transaction 领取并递增 `next_generation`；失败 generation 不回退、不复用。
- 任一 source 失败整体失败，保留 pointer；全部成功才在同一 transaction 写 Fact、membership、Scan coverage、Scan completed/时间、pointer 与 Dirty，coverage 只存 Scan。
- 解析 Committer Date、merge、binary、rename；按 repo+sha 去重。
- 实现初次上限、coverage、current+前二 generation/7 天诊断留存。

### 验收门槛

- 未 push、多 Workspace、部分 source 失败、failed generation gap、切换写入 fault injection 回滚、rebase、merge/binary、pointer/coverage 来源/Repo status/retention 测试通过。
- 不存 Commit Message、路径、Diff、绝对路径或 remote URL。

## 阶段：Workbench Dashboard

### 目标

在现有 Workbench 壳内提供安全、可解释的 Dashboard tab。

### 修改范围

- Shared public contracts、Fastify routes、Workbench activeKey/navigation、Dashboard components/tests。

### 关键步骤

- `/dashboard` 映射 `WorkbenchPage`，新增 dashboard tab/activeKey；不建无壳 DashboardPage。
- 接入概览、Agent、模型、工具、Git、Worker 数据与按 `analytics_domain_state` 返回的九域 status；execution 不显示 pending Dirty、agentDuration 显示时长 Dirty；模型 Gap、delivery incident、historical loss 显示全局采集健康诊断/coverage degraded，Git coverage 按 TypeBox status 判别联合仅展示 Repo 级 current Scan 诊断。
- 严格隐藏模型/工具 Workspace filter；显示 coverage/null/dataIncomplete。
- 后端趋势 points 直接渲染，前端不二次聚合。

### 验收门槛

- OpenAPI、类型检查、鉴权/filter 拒绝、Workbench 路由/组件状态测试通过。
- 页面无绩效、时间杠杆、推理耗时或 Agent Git 归因文案。

## 阶段完成后的自检

每阶段按实际变更运行相应测试；通用最低集：

```bash
npm run build -w packages/shared
npm run typecheck -w apps/api
npm run typecheck -w apps/web
npm run typecheck
```

新增专项测试路径在实现后写入对应 package script 或 CI，避免文档引用不存在的固定文件名。Worker/API 生命周期变更必须使用真实进程或等价集成测试。
