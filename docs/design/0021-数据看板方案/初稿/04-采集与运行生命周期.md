# 采集与运行生命周期

## 写入可靠性边界

### 业务事实与 Dirty 的原子关系

以下事实一旦缺失，Agent 域重建后无法可靠补齐；其创建/状态变化与其**适用的** Dirty Bucket 标记必须在**同一 SQLite transaction**内：

- `analytics_session_fact`、`analytics_message_fact`、`analytics_run_fact`、`analytics_tool_fact`。
- `analytics_run_execution` 的 queued、running、ended 迁移必须可靠，但 `execution` 是原始状态/coverage domain，不创建聚合 Dirty。
- 只有顶层 user Execution 的可靠有效区间新增、修正或清除，才同事务标记 `domain='agent_duration'` Dirty；queued/running、无可靠区间和非统计对象均不标 Dirty。
- API 主库中的 `analytics_model_call_fact` begin/finish 及其模型 Dirty。
- Worker instance/restart/event 及其 Worker Dirty。
- Git Fact、成功 scan membership/current pointer 及其 Git Dirty。

聚合作业可失败重试，且不得阻断 Agent；但 Dirty 不得成为“写 Fact 成功、标脏失败后永久丢失”的 Best-effort。若业务 SQLite transaction 无法同时包含某种外部收集结果，必须先将可重试的受控 outbox 记录与业务变更同事务保存；outbox 成功落 Fact 时再与 Dirty 同事务提交。

### 不阻断业务的边界

- Worker 私有 Delivery Outbox 不是 API 主库 Fact：它只可靠保存、重放无敏感模型 DTO，Dashboard 和聚合绝不读取它。
- Provider 网络调用不等待 API Analytics 成功；但调用前必须先成功将**不可投递的 prepared begin**事务写入 Worker 私有 Outbox。SDK 调用返回或同步 throw 后才能晋级为可投递 invoked begin。API 暂时不可用时 sender 异步重试，不阻断 Provider；Outbox 本地不可写则拒绝调用 Provider，避免真实请求没有可恢复事实。
- Git scan、Worker event 记录、聚合与全量重建不阻断 Commit、Push、Sync、Agent 运行或 Worker 重启。
- 不得把“模型/Worker/Git 可异步采集”误解为允许丢失已写 Fact 对应的 Dirty。

## Run 与 Execution

### 现状与必要性

当前 `SqliteRunLifecyclePersistence` 的 Run 激活路径创建业务 Run 时已写 `status='running'`，即使 Worker 尚未从内存队列取出它。因此：

- 不得用 `agent_run.status='running'` 区分 queued/running。
- 不得用 `agent_run.created_at/updated_at` 计算真实执行时长。
- 必须使用 `analytics_run_execution` 记录 queued、实际开始和结束。

`RunLifecycleApplication.enqueueActivatedRunOrReconcile()` 是 user、manual compaction、启动恢复共用的 fenced handoff，是创建或确保 queued Execution 的统一边界。

### Execution 状态机

```text
不存在
  └─ queued
       ├─ start handshake 成功 → running
       │    └─ 终态/取消/Worker exit → ended
       └─ 开始前取消/明确 enqueue 失败/恢复替代 → ended
```

| 当前 | 目标 | 条件 | 时长 |
| --- | --- | --- | --- |
| 无 | `queued` | Run 已激活且将 handoff | 不计 |
| `queued` | `running` | Runtime 已取得内存执行权且 start handshake 已持久化 | 写 `started_at` |
| `queued` | `ended` | 开始前取消、enqueue 明确失败、Worker exit 前未开始 | 不计 |
| `running` | `ended` | 本进程观察到业务完成、失败或取消 | `exact`，`effective_ended_at=ended_at` |
| `running` | `ended` | Worker 已观察异常 exit，或恢复/重建发现遗留运行态 | `unknown`，`effective_ended_at=null` |

禁止：

- `ended` 回到 queued/running；恢复必须新建更高 `attempt_no`。
- 同一 Run 同时有多个未结束 Execution。
- 使用最后日志、最后消息、心跳或下次启动时间推断 `effective_ended_at`。
- 用子任务完成关闭父 Execution。

### Execution start handshake

Worker 拿到内存队列项不等于可以执行。顶层 Worker 的严格顺序：

```text
queue 取出 → 占用内存执行权 → await internal execution/start
  → 成功：processRun
  → 失败：不调用模型/工具；释放内存执行权；由 API 受控失败/恢复收敛
```

- 内部 start API 以 `execution_id/run_id/attempt_no/worker_instance_id/started_at` 条件更新 queued→running，必须幂等。
- start API 返回冲突或非当前 Execution 时，Worker 不得调用 `processRun`。
- 若网络超时导致“是否已写入”未知，Worker 不得直接继续；应通过同一幂等 ID 重试查询/写回，仍无法确认则交由 API reconciliation，而非无记录执行。
- local fallback 不经过 Worker HTTP；它必须在取得执行权后、调用 `processRun` 前以同一 API 进程事务完成 queued→running。迁移失败同样不得生成 assistant、调用工具或完成 Run。

接入点：

| 路径 | queued | running handshake | ended |
| --- | --- | --- | --- |
| 顶层 user Run | 统一 handoff | `AgentRunner.startRun()` | `completeRunFromWorker()` 对应事务、取消、失败 |
| manual compaction | 统一 handoff | `AgentRunner.startRun()` | compaction 终态事务 |
| 启动恢复 | 先关闭旧 Execution，再统一 handoff 新 attempt | `AgentRunner.startRun()` | 正常或再次恢复 |
| nested subtask | 子 Run 激活后创建 queued | `processNestedRunWithController()` | 子 Run 终态事务 |
| local fallback | 统一 handoff | `AgentRuntime.startRun()` 的同进程事务 | `AgentRuntime.processRun()` 的终态端口 |

nested 子任务不占顶层 Worker 独立槽位，但必须记录 Execution，才能使当前 running Run 数完整；本期不计算 Worker 利用率。

### Worker exit、同时停机与 Agent 域重建

- `AgentWorkerProcessManager` child `exit`（且非 `stop()`）是 Worker 异常退出唯一权威观察点。
- 对该 instance 的未结束 Execution，事务关闭为 `ended`；若之前没有进程内观察到正常终点，写 `ended_at=exit 观察时间`、`effective_ended_at=null`、`end_time_quality='unknown'`。
- API 与 Worker 同时退出或机器断电时，不产生 Worker crash 事件。启动恢复将遗留 Execution 收敛为 unknown；离线区间绝不进入 Agent 时长。
- `rebuildAgentDomain()` 必须在其**同一个 SQLite transaction**中先收敛 Analytics，再执行 Agent 域 drop/create/校验：所有未结束 Execution 设置 `state='ended'`、`ended_at=发现时间`、`effective_ended_at=null`、`end_time_quality='unknown'`、`end_reason='agent_domain_rebuilt'`；相关 Run Fact 设置 `lifecycle_status='interrupted'`（无法证明时 `unknown`）并写 `terminal_at`。
- 同一 transaction 还必须将所有 `queued/running` Tool Fact 收敛为 `status='unknown'`、`completed_at=发现时间`、`duration_completed_at=null`，并为 Run、Tool 及顶层 user Execution 变更前可靠有效区间所涉的 `agent_duration` 桶标记 Dirty。Execution 本身不标 Dirty；若旧/新可靠终点被修正或清除，标记旧/新区间并集。任何一步失败回滚时，Analytics 收敛、Dirty 和 Agent rebuild 均回滚。
- 事务提交后当前 queued/running 查询不得残留重建前 Execution 或 Tool Fact。

## 模型 Attempt

### 采集边界与顺序

`AgentRunner.runModelStep()` 每次进入 `streamTextFn(request)` / SDK Provider 调用边界是一条 Attempt：一个 Run 有多轮模型步骤，同一步重试也有多个 Attempt。`started_at` 是调用前在内存捕获的 `attempt_boundary_at`，但只在随后 SDK 调用返回或同步 throw 且 Outbox 晋级成功后持久化；它不表示网络层实际送达。

每个 Worker 必须在启动时先取得 Worker 私有 Outbox 的独占 owner lock/fence，处理恢复遗留状态后才启动 sender、宣布 ready 和允许模型执行。取得失败或 fence 不匹配时不得调用 `streamTextFn`；旧 owner 的任何 prepared/晋级/finish/ACK/gap/清理写入都必须条件失败。

本期不能、也不声称外部 SDK 调用与 Worker SQLite 的 exactly-once 原子性；为避免预调用崩溃制造幽灵请求，执行以下顺序：

- Worker 生成稳定 `model_call_id` 与完整不可变身份：`run_id/execution_id/turn_id/step/attempt_no/provider_id/model_id`。
- 在调用 SDK 前的同一 owner/fence SQLite transaction，先完成 capacity admission，并创建不带 `started_at` 的 `prepared` begin、同 call 的 `reserved` finish 行、reservation 实体、一个未物化 Gap 行槽位和 **64 KiB** 字节 reservation。有效占用同时计 delivery 物理行、Gap 物理行、reservation 实体行和未来 Gap 槽位；新 Attempt 固定消耗 4 个单位，99,996 可准入，99,997 及以上拒绝。字节使用逻辑 SQLite 已用空间加 WAL、SHM 和未消费 reservation 计算；sender 严禁读取或投递 prepared/reserved；admission、写入或磁盘检查失败时不调用 SDK，Run 受控失败。
- 调用前在内存取高精度 `attempt_boundary_at`，执行 `streamTextFn(request)`。无论得到 stream 还是同步 throw，均立即在同一可达控制流中 transaction 执行 `prepared → provider_invoked`，把 `started_at=attempt_boundary_at` 填入 delivery 列和 begin DTO，并释放唯一未来 Gap 槽位；晋级成功前不得消费 stream。
- SDK 同步 throw 已跨过调用边界：晋级成功后将预先存在的 `reserved` finish 行原子更新为带同一 started_at 的 `failed` `pending`，再按正常 sender 流程投递，因此计一次请求。SDK 返回 stream 时，晋级成功后才继续消费流、处理 usage 和终态。
- 若 SDK 后 promotion 未成功但 Outbox 仍可写，必须以单一 owner/fence transaction 物化 promotion Gap、删除 prepared/unused reserved、删除 reservation 后 commit；提交成功后 handoff 不得再建 prepared-expired Gap。若该 transaction 回滚或进程崩溃，则 promotion Gap 不存在且 prepared/reserved/reservation 保留，后续仅由 handoff 物化 `prepared_expired_ambiguous`。恢复发现两类 Gap 同时存在必须隔离并 fail-closed。
- sender 只投递 `provider_invoked` begin 与 `pending` finish；每个 begin、finish、gap 都在认证 envelope/header 携带稳定的 `delivery_event_id`，并与业务 DTO 的 `event_id` 一致。API 在 body 解析前读取并校验该 ID，在一个主库 Analytics transaction 中验证 `execution_id` 存在且 `execution.run_id=run_id`，写/更新 Fact 与模型 Dirty，提交成功后才 ACK。
- 流结束、错误、timeout 或取消后，先将同一完整身份且携带非空 started_at 的 finish 持久化为 `pending`，再异步投递。finish 可先到 API 并完整补建，但不可覆盖冲突 Fact。
- finish 完整物化后在同一 owner/fence transaction 删除 reservation；`provider_invoked+reserved` 崩溃恢复则使用 reserved 行物化 `interrupted|unknown` finish 后删除 reservation。begin 或 finish API 投递失败仅影响 sender 重试，不阻断 Provider；网络/5xx/SQLite busy 指数退避；认证与 `delivery_event_id` 有效的 `409` 身份或终态冲突、`422` DTO 非法仅在 API 返回 incidentId 后进入 quarantine，均不得无限重试或泄露原始内容。
- 调用 SDK 前崩溃仅留下 prepared、reserved finish 与 reservation；新 Worker 对每条遗留 prepared 必须在一个 owner/fence transaction 内使用预留 gap 槽位幂等创建 `prepared_expired_ambiguous` gap、删除 prepared 与 reserved finish、释放 reservation后提交，**不投递 prepared、不建 Fact、不计请求**。不使用 TTL/年龄阈值；任一步失败则整体回滚且不得 ready/sender/模型执行，活跃 owner 的 prepared 不被后台清理。该 gap 只降 coverage，绝不自动重发 SDK 或估算请求。
- SDK 调用后、Outbox 晋级前崩溃，或晋级本地写失败，是外部调用与本地事务无法完全消除的极窄窗口。可观察时写 `analytics_model_delivery_gap` 并使模型 coverage degraded；不得把 prepared 投递或补造 Fact。晋级写反复失败时已发生调用不可撤销：受控失败 Run、有限本地恢复尝试，但不写原始 usage/错误补救。

Gap sender 用稳定 `gap_id/event_id` 重放；Worker Outbox 与 API 都以 `model_call_id` 保证每 Attempt 至多一个 Gap。重放仅在 gap kind 和完整身份一致时幂等返回原 Gap；任一 kind/身份冲突均隔离、fail-closed，绝不覆盖或新增第二个 Gap。post-call promotion 两类 gap 在身份一致的 begin 或完整 finish 成功写 Fact+Dirty 的同一 transaction resolve；prepared ambiguous 默认不 resolve，只有后续身份一致可信 Fact 才 resolve。gap 先到 Fact 后到时由 Fact transaction resolve；Fact 先到 gap 后到时 gap 写入 transaction 立即 resolve。Gap API ACK 后 Worker 本地改 acked，固定 24h 后即可清理，绝不依赖主库 resolved；主库 Gap 状态才决定全局健康计数。gap 从不进入请求数、模型聚合或任何时间/Provider/Model 筛选，公开的全局未 resolve 数仅作采集健康诊断。

当 API 对认证且 `delivery_event_id` 有效的 delivery 返回 `409/422`，它必须已持久化并返回 `incidentId`；body 无法解析但该 ID 有效时也创建 `model_call_id=null` incident。ID 缺失/非法时 API 返回协议错误、Worker 告警并 fail-closed，既不建 incident 也不得 quarantine。Worker 仅在收到该 ID 对应的 incidentId 后 quarantine。未 resolve incident、未 resolve gap 或未修复 `confirmed_missing` incident 都会令 coverage degraded；本地删除 quarantined 不得解除主库 incident。

begin/finish DTO 必须携带相同完整不可变身份、**非空 `started_at`** 和必填 `execution_id`。begin 已存在时逐项验证，不一致（包括 started_at）返回 `409`；begin 缺失时仅完整身份齐全、Execution/Run 一致性校验通过才可补建。任何冲突终态不能覆盖。Outbox 的状态、ACK、容量、清理与隐私边界以[数据与实体设计](./03-数据与实体设计.md)为准。

### 状态与使用量

状态优先级：外层用户/父任务 abort 为 `cancelled`；idle/total 标志为 `timed_out`；已观察 Worker exit 为 `interrupted`；其他受控异常为 `failed`；Execution/Run 已结束却无法判断 Attempt 为 `unknown`。

唯一 `normalizeModelUsage()` 输出 Token、`total_source`、`cache_comparable`、`cache_write_verified`。不保存 stream chunk、原始 usage、Provider request/response 或错误文本。

### 不用纯 TTL 收敛

running Attempt 的收敛只以可证明状态触发：

- Worker unexpected exit → `interrupted`。
- Run/Execution 取消 → `cancelled`。
- Execution 已 ended、Run 已终态但 Attempt 未闭合 → `unknown`。
- Worker/Execution/Run 仍活跃 → 不得仅按年龄收敛。

当 profile 配置了有限 total timeout 时，超过该 timeout 加合理控制面宽限仍可作为额外兜底，且只用于发现应已结束却未闭合的异常；没有有限 total timeout 的请求禁止 TTL 收敛。

## 工具、消息与 Session

### 工具

在现有工具 store/service 的创建、开始和终态事务中镜像最小字段到 `analytics_tool_fact`：

- 创建：写 `queued/tool_name/created_at`。
- 开始：写 `running/started_at`，但 Dirty 仍标记 `created_at` 桶。
- 真实观察到 completed/failed/cancelled 终态：写 status、`completed_at` 与 `duration_completed_at`，仍标记 `created_at` 桶。
- 恢复或 Agent rebuild 收敛为 `unknown`：写 `completed_at=收敛时间`、`duration_completed_at=null`，不得改为 failed，也不得伪造时长。
- 工具时长只能是 `duration_completed_at-started_at`；`completed_at` 只是状态收敛时间，不能替代时长终点。

不保存输入、结果、Artifact、错误；本期表中不保存 Workspace，API 也不提供工具 Workspace 筛选。

### 消息与 Session

- Session 创建事务写 `analytics_session_fact`。
- user 消息创建事务写 `analytics_message_fact`。
- 两者主键等于业务 ID，重试 `insert or ignore` 后验证身份；不写标题、正文、附件信息。

## Worker 生命周期

`AgentWorkerProcessManager` 是 spawn、ready、exit、退避和熔断边界。采集规则：

| 时机 | 记录 |
| --- | --- |
| 初次启动 spawn | instance + `spawned`，无 restart attempt |
| 初次启动 ready | instance `ready_at` + `ready` |
| 初次启动失败 | instance `startup_failed` + 诊断 event，不计 restart failed |
| 非预期 exit | instance `unexpected_exit` + event，创建 restart chain |
| 计划 restart | 仅内部诊断 `restart_scheduled` |
| 实际调用 restart start | 创建 `restart_attempt_id`、写 `restart_attempted` |
| attempt ready + ready hook 成功 | 唯一结算 `succeeded`、写 `restart_succeeded` |
| attempt ready 失败或退出前未 ready | 唯一结算 `failed`、写 `restart_failed` |
| stop() 退出 | `expected_stop`，不写 unexpected exit |

instance/restart/event/Dirty 共同落在同一 Analytics transaction。既有退避、熔断和停止语义不得被统计写入改变。
`restart_scheduled` 可留在内部 `analytics_worker_event` 排障，但**不得**写入 `dashboard_worker_10m`、公开 Worker API 或其趋势/概览计数。

## 审查检查点

- 可靠事实/Execution 与 Dirty 是否同事务；异步外部来源是否有持久 outbox？
- Worker 是否 await start handshake 成功后才 `processRun`？local fallback 是否等价？
- 模型 begin 是否先写不可投递 prepared，且 sender 仅发送 invoked begin / pending finish？
- SDK 同步 throw 是否仍晋级 invoked、写 failed finish 并计一次；pre-call 崩溃是否绝不制造 Fact？
- API ACK 是否严格晚于 Fact+Dirty 提交，post-call/pre-promotion gap 是否只降 coverage、不伪造 Fact？
- 是否覆盖 nested subtask、恢复、manual compaction、取消与 Agent rebuild？
- 模型 finish 是否完整身份校验并拒绝 `409` 冲突？
- 是否根据可证明 Worker/Execution/Run 状态收敛 Attempt，而不是纯 TTL？
- 是否未把任何正文、工具参数/结果、错误文本或路径传入 Analytics DTO/日志？
